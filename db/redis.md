# Redis 架构与技术文档

## 第1章：定位与数据模型

### 1.1 Redis 是什么？解决什么问题？

Redis（Remote Dictionary Server）是一个开源的、基于内存的高性能键值存储数据库。它的核心定位涵盖以下四个维度：

1. **内存数据库**：所有数据存储在内存中，提供微秒级的读写响应。
2. **缓存**：作为关系型数据库（如 MySQL）的前置缓冲层，大幅降低数据库 I/O 压力。
3. **消息中间件**：通过发布/订阅（Pub/Sub）或 Streams 实现轻量级的消息队列功能。
4. **计数器与限流器**：利用原子操作实现高并发场景下的精确计数与流量控制。

**与 Memcached 对比**

Memcached 是纯粹的内存缓存，而 Redis 在功能上更为丰富：

- **数据结构**：Memcached 仅支持简单的 Key-Value（字符串），Redis 支持 String、List、Hash、Set、ZSet 等丰富结构。
- **持久化**：Memcached 重启后数据丢失，Redis 支持 RDB 快照和 AOF 日志持久化。
- **线程模型**：Memcached 采用多线程模型，Redis 核心命令执行采用单线程模型（6.0+ 引入多线程 I/O），避免了锁竞争。

**与关系型数据库（RDBMS）对比**

- **存储介质**：RDBMS 数据主要存储在磁盘，Redis 存储在内存。
- **事务支持**：RDBMS 支持强 ACID 事务，Redis 仅支持简单的 MULTI/EXEC 事务（不具备回滚能力）。
- **查询能力**：RDBMS 支持复杂的 SQL 关联查询，Redis 仅支持基于 Key 的简单查询及特定结构的内置命令。

| 对比维度 | Redis | Memcached | RDBMS (如 MySQL) |
| :--- | :--- | :--- | :--- |
| 存储介质 | 内存 (支持持久化) | 纯内存 | 磁盘 (内存作缓冲) |
| 数据结构 | String/List/Hash/Set/ZSet等 | 仅 Key-Value | 关系表 |
| 线程模型 | 单线程执行 (6.0+ 多线程I/O) | 多线程 | 多线程 |
| 查询语言 | 丰富的内置命令 | 仅 get/set | SQL |
| 事务支持 | 弱事务 (无回滚) | 不支持 | 强 ACID 事务 |

### 1.2 五大基本数据类型

1. **String（字符串）**：最基础的类型，可存文本、数字或二进制数据。
   - *示例*：**分布式锁**。使用 `SET lock_key value NX EX 10` 实现互斥访问，NX 保证不存在时才设置，EX 设置 10 秒自动过期防死锁。
2. **List（列表）**：双向链表结构，支持头尾插入和范围查询。
   - *示例*：**消息队列**。生产者使用 `LPUSH` 将消息推入列表，消费者使用 `BRPOP` 阻塞获取消息，实现异步解耦。
3. **Hash（哈希）**：键值对集合，适合存储对象。
   - *示例*：**用户信息缓存**。使用 `HSET user:1001 name "Alice" age 25` 存储用户属性，通过 `HGET` 局部获取，避免序列化整个对象的开销。
4. **Set（集合）**：无序、不重复的字符串集合。
   - *示例*：**抽奖系统**。使用 `SADD` 将参与用户加入集合，使用 `SRANDMEMBER` 随机抽取中奖者，天然去重。
5. **ZSet / Sorted Set（有序集合）**：在 Set 基础上增加 score（分数）排序。
   - *示例*：**游戏排行榜**。使用 `ZADD leaderboard 95.5 "player_A"` 记录分数，使用 `ZREVRANGE leaderboard 0 9` 获取前 10 名玩家。

### 1.3 扩展数据类型

1. **Bitmaps（位图）**：本质是 String，通过位操作实现极致的空间压缩。
   - *示例*：**用户活跃统计**。使用 `SETBIT active:20231001 10086 1` 记录用户 ID 为 10086 的用户当天活跃，统计连续签到可使用 `BITCOUNT` 和 `BITOP`。
2. **HyperLogLog（基数统计）**：用于估算不重复元素数量，固定消耗约 12KB 内存。
   - *示例*：**网站 UV 统计**。使用 `PFADD page_uv:20231001 user_1 user_2` 记录访问，使用 `PFCOUNT` 获取近似 UV 数，无需存储海量用户 ID。
3. **Geo（地理位置）**：用于存储和查询地理坐标。
   - *示例*：**附近的人**。使用 `GEOADD users 116.40 39.90 "user_A"` 录入坐标，使用 `GEORADIUS` 查找 5km 内的其他用户。
4. **Streams（消息流）**：Redis 5.0 引入，支持多消费者组、消息确认（ACK）和持久化。
   - *示例*：**可靠消息队列**。生产者 `XADD` 写入消息，消费者通过 `XREADGROUP` 消费并 `XACK` 确认，支持消息重试与回溯。

### 1.4 底层编码映射表

Redis 会根据数据量和元素大小动态选择底层编码，以平衡内存与性能：

| 数据类型 | 紧凑编码 (小数据量) | 标准编码 (大数据量) | 编码升级条件示例 |
| :--- | :--- | :--- | :--- |
| String | SDS / Embstr | SDS (Raw) | 字符串长度 > 44字节 或 无法用 embstr 编码时 |
| List | ZipList / ListPack | QuickList | 元素数量 > 512 或 单个元素 > 64字节 |
| Hash | ZipList / ListPack | HashTable | 键值对数量 > 512 或 单个键/值 > 64字节 |
| Set | IntSet | HashTable | 包含非整数元素 或 元素数量 > 512 |
| ZSet | ZipList / ListPack | SkipList + HashTable | 元素数量 > 128 或 单个元素 > 64字节 |

*注：Redis 7.0 开始全面使用 ListPack 替代 ZipList，以解决连锁更新问题。*

## 第2章：存储引擎

### 2.1 单线程 Reactor 模型

Redis 核心命令执行采用单线程模型，其事件循环架构如下：

```
+----------------+      +---------------------+      +------------------+
| Client Connect | ---> | I/O 多路复用 (epoll)| ---> |    事件循环       |
+----------------+      +---------------------+      +------------------+
                                                         |          |
                                              +----------+          +-----------+
                                              |                               |
                                     +----------------+             +-----------------+
                                     | 读事件: 解析命令|             | 写事件: 回写响应 |
                                     +----------------+             +-----------------+
                                              |                               ^
                                              v                               |
                                     +----------------+                       |
                                     |   执行命令      | ----------------------+\
                                     | (单线程串行执行) |
                                     +----------------+
```

**为什么单线程反而高性能？**

1. **避免上下文切换**：无需在多个线程间切换，节省 CPU 调度开销。
2. **无锁竞争**：不存在多线程共享内存的锁竞争，无需加锁/解锁，避免死锁风险。
3. **内存与 CPU 缓存友好**：单线程顺序执行指令，对 CPU Cache 极其友好。
4. **瓶颈在网络与内存**：Redis 性能瓶颈通常是网络带宽或内存带宽，而非 CPU 计算能力。

### 2.2 网络 I/O 多路复用详解

```
[select/poll]                       [epoll]
+-------------------+               +-------------------------+
| 遍历所有文件描述符 |               | 仅返回就绪的文件描述符    |
| O(N) 线性扫描     |               | O(1) 回调通知           |
| 内存拷贝开销大     |               | 基于事件驱动，无轮询     |
+-------------------+               +-------------------------+
```

**epoll 触发模式**：

- **Level-Triggered (LT)**：默认模式，只要缓冲区有数据就持续通知，编程简单但可能重复唤醒。
- **Edge-Triggered (ET)**：仅在状态变化时通知一次，需一次性读完数据，减少系统调用，Redis 默认使用 ET 模式。

**Redis 6.0+ 多线程 I/O 架构**：

Redis 6.0 引入多线程仅用于网络 I/O 的读写和协议解析，**命令执行依然是单线程**。

```
+----------------+   +----------------+   +----------------+
|  网络线程 1     |   |  网络线程 2     |   |  网络线程 N     |
| (读/解析/写)   |   | (读/解析/写)   |   | (读/解析/写)   |
+-------+--------+   +-------+--------+   +-------+--------+
        |                     |                     |
        +---------------------+---------------------+
                              |
                    +-------------------+
                    |  主线程 (单线程)   |
                    | (命令队列串行执行) |
                    +-------------------+
```

### 2.3 RESP 协议

RESP（Redis Serialization Protocol）是 Redis 客户端与服务端的通信协议，支持 5 种数据类型：

1. **Simple Strings**：以 `+` 开头，如 `+OK\r\n`
2. **Errors**：以 `-` 开头，如 `-ERR unknown command\r\n`
3. **Integers**：以 `:` 开头，如 `:100\r\n`
4. **Bulk Strings**：以 `$` 开头，如 `$5\r\nhello\r\n`
5. **Arrays**：以 `*` 开头，如 `*2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n`

**SET 命令的 RESP 编码过程**：

```
客户端发送:  SET mykey hello
RESP 编码:   *3\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$5\r\nhello\r\n

服务端响应:  OK
RESP 编码:   +OK\r\n
```

### 2.4 命令执行流程

```
[客户端发送命令]
       |
       v
[网络接收 (多线程)] --> [协议解析 (RESP解码)]
       |
       v
[命令路由 (查找命令表)] --> [执行命令 (单线程)]
       |
       v
[结果序列化 (RESP编码)] --> [网络发送 (多线程)] --> [客户端接收]
```

## 第3章：内存与数据结构

### 3.1 SDS (Simple Dynamic String)

Redis 未使用 C 语言原生字符串，而是自定义了 SDS：

```
+----------+----------+------------------+
|  len     |  free    |  buf[] (字符数组) |
| (4 bytes)| (4 bytes)|                  |
+----------+----------+------------------+
```

**相比 C 字符串的优势**：

1. **O(1) 获取长度**：`len` 字段直接记录，无需遍历。
2. **二进制安全**：`buf` 可存任意二进制数据，不以 `\0` 作为结束判断。
3. **防缓冲区溢出**：修改时自动检查 `free` 空间，不足则扩容。
4. **空间预分配**：减少连续内存重分配次数。
5. **惰性释放**：缩短字符串时不立即释放空间，而是更新 `free` 字段供后续使用。

**空间预分配策略**：

- 修改后 `len < 1MB`：预分配与 `len` 相同大小的 `free` 空间。
- 修改后 `len >= 1MB`：固定预分配 `1MB` 的 `free` 空间。

### 3.2 ZipList / ListPack

**ZipList 内存布局**：

```
+---------+--------+-----------------+-----------------+---------+
| zlbytes | zltail | zllen           | entry1          | ...     |
| (4B)    | (4B)   | (2B)            | (prevlen+enc+val)|         |
+---------+--------+-----------------+-----------------+---------+
```

**连锁更新问题**：当插入一个较大元素导致后续节点的 `prevlen` 编码长度变化时，会触发级联的内存重分配，最坏情况复杂度为 O(N^2)。

```
[插入前]  [A(3B)][B(3B)][C(3B)][D(3B)]
           prevlen prevlen prevlen prevlen

[插入大元素X后]
[A(3B)][X(10B)][B(4B*)][C(4B*)][D(4B*)]
         prevlen  prevlen* prevlen* prevlen*
                      ↑ 连锁更新：B/C/D 的 prevlen 编码都需从2B变为4B
```

**ListPack 改进**：

```
+---------+--------+-----------------+-----------------+---------+
| bytes   | size   | element1        | element2        | ...     |
| (4B)    | (2B)   | (len+enc+val)   | (len+enc+val)   |         |
+---------+--------+-----------------+-----------------+---------+
```

ListPack 移除了 `prevlen` 字段，每个节点仅记录自身长度，彻底消除了连锁更新问题。

### 3.3 QuickList

```
+-------------+      +-------------+      +-------------+
|  ListPack 1 | <--> |  ListPack 2 | <--> |  ListPack 3 |
| [A][B][C][D]|      | [E][F][G][H]|      | [I][J][K]   |
+-------------+      +-------------+      +-------------+
       ^                    ^                    ^
       +--------------------+--------------------+
                    双向链表指针
```

QuickList 是双向链表与 ListPack 的结合体。每个链表节点是一个 ListPack，兼顾了：

- **插入性能**：链表结构支持 O(1) 的头尾插入。
- **内存紧凑**：ListPack 减少了链表节点的指针开销。

`list-max-ziplist-size` 参数控制每个 ListPack 节点的最大大小（默认 -2 表示 8KB），超过则分裂为新节点。

### 3.4 SkipList (跳表)

```
Level 3:  [HEAD] ----------------------------> [TAIL]
Level 2:  [HEAD] --------> [C] --------------> [TAIL]
Level 1:  [HEAD] --> [A] --> [C] --> [D] ----> [TAIL]
Level 0:  [HEAD] --> [A] --> [B] --> [C] --> [D] --> [E] --> [TAIL]
```

**ZSet 选择跳表而非平衡树/红黑树的原因**：

1. **实现简单**：跳表代码量远小于红黑树，易于维护和调试。
2. **范围查询友好**：跳表底层是有序链表，`ZRANGE` 等操作只需找到起点后顺序遍历，而红黑树需要中序遍历，效率较低。
3. **CPU 缓存友好**：跳表节点内存分配相对连续，对缓存命中率更优。

### 3.5 HashTable

**Redis HashTable 底层结构与进阶机制详解**

Redis 的 HashTable（底层实现为字典 `dict`）不仅用于存储 Hash 类型的键值对，整个 Redis 数据库的全局 Key-Value 空间也由它管理。其最核心的设计在于**双哈希表结构**、平滑过渡的**渐进式 Rehash**机制，以及抵御攻击的**SipHash**算法。

**一、 底层核心结构剖析**

Redis 的字典主要由三层嵌套结构组成：

| 结构名称 | 核心组件 | 作用说明 |
| :--- | :--- | :--- |
| **`dict` (字典)** | `ht[2]` (两张哈希表), `rehashidx` | 封装完整的字典。包含两个独立的哈希表（用于扩容交替使用）和记录 Rehash 进度的索引。 |
| **`dictht` (哈希表)** | `table` (节点数组), `size`, `used` | 实际的哈希表，维护一个指针数组。`used` 记录当前哈希表中已存在的节点总数。 |
| **`dictEntry` (节点)** | `key`, `v` (值), `next` (指针) | 存储具体的键和值。`next` 指针用于通过**链地址法**将冲突的节点连在一起。 |

**哈希冲突解决：**
当多个 Key 映射到同一个数组索引时，Redis 通过 `dictEntry` 的 `next` 指针使用**头插法**形成单向链表，新节点总是插入链表头部以保证极速响应。

**二、 内存结构图解 (Rehash 进行中)**

当字典正在进行扩容操作时，新旧两张表会同时存在。内存结构如下所示：

> [ dict 结构 ]
>   ├── ht[0] (旧表, 容量为4, 正在被逐渐清空)
>   │    ├── table[0] ---> NULL (已完成迁移)
>   │    ├── table[1] ---> NULL (已完成迁移)
>   │    ├── table[2] ---> [ key3 : v3 | next ] ---> [ key7 : v7 | next ] ---> NULL
>   │    └── table[3] ---> [ key4 : v4 | next ] ---> NULL
>   │
>   ├── ht[1] (新表, 扩容至8, 正在接收新数据)
>   │    ├── table[0] ---> [ key1 : v1 | next ] ---> NULL (从旧表迁移而来)
>   │    ├── table[1] ---> NULL
>   │    ├── table[2] ---> [ key8 : v8 | next ] ---> NULL (Rehash期间直接写入的新数据)
>   │    ├── table[3] ---> [ key5 : v5 | next ] ---> NULL (从旧表迁移而来)
>   │    └── table[4] ~ table[7] ... (等待分配)
>   │
>   └── rehashidx = 2 (当前进度：下次顺带操作将迁移 ht[0] 的 table[2])

**三、 扩缩容条件与渐进式 Rehash**

为了防止海量数据一次性迁移导致 Redis 单线程长时间阻塞，Redis 采用了分摊到每次操作的渐进式策略。

**扩缩容触发条件：**
*   **触发扩容**：无持久化操作（RDB/AOF）时，负载因子（当前节点数 / 数组长度）≥ 1；若正在持久化，为降低写时复制 (COW) 压力，阈值放宽至 ≥ 5。
*   **触发缩容**：负载因子 < 0.1 时自动执行缩容。

**渐进式 Rehash 演进过程：**

| 步骤 | 触发动作 | `rehashidx` | 底层状态变化 |
| :--- | :--- | :--- | :--- |
| **1. 准备** | 负载因子达标触发扩缩容 | `0` | 为 `ht[1]` 分配空间。`rehashidx` 从 `-1` 改为 `0`，标志 Rehash 开启。 |
| **2. 分摊迁移** | 客户端发起 `SET/GET/DEL` | `+1` (按次递增) | 每次请求顺带将 `ht[0]` 在 `rehashidx` 索引处的整条链表迁入 `ht[1]`。**新增数据直接落入 `ht[1]`**，查询跨越两表。 |
| **3. 定时辅助** | 长时间无客户端操作触发 `serverCron` | `+N` (按批递增) | 后台微秒级定时任务主动按步长迁移 `ht[0]` 节点，防止冷数据长期滞留。 |
| **4. 收尾** | 旧表最后一个索引迁移完毕 | `-1` | 清空并释放 `ht[0]`。将原 `ht[1]` 改名为 `ht[0]`，重置 `ht[1]` 为空，结束 Rehash。 |

---

**四、 安全性保障：SipHash 算法**

自 Redis 4.0 起，为了彻底根除 **哈希碰撞攻击 (Hash DoS)**，底层哈希算法从 MurmurHash2 切换为了 SipHash。

*   **带随机密钥（Keyed）**：Redis 实例启动时会在内部生成 128 位随机密钥作为算法种子。
*   **短文本优化**：专为短字节流（Redis Key）量身定制，在保障安全的同时计算速度逼近非加密哈希算法。
*   **防御逻辑对比**：

| 防御维度 | 传统哈希（如 MurmurHash） | SipHash（Redis 4.0+） |
| :--- | :--- | :--- |
| **碰撞预测** | 算法静态，攻击者可在本地低成本构造百万个哈希值相同的恶意 Key。 | 依赖 Redis 内存中的随机密钥，攻击者无法在本地预测和计算碰撞结果。 |
| **攻击后果** | 恶意 Key 落入同槽位形成超长链表，字典退化为 O(N) 遍历，CPU 飙升。 | 恶意 Key 被随机密钥彻底打乱，均匀分布于各槽位，字典维持 O(1) 性能。 |


**渐进式 rehash**：为避免一次性迁移大量数据导致阻塞，Redis 在 rehash 期间同时维护两张表。每次执行增删改查命令时，顺带将 `ht` 的一个桶迁移到 `ht`，将 O(N) 的迁移分散到 O(1) 的多次操作中。

`dictSize` 记录哈希表总容量，`dictUsed` 记录已使用的桶数量，当 `dictUsed / dictSize` 超过阈值时触发扩容。

### 3.6 内存淘汰策略

| 策略 | 淘汰范围 | 淘汰算法 | 适用场景 |
| :--- | :--- | :--- | :--- |
| noeviction | 不淘汰 | - | 纯缓存且不允许丢失数据 |
| allkeys-lru | 所有键 | LRU | 通用缓存，优先保留最近访问的 |
| allkeys-random | 所有键 | 随机 | 访问模式均匀，无明确热点 |
| volatile-lru | 设置了过期时间的键 | LRU | 部分数据需持久化，部分作缓存 |
| volatile-random | 设置了过期时间的键 | 随机 | 过期键中无明确访问规律 |
| volatile-ttl | 设置了过期时间的键 | TTL最短 | 希望尽快清理即将过期的数据 |

### 3.7 过期策略

Redis 采用**惰性过期 + 定期过期**的组合策略：

```
[客户端访问 Key]
       |
       v
[检查是否过期?] --是--> [删除Key并返回nil]
       |
      否
       |
       v
[返回正常值]

[定时任务 (100ms/次)]
       |
       v
[随机抽取20个设置了过期时间的Key]
       |
       v
[删除已过期的Key]
       |
       v
[若过期比例>25%?] --是--> [重新抽取]
       |
      否
       |
       v
[结束本轮检查]
```

- **惰性过期**：访问时检查，避免无效 Key 占用内存，但可能长期不访问的过期 Key 不被清理。
- **定期过期**：每秒 10 次随机抽样清理，平衡 CPU 消耗与内存回收效率。

### 3.8 内存碎片与 defrag

**内存碎片产生原因**：频繁的增删改导致内存分配器（如 jemalloc）产生外部碎片，实际占用内存 > 数据实际大小。

**Active Defrag 原理**：Redis 4.0+ 引入，利用后台线程在空闲周期对内存进行整理，将分散的数据块迁移到连续内存区域，释放碎片空间。通过 `activedefrag yes` 开启。

**maxmemory 配置建议**：

- 建议设置为物理内存的 70%-80%，为操作系统和 Redis 自身 fork（如 RDB/AOF 重写）预留空间。
- 配合 `maxmemory-policy` 使用，避免 OOM。

## 第4章：索引与查询

### 4.1 SCAN 游标迭代

**为什么不用 KEYS \***：`KEYS *` 会遍历所有键，时间复杂度 O(N)，阻塞主线程，生产环境严禁使用。

**SCAN 游标机制**：

```
SCAN 0 MATCH user:* COUNT 10
       |
       v
返回: cursor=15, keys=[user:1, user:2, ...]
       |
       v
SCAN 15 MATCH user:* COUNT 10
       |
       v
返回: cursor=0, keys=[user:99, ...]  (cursor=0 表示遍历结束)
```

**不确定性说明**：SCAN 基于哈希表的桶索引游标，遍历过程中若发生 rehash 或数据增删，可能出现**重复返回**或**遗漏**，客户端需自行去重。

### 4.2 慢查询日志

- `slowlog-log-slower-than`：记录执行时间超过此阈值（微秒）的命令，默认 10000（10ms）。
- `slowlog-max-len`：慢查询日志最大条数，默认 128，超出后 FIFO 淘汰。

**定位慢查询**：通过 `SLOWLOG GET 10` 查看最近 10 条慢查询，分析命令类型、执行时间及客户端 IP，结合业务逻辑优化。

### 4.3 事务 MULTI/EXEC/WATCH

```
[MULTI] --> [返回OK，进入事务模式]
    |
    v
[SET k1 v1] --> [返回QUEUED]
[SET k2 v2] --> [返回QUEUED]
    |
    v
[EXEC] --> [依次执行所有命令，返回结果数组]
```

**错误处理**：

- **编译时错误**（如命令不存在）：整个事务被拒绝，EXEC 返回错误。
- **运行时错误**（如类型不匹配）：仅该命令失败，其余命令正常执行，**不回滚**。

**WATCH 乐观锁**：在 EXEC 前 WATCH 某个 Key，若该 Key 在事务执行前被其他客户端修改，EXEC 返回 nil，事务失败，客户端可重试。

### 4.4 Lua 脚本

```
[客户端发送 EVAL 脚本]
       |
       v
[服务端加载并编译 Lua]
       |
       v
[原子执行脚本 (阻塞其他客户端)]
       |
       v
[返回结果]
```

- `redis.call`：执行失败时抛出错误，终止脚本。
- `redis.pcall`：执行失败时捕获错误，返回错误对象，脚本继续执行。

**脚本缓存**：使用 `SCRIPT LOAD` 预加载脚本获取 SHA1，后续用 `EVALSHA sha1` 执行，避免重复传输和编译脚本。

### 4.5 Pipeline（管道）

**Pipeline 原理**：客户端将多条命令打包，一次性通过网络发送给服务端，服务端在内存中排队后依次执行，最后将多个结果打包一次性返回。

**无 Pipeline vs 有 Pipeline 对比**：

```
无 Pipeline (3次RTT):
Client --> [SET k1 v1] --> Server --> [OK]      (RTT 1)
Client --> [GET k1]  --> Server --> [v1]        (RTT 2)
Client --> [SET k2]  --> Server --> [OK]        (RTT 3)
总计: 3 次网络往返

有 Pipeline (1次RTT):
Client --> [SET k1 v1, GET k1, SET k2] --> Server  (1次RTT)
                  <-- [OK, v1, OK] <--            (1次RTT)
总计: 1 次网络往返
```

**Pipeline 的局限性**：

1. **非原子性**：Pipeline 中的命令不具备原子性，中间可能被其他客户端的命令穿插。
2. **内存消耗**：大批量命令打包会占用客户端和服务端内存。
3. **错误处理**：部分命令失败不影响其他命令执行，需客户端自行处理。

### 4.6 SORT 命令

`SORT` 命令可对 List、Set、ZSet 进行排序，支持 `BY`、`GET`、`LIMIT` 等选项。但 `SORT` 时间复杂度为 O(N+log(N))，在大集合上性能较差，生产环境应谨慎使用。

## 第5章：并发与一致性

### 5.1 单线程的优劣分析

**优势：**

1. **无锁竞争**：不需要处理复杂的锁机制（如互斥锁、读写锁），避免了死锁问题。
2. **无上下文切换**：没有多线程切换带来的 CPU 开销，指令执行连贯。
3. **命令原子性**：单线程顺序执行命令，天然保证了单个命令的原子性。

**劣势：**

1. **单核性能瓶颈**：无法充分利用多核 CPU 的计算能力。
2. **阻塞风险**：一旦执行耗时命令（如 `KEYS *`、大 Key 删除），整个服务将被阻塞。

**为什么 Redis 选择单线程？**

Redis 的核心瓶颈在于**网络 I/O** 和**内存操作**，而非 CPU 计算。单线程配合 I/O 多路复用（epoll/kqueue）足以跑满千兆/万兆网卡。引入多线程反而会增加锁竞争和上下文切换的开销，得不偿失。（注：Redis 6.0+ 引入多线程仅用于网络 I/O 读写，命令执行依然是单线程。）

### 5.2 并发写入策略

| 方式 | 原子性 | 性能 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **Pipeline** | 非原子 | 极高 | 批量读取、非强一致性的批量写入（如日志收集） |
| **Lua 脚本** | 完全原子 | 中等 | 复杂业务逻辑（如秒杀扣减、限流计数器） |
| **MULTI/EXEC** | 语法原子，逻辑非原子 | 中等 | 简单的批量操作，不依赖前一个命令的结果 |

### 5.3 分布式锁

**基础实现：**

`SET key value NX EX seconds`。NX 保证互斥，EX 保证锁自动释放防止死锁。Value 必须是唯一标识（如 UUID），释放锁时需校验 Value 防止误删他人锁。

**RedLock 算法：**

解决单点故障导致锁失效的问题。

1. 获取当前时间戳。
2. 依次向 N 个独立 Redis 节点请求锁（超时时间要短）。
3. 如果在超时时间内，成功在 **N/2 + 1** 个节点获取锁，则获取成功。
4. 锁的有效时间 = 原始有效时间 - 获取锁耗时。
5. 若获取失败，立即向所有节点释放锁。

```
[Client]
   |
   +---> [Redis Master 1] (OK)
   +---> [Redis Master 2] (OK)
   +---> [Redis Master 3] (Timeout)
   +---> [Redis Master 4] (OK)
   +---> [Redis Master 5] (Failed)

Result: 3/5 成功 (> N/2)，获取锁成功
```

**分布式锁的坑：**

1. **时钟回拨**：导致锁提前过期。
2. **节点宕机**：主从切换时，主节点未同步的锁丢失，导致多客户端同时持有锁。
3. **锁过期但业务未完成**：需引入看门狗（Watchdog）机制自动续期。

### 5.4 PUB/SUB 消息订阅

```
[Publisher] --PUBLISH--> [Redis Server] --推送--> [Subscriber 1]
                                            --推送--> [Subscriber 2]
```

**特性：**

1. **不持久化**：消息发完即丢，离线客户端收不到历史消息。
2. **无 ACK 机制**：发布者不关心消费者是否收到。
3. **背压问题**：消费者处理慢会导致服务端内存暴涨。

**适用场景：** 实时聊天室、弹幕、实时通知、配置变更广播。

### 5.5 Stream 消费者组

Stream 是 Redis 5.0 引入的，结合了 Kafka 的消费者组概念。

**数据结构：** Radix Tree（压缩前缀树）存储消息，每个消费者组维护一个 `last_delivered_id`。

**ACK 机制流程：**

```
[Producer] --XADD--> [Stream]
                        |
        +---------------+---------------+
        |                               |
[Consumer Group A]              [Consumer Group B]
   |          |                    |
[XREADGROUP] [XREADGROUP]      [XREADGROUP]
   |          |                    |
(处理中...)  (处理中...)         (处理完成)
   |          |                    |
   |          |               [XACK msg_id]
   |          |                    |
[Pending List]                 (消息移除)
```

**XREADGROUP vs XREAD：**

- `XREAD`：普通读取，类似 List 的 BRPOP，不记录消费进度。
- `XREADGROUP`：绑定消费者组，自动更新组进度，支持 Pending 列表查询和 ACK。

**重试机制：** 通过 `XPENDING` 查看未 ACK 消息，结合 `XCLAIM` 将超时消息转移给其他消费者处理。

### 5.6 一致性模型

- **强一致**：写操作成功，所有节点立即可读（Redis 默认不支持）。
- **最终一致**：写操作成功，经过一段时间后所有节点数据一致。

**Redis 的弱一致性：**

主从异步复制。Master 执行完写命令立即返回客户端，后台异步同步给 Slave。若 Master 在同步前宕机，数据丢失。

**如何保证强一致性（相对）：**

使用 `WAIT numslaves timeout` 命令。阻塞当前客户端，直到指定数量的 Slave 确认收到写入，或超时。这实现了**同步复制**，但牺牲了高可用性和性能。

## 第6章：分布式与高可用

### 6.1 主从复制

**全量复制流程：**

```
[Slave] --PSYNC ? -1--> [Master]
[Slave] <--- +FULLRESYNC <uuid> <offset> ---
[Slave] <--- RDB Stream --- (Master BGSAVE)
[Slave] (Load RDB to Memory)
[Slave] <--- Replication Buffer (增量命令) ---
```

**增量复制流程：**

```
[Slave] --PSYNC <uuid> <offset>--> [Master]
[Master] (Check offset in backlog)
[Master] -- +CONTINUE --> [Slave]
[Master] -- Replication Backlog (增量) --> [Slave]
```

**断线重连：** Slave 定期 ping Master，断开后自动重连，尝试增量复制；若 offset 过期则回退到全量复制。

**级联复制：** Slave 可以有自己的 Slave，减轻 Master 压力，但会增加数据延迟。

### 6.2 Sentinel（哨兵）

**架构：**

```
       [Sentinel 1]   [Sentinel 2]   [Sentinel 3]
            |              |              |
            +--------------+--------------+
                           |
              [Master] --- [Slave 1]
                 |
              [Slave 2]
```

**故障检测流程：**

1. **SDOWN（主观下线）**：单个 Sentinel 认为 Master 不可用。
2. **ODOWN（客观下线）**：Quorum 个 Sentinel 同意 SDOWN。
3. **故障转移**：选举 Leader Sentinel，选择最佳 Slave 晋升，通知其他 Slave 复制新 Master，通知客户端新地址。

**投票机制：** 基于 Raft 协议思想，Sentinel 之间通过 `SENTINEL is-master-down-by-addr` 投票，获得 **N/2 + 1** 票的 Sentinel 成为 Leader 执行故障转移。

### 6.3 Redis Cluster

**哈希槽：** 16384 个槽位，`CRC16(key) % 16384`。每个 Master 负责一部分槽位。

**客户端路由过程：**

```
Client -> CRC16("user:1001") % 16384 = 5798
Client -> 发送 GET user:1001 到 Node A
Node A (负责 0-5000) -> 返回 MOVED 5798 192.168.1.3:6379
Client -> 更新本地槽位表
Client -> 发送 GET user:1001 到 Node B (192.168.1.3)
Node B -> 返回 Value
```

**Gossip 协议：** 节点间通过 PING/PONG/MEET/FAIL 消息交换状态，最终一致性。

**数据迁移 (ASK)：**

扩容时，槽位从 A 迁到 B。

1. 客户端访问 A，A 发现槽位正在迁移 -> 返回 `ASK target_node`。
2. 客户端发送 `ASKING` 到 B。
3. 客户端发送命令到 B，B 执行。

（ASK 是临时重定向，不更新客户端槽位表；MOVED 是永久重定向，更新槽位表。）

**Cluster 扩容缩容流程：**

```
[扩容前]
[Master A: Slot 0-5460]  [Master B: Slot 5461-10922]  [Master C: Slot 10923-16383]

[开始迁移 Slot 5461-10922 从 B 到 新节点 D]
[Master B] --迁移部分槽位--> [Master D]
[客户端访问被迁移的槽位] --> ASK重定向 --> [Master D]

[扩容后]
[Master A: Slot 0-5460]  [Master B: Slot 10923-16383]  [Master C: Slot ?-?]  [Master D: Slot 5461-10922]
```

### 6.4 跨机房多活

1. **全局负载均衡 (GLB)**：DNS 或 GSLB 将用户路由到最近机房。
2. **异步复制跨机房**：使用 Redis-Shake 或原生跨机房复制，存在延迟。
3. **冲突解决**：
    - **Last Write Wins (LWW)**：基于时间戳，简单但可能丢数据。
    - **CRDTs**：无冲突复制数据类型，Redis 官方正在探索，但尚未完全成熟。
    - **业务层解决**：按用户 ID 分片，单写单读，避免跨机房写冲突。

## 第7章：持久化与恢复

### 7.1 COW (Copy-On-Write) 详解

**Fork 后的内存共享机制：**

```
Fork前:
[主进程] --指向--> [物理内存页]

Fork后(共享):
[主进程] --指向(只读)--> [物理内存页] <--指向(只读)-- [子进程]
(物理内存只有一份，零拷贝)

主进程修改时(COW触发):
[主进程] --写入--> [新复制的内存页]
[子进程] --读取--> [原始内存页] (互不干扰，保证快照一致性)
```

**原理：** `fork()` 只复制页表，不复制物理内存。只有当主进程修改某页时，OS 才复制该页。这确保了子进程拿到的是 fork 瞬间的一致性快照，同时避免了海量数据的完整拷贝，极大降低了内存与 CPU 开销。

**局限性：** 如果主进程写入极其频繁，大量页面被复制，会导致内存翻倍甚至 OOM。

### 7.2 RDB (远程数据库)

**文件格式：**

```
+--------+--------+--------+--------+----------+
| 魔数   | 版本   | 数据库0  | 数据库1  | EOF/校验 |
| REDIS0 | 0009   | Key-Val | Key-Val | CRC64    |
|  11    |        | 对...   | 对...   |          |
+--------+--------+--------+--------+----------+
```

**触发条件：** `save 900 1` (900秒内至少1次写)、`save 300 10` (300秒内至少10次写)、`FLUSHALL`、`SHUTDOWN SAVE`、手动 `BGSAVE`。

**bgsave 执行流程：**

```
[客户端触发 BGSAVE]
       |
       v
[主进程 fork 子进程]
       |
       v
[子进程: 将内存数据写入 RDB 临时文件]
       |
       v
[子进程: 替换旧 RDB 文件]
       |
       v
[通知主进程 BGSAVE 完成]
```

**优缺点：**

- **优**：文件紧凑，恢复速度快，适合备份/灾难恢复。
- **缺**：两次快照间的数据可能丢失，Fork 大内存时有卡顿风险。

### 7.3 AOF (追加写文件)

**文件格式 (RESP 命令追加)：**

```
*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$3\r\nval\r\n
*3\r\n$3\r\nSET\r\n$4\r\nkey2\r\n$5\r\nvalue\r\n
*3\r\n$3\r\nINCR\r\n$3\r\ncnt\r\n
```

**Fsync 策略对比：**

| 策略 | 性能 | 数据安全 | 说明 |
| :--- | :--- | :--- | :--- |
| `always` | 低 | 高 | 每次写操作立即 fsync，磁盘 I/O 瓶颈 |
| `everysec` | 中 | 中高 | 每秒 fsync 一次，最多丢 1 秒数据（推荐） |
| `no` | 高 | 低 | 依赖 OS 刷盘，不可控 |

**AOF 重写（Rewrite）机制：**

后台 Fork 子进程，根据当前内存数据生成新 AOF 文件，期间主进程命令写入 Rewrite Buffer。完成后替换旧文件。解决文件膨胀问题。

**AOF 重写流程：**

```
[客户端触发 BGREWRITEAOF]
       |
       v
[主进程 fork 子进程]
       |                    \
       v                     \
[子进程: 从内存中读取数据，生成精简 AOF 文件]  [主进程: 新写命令同时写入旧AOF+Rewrite Buffer]
       |
       v
[子进程完成: 合并 Rewrite Buffer]
       |
       v
[替换旧 AOF 文件为新文件]
```

### 7.4 混合持久化 (Redis 4.0+)

**文件结构：**

```
+----------------------------------+----------------------------------+
| [ RDB 二进制快照部分(全量数据) ]   | [ AOF 增量命令部分(增量) ]    |
+----------------------------------+----------------------------------+
(极速加载)                          (保证最后几秒数据不丢)
```

**优势：**

1. **极速恢复**：前半部分是 RDB，加载速度远快于纯 AOF。
2. **数据安全**：后半部分是 AOF，保证重启前最后几秒的数据不丢。

### 7.5 故障恢复流程

1. **纯 RDB**：直接加载文件到内存。速度最快，但可能丢数据。
2. **纯 AOF**：加载文件，重放命令。速度最慢，数据最全。
3. **混合持久化**：加载 RDB 部分 -> 追加 AOF 增量。速度与安全的最佳平衡。

```
[Redis 启动]
       |
       v
[检查配置: 开启RDB? 开启AOF?]
       |
       +-- 仅RDB --> [加载 dump.rdb] --> [启动完成]
       |
       +-- 仅AOF --> [加载 appendonly.aof] --> [重放命令] --> [启动完成]
       |
       +-- 混合持久化 --> [加载RDB部分(全量)] --> [追加AOF增量部分] --> [启动完成]
```

### 7.6 文件安全校验

- `redis-check-rdb dump.rdb`：检查 RDB 完整性。
- `redis-check-aof appendonly.aof`：检查 AOF，修复截断的尾部命令。
- 若文件尾部损坏，Redis 启动时会报错，需手动修复或丢弃损坏部分。

## 第8章：性能与场景

### 8.1 jemalloc 内存分配器详解

#### 8.1.1 glibc malloc (ptmalloc) 的痛点

glibc 的 malloc 实现（ptmalloc）在高并发场景下面临两大核心问题：

**痛点一：多线程锁竞争**

ptmalloc 使用 Arena 机制管理内存。默认情况下，每个线程会绑定到一个 Arena，但当线程数远多于 Arena 数时，大量线程会争抢少量 Arena，导致严重的锁竞争。

```
[Thread 1] --锁定--> [Arena 1] <--锁定-- [Thread 2]
                                          (等待锁...)
[Thread 3] --锁定--> [Arena 1] <--锁定-- [Thread 4]
                                          (等待锁...)
                    ↑ 锁竞争瓶颈
```

**痛点二：内存碎片**

ptmalloc 在频繁分配和释放不同大小的对象时，容易产生外部碎片——空闲内存块分散在已用内存块之间，虽然总空闲内存充足，但无法分配大块连续内存。

```
[已用][空闲16B][已用][空闲8B][已用][空闲32B][已用][空闲4B][已用]
 ↑ 总空闲 = 60B，但无法分配 50B 的连续内存！
```

#### 8.1.2 jemalloc 的架构与优势

jemalloc 通过分层架构彻底解决了上述问题：

```
[ Thread 1 ]  [ Thread 2 ]  [ Thread 3 ]
     |             |             |
[tcache 1 ] [tcache 2 ] [tcache 3 ]  <- 线程私有，无锁访问
     |             |             |
(Cache Miss) (Cache Miss) (Cache Miss)
     v             v             v
[ Arena 1 ]  [ Arena 2 ]  [ Arena 3 ]  <- 线程绑定，少量锁
     |             |             |
[ Chunk ] --> [ Chunk ] --> [ Chunk ]  <- 向OS申请的大块内存(通常几MB)
     |             |             |
[ Run ]    --> [ Run ]    --> [ Run ]   <- 连续内存页
     |             |             |
[Region] --> [Region] --> [Region]    <- 固定大小内存块 --> 分配给业务
```

**各层详解：**

1. **tcache（线程本地缓存）**：每个线程拥有独立的 tcache，小对象（<= 128字节）的分配和释放完全在 tcache 内完成，**零锁操作**。这是 jemalloc 高性能的核心。

2. **Arena（区域）**：当 tcache 未命中时，线程向绑定的 Arena 请求内存。每个 Arena 内部有独立的锁，多个 Arena 分散了锁竞争。默认 Arena 数量 = 4 * CPU核数。

3. **Chunk（块）**：Arena 向操作系统（通过 mmap）申请的大块内存（通常 2MB~4MB）。Chunk 是 Arena 和 OS 之间的桥梁。

4. **Run（运行区）**：Chunk 内部被划分为固定大小的连续内存页（Page），每个 Page 通常 4KB~64KB。

5. **Region（区域）**：Run 内部被进一步划分为固定大小的 Region，每个 Region 大小对应一个 Size Class。这是实际分配给业务的最小内存单元。

**Size Class 机制：**

jemalloc 将所有可能的内存请求归类到预定义的 Size Class 中（如 8B、16B、24B、32B、48B、64B、...、32768B）。每个 Size Class 有独立的 tcache 和 Run，避免了内部碎片。

```
Size Class 划分示意:
  8B   | [Region 8B] [Region 8B] [Region 8B] ...  (Run A)
  16B  | [Region 16B][Region 16B][Region 16B]...  (Run B)
  32B  | [Region 32B][Region 32B]...               (Run C)
  64B  | [Region 64B][Region 64B]...               (Run D)
  ...
  大对象(>128B) --> 直接走 mmap 分配，不走 Size Class
```

**Dirty Page 回收（Decay）：**

jemalloc 会定期将 Run 中已释放的空闲页标记为"脏页"，并在后台线程中将脏页归还给操作系统（通过 madvise/MADV_FREE），从而减少 RSS 占用。这解决了 ptmalloc 长期运行后 RSS 居高不下的问题。

#### 8.1.3 glibc malloc vs jemalloc 详细对比

| 对比维度 | glibc malloc (ptmalloc) | jemalloc |
| :--- | :--- | :--- |
| **多线程锁竞争** | 少 Arena，多线程争抢导致严重锁竞争 | tcache 无锁 + 多 Arena 分散锁竞争 |
| **内存碎片** | 外部碎片严重，长期运行 RSS 居高不下 | Size Class 精细划分 + Decay 归还脏页 |
| **CPU缓存友好** | 分配地址较散，缓存命中率一般 | 地址对齐 + 局部性优化，缓存命中率更高 |
| **小对象分配** | 每次可能需加锁，竞争激烈 | tcache 命中零锁，性能极致 |
| **大对象分配** | 直接 mmap | 直接 mmap（不走 Size Class，效率相当） |
| **内存利用率** | 碎片率高，实际 RSS 远大于数据量 | 碎片率低，RSS 接近实际数据量 |
| **实测性能** | 基准 | 高并发小对象场景吞吐量高 1.5x~2x |

**Redis 为什么默认使用 jemalloc？**

Redis 是典型的高并发、小对象频繁分配/释放的场景（每个 Key 的 SDS、每个 List 节点等）。jemalloc 的 tcache 机制让每个线程的小对象分配完全无锁，极大提升了吞吐量；同时其精细的碎片管理机制让长期运行的 Redis 实例内存占用更稳定。

### 8.2 性能基准

- **典型 QPS**：单实例 8w~10w+ QPS（Pipeline 可达 20w+）。
- **影响因素**：
    - **Key 大小**：大 Key 操作阻塞主线程。
    - **命令复杂度**：`O(N)` 或 `O(logN)` 命令慎用。
    - **网络延迟**：RTT 是最大瓶颈，务必使用 Pipeline。
    - **客户端**：连接池配置、序列化开销。

### 8.3 适用场景

1. **缓存**：减轻 DB 压力，加速读取。
2. **计数器/限流**：`INCR`、Lua 脚本实现滑动窗口。
3. **消息队列**：List（简单）、Stream（可靠）。
4. **分布式锁**：`SETNX`、RedLock。
5. **排行榜**：ZSet（`ZREVRANGE`）。
6. **会话存储**：集中式 Session，支持多服务共享。
7. **实时分析**：HyperLogLog（UV）、Bitmaps（签到）。

### 8.4 不适用场景

1. **大规模数据存储**：内存昂贵，TB 级数据请选 HBase/ES。
2. **复杂查询**：不支持 SQL、Join，需应用层处理。
3. **强一致性**：金融核心账务请选关系型数据库。
4. **大 Key 场景**：如 10MB 的 String，会导致网络阻塞和主线程卡顿。

### 8.5 生产环境调优建议

1. **连接池**：合理设置 MaxActive/MaxIdle，避免连接泄露。
2. **大 Key 治理**：拆分 Hash/List，异步删除（`UNLINK`）。
3. **热 Key**：本地缓存（Caffeine）+ 多副本 Redis。
4. **网络**：`tcp-backlog 511`，`tcp-keepalive 300`。
5. **OS 参数**：`vm.overcommit_memory=1`（允许 Fork），`net.core.somaxconn=2048`。
6. **Maxmemory**：必须设置！策略推荐 `volatile-lru` 或 `allkeys-lru`。
7. **持久化**：主库关闭持久化，从库开 AOF；或主库开混合持久化。

### 8.6 常见运维命令

- `INFO`：`memory`（内存）、`replication`（主从）、`stats`（统计）。
- `CONFIG GET/SET`：动态修改配置（如 `maxmemory`）。
- `CLIENT LIST/KILL`：排查慢客户端，强制断开连接。
- `SLOWLOG GET 10`：查看慢查询日志。
- `MEMORY USAGE key`：查看 Key 内存占用。
- `MEMORY DOCTOR`：内存健康诊断。

## 第9章：常见面试问题

### 1. Redis 为什么这么快？

1. **纯内存操作**：所有数据在内存，纳秒级访问。
2. **单线程**：避免上下文切换和锁竞争，逻辑简单高效。
3. **I/O 多路复用**：epoll 模型，单线程处理高并发连接。
4. **高效数据结构**：SDS、ZipList、QuickList、SkipList 等针对场景优化。
5. **通信协议**：RESP 协议解析快，二进制兼容格式开销小。
6. **jemalloc 内存分配器**：减少碎片和锁竞争，提升分配效率。

### 2. Redis 的线程模型是怎样的？

- **Redis 5.0 及之前**：纯单线程模型（网络 I/O + 命令执行都在主线程）。
- **Redis 6.0+**：引入多线程 I/O，网络数据的读取/解析和响应写入由多个 I/O 线程并行处理，但**命令执行仍然是单线程**。这样既压榨了网络带宽，又保留了单线程无锁执行的安全与简单。

### 3. RDB 和 AOF 的区别？如何选择？

| 维度 | RDB | AOF |
| :--- | :--- | :--- |
| 原理 | 快照（fork子进程写文件） | 命令追加日志 |
| 文件大小 | 小（二进制压缩） | 大（文本命令） |
| 恢复速度 | 快 | 慢（需重放命令） |
| 数据安全性 | 可能丢最后一次快照后的数据 | 可配置（最多丢1秒） |
| CPU开销 | fork时高 | 持续写入开销 |

**建议**：生产环境开启混合持久化（Redis 4.0+），兼顾恢复速度与数据安全。

### 4. Sentinel 和 Cluster 的区别？

- **Sentinel**：高可用方案，单主多从，故障自动转移，数据量受单机限制，不支持自动分片。
- **Cluster**：分布式方案，多主多从，数据自动分片（16384槽），支持水平扩容，无中心架构。

### 5. 缓存穿透、击穿、雪崩及解决方案？

- **穿透**（查不存在的数据，恶意攻击）：布隆过滤器预判、缓存空值（设置短过期时间）。
- **击穿**（热点 Key 过期瞬间大量请求打到 DB）：互斥锁（Singleflight 只让一个请求查 DB）、逻辑过期（Key 不过期，业务层异步刷新）。
- **雪崩**（大量 Key 同时过期或 Redis 宕机）：随机过期时间打散、多级缓存（本地缓存+Redis）、限流降级、Redis 高可用。

### 6. 分布式锁怎么实现？有哪些坑？

- **基础实现**：`SET key val NX EX seconds`，释放时用 Lua 脚本校验 Value 再 DEL（防止误删他人锁）。
- **进阶方案**：RedLock（多节点投票），解决单点故障但争议较大。
- **生产推荐**：使用 Redisson 框架，自带看门狗自动续期、可重入锁、阻塞等待、读写锁等高级特性。
- **常见坑**：时钟回拨导致锁提前过期、主从切换锁丢失、锁过期但业务未完成。

### 7. 大 Key 问题怎么处理？

- **定义**：String > 10KB，Hash/List/Set/ZSet > 5000 元素。
- **危害**：网络带宽打满、主线程阻塞（删除/序列化耗时）、内存不均（Cluster 数据倾斜）。
- **解决方案**：
    1. 拆分：将大 Key 拆分为多个小 Key（如按时间分片）。
    2. 异步删除：使用 `UNLINK` 替代 `DEL`（异步释放内存）。
    3. 扫描清理：使用 `SCAN` 替代 `KEYS`（非阻塞迭代）。
    4. 监控告警：定期 `MEMORY USAGE` 检测大 Key。

### 8. Redis 内存淘汰策略有哪些？

- **noeviction**：不淘汰，写满报错（默认）。
- **allkeys-lru**：所有 Key 中最近最少使用（最常用）。
- **allkeys-lfu**（4.0+）：所有 Key 中最不经常使用。
- **volatile-lru**：设置了过期时间的 Key 中 LRU。
- **volatile-lfu**（4.0+）：设置了过期时间的 Key 中 LFU。
- **allkeys-random / volatile-random**：随机淘汰。
- **volatile-ttl**：淘汰即将过期的（TTL 最短的）。

### 9. Redis 事务支持 ACID 吗？

**不支持完整的 ACID。**

- **原子性（A）**：不完全支持。编译时错误（如语法错误）会导致整个事务被拒绝；但运行时错误（如类型错误）只影响当前命令，其余命令继续执行，**不会回滚**。
- **隔离性（I）**：支持。`MULTI/EXEC` 之间的命令不会被其他客户端穿插执行（单线程保证）。
- **一致性（C）**：由业务保证，Redis 不做强一致性约束。
- **持久性（D）**：取决于持久化策略（RDB/AOF），与事务无关。

### 10. Pipeline 的原理和局限性？

- **原理**：客户端将多条命令打包，一次性通过网络发送给服务端，服务端排队依次执行后一次性返回结果。核心价值是减少网络 RTT。
- **局限性**：
    1. **非原子性**：Pipeline 中的命令中间可能被其他客户端命令穿插。
    2. **内存消耗**：大批量命令打包会占用客户端和服务端内存。
    3. **错误处理**：部分命令失败不影响其他命令，需客户端自行处理。

### 11. Lua 脚本在 Redis 中的作用？

- **原子性执行**：脚本内所有命令作为一个整体原子执行，期间不会被其他客户端命令插入。
- **减少网络往返**：将多条命令打包为一个脚本，减少网络 RTT。
- **复用性**：通过 `SCRIPT LOAD` + `EVALSHA` 缓存脚本，避免重复传输。
- **注意**：脚本执行期间主线程阻塞，脚本内禁止使用耗时操作（如 `KEYS *`、大 Key 操作）。

### 12. Redis 与数据库一致性如何保证？

- **缓存更新策略**：
    1. **Cache-Aside（旁路缓存）**：读时先查缓存，miss 则查 DB 并写入缓存；写时先更新 DB 再删除缓存（推荐）。
    2. **Read/Write Through**：应用只操作缓存，缓存负责与 DB 同步（需自定义缓存中间件）。
    3. **Write Behind**：应用写缓存，缓存异步批量写 DB（性能高但数据风险大）。
- **关键原则**：优先保证 DB 一致性，缓存作为加速层允许短暂不一致。设置合理的过期时间作为兜底。

### 13. Redis 集群数据迁移过程？

1. **分配槽位**：新节点加入集群，主节点通过 CLUSTER MEET 发现新节点。
2. **开始迁移**：源节点通过 `CLUSTER SETSLOT` 将部分槽位标记为 MIGRATING。
3. **数据迁移**：源节点通过 `MIGRATE` 命令将槽位数据逐个迁移到目标节点。
4. **客户端重定向**：迁移期间访问被迁移槽位的客户端收到 ASK 重定向，自动转发到目标节点。
5. **完成迁移**：源节点将槽位标记为 DONE，目标节点开始负责该槽位。

### 14. 什么是 Redis 的热 Key 问题？如何排查和处理？

- **问题**：某个 Key 被高频访问，导致单个 Redis 实例的 CPU 或网络带宽被打满。
- **排查**：`SLOWLOG` 查看高频命令、`INFO stats` 查看 keyspace_hits/misses、使用 `--hotkeys` 参数扫描。
- **处理方案**：
    1. **本地缓存**：在应用服务器本地（如 Caffeine）缓存热 Key，减少 Redis 压力。
    2. **多副本**：在 Cluster 中将热 Key 复制到多个节点，分散读压力。
    3. **Key 拆分**：将一个大 Key 拆分为多个小 Key（如 `hotkey:1`、`hotkey:2`...），分散访问。

### 15. Redis 的持久化机制有哪些？各自优缺点？

| 持久化方式 | 原理 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **RDB** | fork子进程写快照文件 | 文件小、恢复快、适合备份 | 可能丢数据、fork大内存有开销 |
| **AOF** | 追加写命令日志 | 数据更安全、可配置 fsync 策略 | 文件大、恢复慢 |
| **混合持久化** | RDB快照 + AOF增量 | 兼顾恢复速度与数据安全 | Redis 4.0+ 才支持 |

### 16. Redis 如何实现消息队列？

- **List 实现**：`LPUSH` + `BRPOP`，简单但消息不持久化、无 ACK 机制。
- **Stream 实现**（推荐）：`XADD` 写入、`XREADGROUP` 消费、`XACK` 确认，支持消费者组、消息重试、回溯。
- **Publish/Subscribe**：`PUBLISH` + `SUBSCRIBE`，轻量但消息不持久化、无消费确认。

### 17. Redis 6.0 多线程 I/O 的原理？

Redis 6.0 引入的多线程仅用于网络 I/O 层：

```
[网络线程1] [网络线程2] ... [网络线程N]
     |           |              |
     v           v              v
[读取Socket数据] [解析RESP协议] [写入响应数据]
     |           |              |
     +-----+-----+--------------+-+
           |                     |
           v                     v
    [命令放入主线程队列]  [主线程单线程执行命令]
                              |
                              v
                    [结果写入I/O线程写缓冲区]
```

- **多线程负责**：Socket 读取、RESP 协议解析、响应数据写入 Socket。
- **单线程负责**：命令执行、内存操作、写缓冲区管理。
- **收益**：在网络带宽成为瓶颈的场景下（万兆网卡），多线程 I/O 能显著提升吞吐量。

### 18. Redis 的内存管理机制？如何监控和优化？

- **内存管理**：使用 jemalloc 分配器，支持 Active Defrag 整理碎片。
- **maxmemory**：必须设置最大内存限制，配合淘汰策略使用。
- **监控命令**：`INFO memory` 查看内存使用、`MEMORY USAGE key` 查看 Key 内存、`MEMORY DOCTOR` 诊断问题。
- **优化建议**：设置合理的 maxmemory（物理内存 70-80%）、开启 Active Defrag、避免大 Key、合理选择淘汰策略。

### 19. Redis 集群中节点是如何通信的？

通过 **Gossip 协议** 进行节点间通信：

- **PING/PONG**：节点间定期发送心跳，检测节点存活状态。
- **MEET**：管理员通过 `CLUSTER MEET` 手动添加新节点。
- **FAIL**：节点故障时，其他节点通过 Gossip 传播故障信息。
- **SYNC**：节点间同步哈希槽分配信息。

Gossip 协议的特点是最终一致性——所有节点最终会达成一致的状态，但短时间内可能出现不一致。

### 20. 你如何设计一个基于 Redis 的高并发系统？

**架构要点：**

1. **缓存层**：Redis Cluster 做分布式缓存，本地缓存（Caffeine）做二级缓存。
2. **异步处理**：消息队列（Stream/Kafka）解耦读写链路。
3. **限流降级**：Redis 计数器 + Lua 脚本实现滑动窗口限流。
4. **高可用**：Sentinel/Cluster 保证 Redis 高可用，应用层做熔断降级。
5. **持久化**：混合持久化保证数据安全，定期 RDB 备份。
6. **监控**：Prometheus + Grafana 监控 QPS、延迟、内存、连接数等指标。
7. **大 Key 治理**：定期扫描大 Key，拆分+异步删除。
8. **连接池**：使用连接池（Lettuce/Jedis Pool）复用连接，减少握手开销。
