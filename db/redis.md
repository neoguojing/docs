
# Redis 架构与技术文档

## 1. 定位与数据模型

### 核心定位与解决的问题

Redis（Remote Dictionary Server）是一个开源的、基于内存的高性能键值存储数据库，同时兼具缓存、消息代理和流处理功能。其核心设计目标是提供亚毫秒级的响应延迟和极高的吞吐量，解决传统磁盘数据库在高并发场景下的性能瓶颈，以及复杂业务逻辑下的状态管理问题。

### 数据库生态定位对比

| 特性维度 | Redis | 关系型数据库 (MySQL/PG) | 其他 NoSQL (MongoDB/Cassandra) |
| :--- | :--- | :--- | :--- |
| **存储介质** | 内存为主，磁盘为辅 | 磁盘为主，内存为辅 | 磁盘/内存混合 |
| **数据模型** | Key-Value / 多数据结构 | 二维表 / 关系模型 | 文档 / 宽列 / 图 |
| **查询能力** | 基于 Key 的 O(1) 查找 | 复杂 SQL / JOIN / 聚合 | 灵活查询，弱事务 |
| **事务支持** | 基础事务 (无回滚) / Lua | ACID 强事务 | 最终一致性 / 弱事务 |
| **典型场景** | 缓存、会话、排行榜、锁 | 核心业务、复杂报表 | 内容管理、时序数据 |

### 五大基本数据类型及应用

1. **String**：最基础的类型，可存储字符串、整数或浮点数。常用于缓存、计数器（`INCR`/`DECR`）、分布式锁、Session 共享。
2. **Hash**：键值对集合，适合存储对象。相比序列化整个 JSON 字符串，Hash 支持对内部字段的单独读写，节省内存且减少网络开销。常用于用户信息、购物车。
3. **List**：双向链表（底层 Quicklist），支持两端推入/弹出。适用于消息队列、最新列表、分页数据。
4. **Set**：无序字符串集合，支持交集、并集、差集。适用于标签系统、共同好友、抽奖、去重。
5. **ZSet (Sorted Set)**：在 Set 基础上增加分数（Score）排序。适用于排行榜、延迟队列、滑动窗口限流。

### 扩展数据类型

- **Bitmaps**：基于 String 的位操作，极致节省空间。适用于签到、在线状态、布隆过滤器。
- **HyperLogLog**：基数统计，固定 12KB 内存估算百万级去重数据。适用于 UV 统计。
- **Geo**：地理位置索引。适用于附近的人、距离计算。
- **Streams**：Redis 5.0 引入，支持消费者组、ACK 机制、消息回溯。适用于高可靠消息队列、事件溯源。

### 底层编码与内存优化

Redis 根据数据量和元素类型自动选择底层编码，以平衡时间与空间：

- **SDS**：String 底层实现，记录 `len` 和 `free`，支持 O(1) 获取长度，二进制安全。
- **ZipList / ListPack**：ListPack 是 ZipList 的改进版（Redis 7.0+），解决连锁更新问题。用于小列表、小哈希、小集合。
- **QuickList**：List 的默认实现，双向链表连接 ZipList/ListPack，兼顾插入性能与内存紧凑。
- **SkipList (跳表)**：ZSet 底层实现，支持 O(log N) 的范围查询与单点查找。
- **HashTable**：Hash、Set、ZSet 在数据量大时的默认实现，O(1) 查找。

## 2. 存储引擎

### 内存存储特性

Redis 全内存操作，避免磁盘 I/O 成为瓶颈。通过 `maxmemory` 限制内存上限，配合淘汰策略保证服务不宕机。所有命令均为原子操作，无需锁竞争。

### 单线程事件循环模型

Redis 核心命令处理采用单线程模型，基于 **Reactor 模式**：

1. **避免上下文切换**：无多线程锁竞争，CPU 利用率高。
2. **简化设计**：无死锁风险，代码逻辑清晰。
3. **瓶颈转移**：性能瓶颈通常在网络带宽或内存大小，而非 CPU。

> **注意**：Redis 6.0+ 引入多线程 I/O，仅用于网络读写（`read`/`write` 系统调用），命令执行依然单线程，以解决高并发下的网络 I/O 瓶颈。

### 网络 I/O 多路复用

Redis 基于 `epoll` (Linux)、`kqueue` (BSD/Mac)、`select` (Windows) 实现 I/O 多路复用。单个线程即可同时监听数千个 Socket 连接，当 Socket 有读写事件时，才触发相应的回调处理，实现高并发连接管理。

### 命令执行流程

1. **解析**：客户端发送 RESP 协议数据。
2. **查找**：在命令表中查找对应函数指针。
3. **执行**：调用命令处理函数，操作数据结构。
4. **响应**：将结果序列化为 RESP 协议返回客户端。

### RESP 协议

Redis 序列化协议（RESP）是文本协议，易于解析：

- **Simple String**：`+OK\r\n`
- **Error**：`-ERR message\r\n`
- **Integer**：`:1000\r\n`
- **Bulk String**：`$5\r\nhello\r\n`
- **Array**：`*2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n`

## 3. 内存与数据结构

### 内存管理机制

Redis 使用 `jemalloc` 作为默认内存分配器，相比 `glibc malloc`，能有效减少内存碎片。通过 `info memory` 可查看 `used_memory`、`mem_fragmentation_ratio` 等关键指标。

### 内存淘汰策略

当 `maxmemory` 达到上限时，根据 `maxmemory-policy` 执行淘汰：

| 策略 | 范围 | 算法 | 适用场景 |
| :--- | :--- | :--- | :--- |
| `allkeys-lru` | 所有 Key | 最近最少使用 | 缓存，无特定过期时间 |
| `volatile-lru` | 设置过期时间的 Key | 最近最少使用 | 缓存，部分 Key 需持久化 |
| `allkeys-random` | 所有 Key | 随机 | 循环访问，无特定偏好 |
| `volatile-random` | 设置过期时间的 Key | 随机 | 同上，但仅淘汰有过期时间的 |
| `volatile-ttl` | 设置过期时间的 Key | 剩余 TTL 最短 | 优先淘汰即将过期的 |
| `noeviction` | - | 不淘汰，写入报错 | 强一致性要求，不允许丢数据 |

### 内存碎片与整理

- **碎片产生**：频繁分配/释放不同大小的内存块导致。
- **Active Defrag**：Redis 4.0+ 支持 `activedefrag yes`，在空闲 CPU 周期自动整理内存，无需重启。

### 数据过期策略

1. **惰性删除**：访问 Key 时检查是否过期，过期则删除。
2. **定期删除**：每 100ms 随机抽取一批设置了过期时间的 Key，删除过期的；若过期比例 > 25%，则重复抽取，但有时间上限防止阻塞。

### 内存优化技巧

- **小对象合并**：利用 ListPack/ZipList 阈值（`list-max-listpack-size`）。
- **Hash 编码**：字段少且值短时，使用 `hash-max-listpack-entries` 优化。
- **避免大 Key**：String > 10KB，集合 > 5000 元素需警惕，应拆分或异步删除（`UNLINK`）。

## 4. 索引与查询

### 键的查找与匹配

- **精确查找**：`GET`、`HGET`，O(1) 复杂度。
- **模式匹配**：严禁在生产环境使用 `KEYS *`，必须使用 `SCAN` 游标迭代，避免阻塞主线程。

### 慢查询日志

- **配置**：`slowlog-log-slower-than 10000` (微秒)，`slowlog-max-len 128`。
- **分析**：`SLOWLOG GET` 查看慢命令，定位性能瓶颈。

### 事务机制

- **MULTI/EXEC**：将命令入队，执行时顺序运行，**不支持回滚**（语法错误入队前报错，运行错误仅跳过该条）。
- **WATCH**：乐观锁，监控 Key 变化，若执行前 Key 被修改，事务失败。

### Lua 脚本

- **原子性**：脚本执行期间阻塞其他命令，保证逻辑原子性。
- **减少 RTT**：服务端执行，减少网络往返。
- **缓存**：`SCRIPT LOAD` + `EVALSHA` 避免重复传输脚本内容。

### 管道（Pipeline）

客户端将多个命令打包发送，服务器批量处理并返回。非原子性，但显著降低网络延迟，适合批量写入。

### 排序与过滤

- **SORT**：对 List/Set/ZSet 排序，支持 `BY`、`GET`、`LIMIT`、`STORE`。
- **注意**：`SORT` 是 O(N) 操作，大数据量慎用，建议用 ZSet 替代。

## 5. 并发与一致性

### 单线程模型的优势与局限

- **优势**：无锁、无上下文切换、实现简单、调试容易。
- **局限**：单机 CPU 上限，无法利用多核进行计算密集型任务；慢命令会阻塞整个实例。

### 并发写入策略

- **Pipeline**：高吞吐写入，无原子性保证。
- **Lua**：复杂逻辑原子写入，需控制脚本执行时长（`lua-time-limit`）。
- **事务**：简单批量写入，配合 WATCH 实现乐观锁。

### 分布式锁实现

1. **基础版**：`SET key value NX EX seconds`。Value 必须唯一（如 UUID），释放时用 Lua 校验 Value 再删除，防止误删他人锁。
2. **RedLock**：向 N 个独立 Master 加锁，超过半数成功才算成功。解决单点故障导致的锁丢失，但争议较大，推荐优先使用 ZooKeeper/Etcd 或 Redisson 的看门狗机制。

### 发布订阅 (PUB/SUB)

- **机制**：Fire-and-Forget，消息不持久化，订阅者离线即丢失。
- **局限**：无 ACK，无回溯，背压处理困难。

### Stream 消息队列

- **消费者组**：类似 Kafka，支持 `XREADGROUP`，消息分配给组内消费者。
- **ACK 机制**：`XACK` 确认消费，未确认消息进入 PEL（Pending Entries List），可通过 `XAUTOCLAIM` 重新分配，保证 At-Least-Once 语义。

### 一致性模型

- **主从复制**：异步复制，默认**最终一致性**。主节点宕机可能丢失未同步数据。
- **强一致**：`WAIT` 命令等待从节点确认，但仍有极端情况（如主从同时宕机）导致不一致。Redis 不追求 CP，而是 AP/最终一致。

### 写扩散与读扩散

- **写扩散**：客户端向所有节点写，Redis 内部主从异步同步。
- **读扩散**：客户端轮询或随机读从节点，需接受短暂数据滞后。

## 6. 分布式与高可用

### 主从复制

1. **全量复制**：首次连接或断线过久，Master 执行 `BGSAVE` 生成 RDB，传输并加载，期间写命令缓存后重放。
2. **增量复制**：基于 `repl_backlog_buffer` 和 `offset`，仅传输差异命令。
3. **PSYNC**：Redis 2.8+ 统一全量/增量复制协议，支持部分重同步。

### 复制延迟与解决方案

- **原因**：网络带宽、大 Key 阻塞、从节点执行慢命令、磁盘 I/O。
- **解决**：从节点 `slave-read-only yes`，开启 `noeviction` 防止从节点淘汰数据导致主从数据不一致，使用 Pipeline 减少 RTT。

### Redis Sentinel

- **功能**：监控、自动故障转移、配置发现、客户端通知。
- **故障判定**：主观下线（SDOWN）-> 客观下线（ODOWN，Quorum 投票）-> Leader 选举 -> 故障转移。
- **脑裂**：网络分区导致双主，需配置 `min-slaves-to-write` 限制写入。

### Redis Cluster

- **数据分片**：16384 个哈希槽（Hash Slot），`CRC16(key) % 16384` 决定归属节点。
- **去中心化**：每个节点维护集群状态，Gossip 协议传播信息。
- **重定向**：客户端访问错误节点，收到 `MOVED`（永久重定向）或 `ASK`（临时重定向，迁移中）。

### 扩容与缩容

- **扩容**：新增节点，手动迁移槽位（`CLUSTER ADDSLOTS` / `redis-cli --cluster reshard`），迁移过程在线，客户端通过 `ASK` 感知。
- **缩容**：迁出槽位，移除节点（`CLUSTER FORGET`）。

### 跨机房与多活

- **Redis Enterprise / 云厂商方案**：Active-Active 双向同步，CRDT 解决冲突，本地读低延迟。
- **开源方案**：RedisShake / DTS 进行数据同步，通常为主备模式，跨机房延迟高，不建议做实时读。

## 7. 持久化与恢复

### RDB 快照

- **原理**：`fork` 子进程，利用 COW (Copy-On-Write) 生成时间点快照。
- **触发**：`save <seconds> <changes>`，`BGSAVE`，`FLUSHALL`。
- **优点**：文件紧凑，恢复快。
- **缺点**：fork 大内存耗时，可能丢失最后一次快照后的数据。

### AOF 持久化

- **原理**：追加写命令到日志文件。
- **Fsync 策略**：
    - `always`：每条写入，最安全，性能差。
    - `everysec`：每秒刷盘，折中方案，最多丢 1s 数据（推荐）。
    - `no`：OS 决定，性能最好，风险最大。
- **Rewrite**：后台重写，压缩文件体积，去除冗余命令。

### 混合持久化 (Redis 4.0+)

- **配置**：`aof-use-rdb-preamble yes`。
- **机制**：AOF 重写时，前段为 RDB 格式，后段为增量 AOF 命令。兼顾恢复速度与数据安全性。

### 性能影响

- **RDB**：Fork 时的页表复制耗时，COW 导致的内存翻倍风险。
- **AOF**：`fsync` 阻塞主线程（若使用 `always` 或 OS 繁忙），Rewrite 时的 I/O 压力。

### 故障恢复

1. 优先加载 AOF（若开启且文件存在）。
2. 否则加载 RDB。
3. 加载期间拒绝外部请求（Redis 7.0+ 支持异步加载，但仍有启动延迟）。

### 文件安全

- **校验**：`redis-check-aof --fix` 修复截断文件。
- **备份**：定期 RDB 异地备份，防止 AOF 重写逻辑 Bug 或误操作（如 `FLUSHALL` 被追加到 AOF）。

## 8. 性能与场景

### 性能基准

- **QPS**：单机 10w+ QPS（Pipeline 可达更高），受限于网络与内存带宽。
- **延迟**：P99 < 1ms，受大 Key、慢命令、Fork、网络抖动影响。

### 适用场景

1. **缓存**：减轻 DB 压力，热点数据加速。
2. **会话存储**：Web 集群 Session 共享，无状态架构。
3. **计数器/限流**：原子操作，滑动窗口，令牌桶。
4. **排行榜**：ZSet 天然支持。
5. **消息队列**：轻量级场景，Stream 提供可靠投递。
6. **分布式锁**：高并发互斥资源访问。

### 不适用场景

1. **大数据量存储**：内存成本高，应选 ES/HBase/S3。
2. **复杂关联查询**：无 JOIN，多表关联需应用层组装，性能差。
3. **强事务/强一致**：金融核心账务，选关系型 DB 或 NewSQL。
4. **冷数据归档**：Redis 不适合做长期存储仓库。

### 性能调优建议

1. **连接池**：复用连接，避免频繁握手。
2. **大 Key 治理**：监控 `BIGKEYS`，拆分 Hash/List，异步删除 `UNLINK`。
3. **热 Key 问题**：本地缓存（Caffeine/Guava）+ 读写分离 + 从节点扩容。
4. **网络优化**：同机房部署，开启 TCP Keepalive，调整 `tcp-backlog`。
5. **OS 优化**：关闭 THP (Transparent Huge Pages)，调整 `vm.overcommit_memory=1`，增加 `somaxconn`。

### 生产环境最佳实践

- **版本**：推荐 Redis 7.x，享受 Function、ACL v2、Sharded Pub/Sub 等新特性。
- **安全**：开启 ACL，禁用危险命令（`FLUSHALL`, `KEYS`, `CONFIG`），绑定内网 IP。
- **监控**：Prometheus + Grafana，关注 `rejected_connections`、`evicted_keys`、`keyspace_hits/misses`。
- **容量规划**：内存预留 30% 给 Fork/COW，单实例内存建议 < 10GB（减少 Fork 耗时）。
- **高可用**：至少 3 主 3 从，Sentinel/Cluster 跨机架/可用区部署。
