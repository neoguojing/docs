# AI Agent 工程实践全景指南

## 1. 整体架构哲学：灵活性与确定性的平衡

### 1.1 核心挑战

构建 Agent 的本质是在 LLM 的**概率性（灵活性）**与工程系统的**确定性（可靠性）**之间找到平衡点。

### 1.2 为什么代码类 Agent 最先可行？

- **试错成本低**：代码写错了可以改，不像物理世界操作不可逆。
- **反馈速度快**：编译器、解释器和测试用例能提供即时反馈。
- **确定性验证**：代码是否运行成功、测试是否通过，有客观标准（Pass/Fail），而非主观判断。
- **人机协作**：在确实犯错的基础上投入，通过自动纠错实现复利。

### 1.3 产品定位与人机边界

- **助手 vs. 自动化系统**：需明确 Agent 是作为"副驾驶"（Copilot）辅助人类，还是作为"自动驾驶"（Autopilot）独立完成任务。
- **渐进放权模式**：初期由人确认关键节点，随着信任建立逐渐放权。
- **沙箱验证模式**：在隔离环境中执行高风险操作，验证无误后再应用到生产环境。
- **边界定义**：任务划分清晰，明确人和 Agent 的边界。

### 1.4 核心能力模型

- **自主决策**：适应未知环境，具备创造性解决问题的能力。
- **自我反思**：感知行动结果，验证是否达标，若不达标则自动迭代修正。
- **架构约束**：通过架构设计限制 Agent 的行为范围，而非仅靠 Prompt。

## 2. 上下文工程：记忆的压缩与蒸馏

### 2.1 核心挑战

随着交互深入，上下文窗口会迅速膨胀（50 轮交互可能突破 128k），必须进行精细化管理。

### 2.2 上下文压缩策略

- **微压缩**：清理规则，移除过时信息（如"10 分钟前读的内容"），删除冗余的工具结果。
- **会话记忆压缩**：将记忆转化为目录结构，限制 Token 数和消息数。
- **完整压缩（9 维分析法）**：在 `<analyse>` 标签中执行分析，输出 `<summary>`（模仿思维链）。
  1. 用户请求意图
  2. 关键技术概念
  3. 文件和代码片段
  4. 错误和修复
  5. 问题解决过程
  6. 所有用户消息
  7. 代办任务
  8. 当前工作
  9. 可选的下一步

### 2.3 信息价值评分

并非所有消息都值得保留，需建立评分机制：

- **指令**：原文保留。
- **关键状态**：转化为结构化摘要。
- **中间推理**：激进摘要，仅保留结论。
- **失败摘要**：记录失败原因，避免重蹈覆辙。

### 2.4 性能优化

- **Prefill 缓存**：将 System Prompt 等不变部分缓存，仅处理变化的动态部分。
- **增量构建**：并行加载文件，提前加载上下文。
- **P99 延迟关注**：关注长尾延迟，优化最差情况下的响应速度。

## 3. 记忆管理：从短期到长期的知识沉淀

### 3.1 记忆分层

- **短期记忆**：当前会话的上下文窗口，随对话推进不断刷新。
- **长期记忆**：跨会话持久化的知识，包括用户偏好、项目结构、历史经验等。
- **工作记忆**：当前任务执行过程中的临时状态，任务完成后丢弃。

### 3.2 记忆存储与检索

- **向量化存储**：将关键信息 Embedding 后存入向量数据库，支持语义检索。
- **结构化存储**：用户偏好、配置项等以 KV 或 JSON 形式存储，精确读取。
- **按需加载**：不将所有记忆注入 Prompt，而是根据当前意图动态检索相关片段。

### 3.3 记忆遗忘机制

- **时效性衰减**：过时信息自动降权或清理。
- **冲突解决**：当新旧记忆冲突时，以最新验证通过的为准。
- **记忆压缩**：定期将碎片化记忆合并为结构化摘要，减少存储冗余。

## 4. 工具设计：能力扩展与按需发现

### 4.1 工具系统架构

- **核心工具常驻**：文件读写、Bash 执行等基础工具始终可用。
- **按需发现**：其他工具（如搜索、API 调用）根据当前任务动态加载。
- **工具规模**：Bash 命令可视为大于 50 个工具，文件系统是信息探索者。

### 4.2 工具调用规范

- **输出指针**：当模型输出过大时，写入外部文件，仅给模型返回文件指针。
- **RESTful 接口降噪**：将 RESTful 接口信息蒸馏，为输入数据降噪，只保留核心参数。
- **工具描述优化**：每个工具需有清晰的名称、参数说明、使用示例，降低模型调用错误率。

### 4.3 工具隔离原则

- 不同 Agent 拥有不同的工具集，实现权限和能力的隔离。
- 只读工具可直接执行，写操作或系统级命令需经过授权或审查。

## 5. 多 Agent 协作：角色拆分与通信机制

### 5.1 何时使用多 Agent？

- **上下文污染**：单一上下文无法容纳所有信息。
- **并行探索**：需要同时尝试多种路径。
- **工具过载**：工具数量超过 20 个，需动态发现和隔离。

### 5.2 何时避免使用？

- 简单查询、低价值任务或单纯的编码任务（单体即可胜任）。
- 子 Agent 应被视为工具，不要过度按角色拆分。

### 5.3 角色拆分原则

- **工具集隔离**：不同 Agent 拥有不同的权限和工具集。
- **Prompt 与权限隔离**：给每个角色明确的权限边界和行为规范。
- **角色示例**：
  - **通用任务 Agent**：主控。
  - **探索 Agent**：负责信息搜集与研究。
  - **Plan Agent**：负责规划。
  - **对抗验证 Agent**：专门负责找茬、发现漏洞。
  - **Guide Agent**：引导流程。
  - **状态 Agent**：负责维护全局状态栏配置。

### 5.4 通信机制

- **文件通信**：Agent 之间通过读写文件交互，而非无限叠加的对话历史，减少上下文污染。
- **迭代合同**：Agent 之间通过明确的输入输出标准进行协作。
- **状态同步**：使用状态 Agent 维护全局任务进度，避免信息在对话中丢失。

### 5.5 架构逻辑示意

```text
[用户输入]
    │
    ▼
[规划器/主控 Agent] ──(文件/指令)──> [子 Agent 集群]
    │                                  │
    │                                  ├── [探索 Agent] (研究/搜索)
    │                                  ├── [执行 Agent] (代码/工具)
    │                                  └── [验证 Agent] (测试/找茬)
    │                                  │
    ▼                                  ▼
[上下文管理器] <──(状态同步/结果)── [评估器/质量门禁]
    │
    ▼
[最终输出]
```

## 6. 提示词工程：模块化与动态注入

### 6.1 模块化设计

- **静态段**：身份、安全指令、代码风格（利用服务端缓存，防止失效）。
- **动态段**：启用的工具、当前工作目录、用户偏好、外部插件等。
- **防幻觉指令**：防止模型说谎，防止模型过度谨慎。

### 6.2 行动风险评估框架

- 判断操作是否可逆、影响范围，决定是否需要人工介入。
- 在工具调用前，通过分类器分析命令类型。

### 6.3 提示词优化技巧

- **思维链引导**：通过 `<analyse>` 等标签引导模型先思考再输出。
- **示例驱动**：提供 Few-shot 示例，明确期望的输出格式。
- **约束强化**：使用"必须"、"禁止"等强约束词，减少模型自由发挥空间。

## 7. Skill 工程：能力的封装与复利增长

### 7.1 Hermes Agent 模式（闭环学习）

- **核心循环**：执行 → 提炼 → 存储 → 索引 → 复用 → 更新。
- **技能沉淀**：当后台检测到重复的复杂操作（如 10 次工具调用）时，自动将其封装为"Skill"。
- **渐进式加载**：Prompt 中仅保留 Skill 名称和索引，实际内容按需加载，节省 Token。

### 7.2 Skill 封装标准

- **触发条件**：明确什么场景下激活该 Skill。
- **输入输出规范**：定义清晰的参数和返回值。
- **执行步骤**：将复杂操作拆解为可复用的步骤序列。
- **版本管理**：Skill 支持迭代更新，旧版本可回滚。

### 7.3 技能复利

- 随着使用次数增加，Skill 库不断扩充，Agent 能力呈指数增长。
- 高频 Skill 优先加载，低频 Skill 按需检索。

## 8. 安全与权限：确定性的防线

### 8.1 安全沙箱

- **容器化部署**：严格管控文件系统读写和 Bash 权限。
- **最小权限原则**：只给必要的权限。
- **隔离环境**：所有代码执行和文件操作必须在沙箱中进行，物理隔离生产环境。

### 8.2 权限管控

- **分类器**：分析命令类型。只读命令直接执行，写操作或系统级命令需弹出授权。
- **审查器**：使用另一个模型审查输入和工具调用，而非仅审查结果。
- **人机回环（Human-in-the-loop）**：高危操作必须暂停执行，请求用户显式授权。

### 8.3 失败处理机制

- **隐形失败**：
  - **死循环**：设置最大循环次数。
  - **方向偏移**：通过自我反思机制纠正。
  - **上下文溢出**：触发上下文管理策略。
  - **检查点**：保存中间状态。
- **快速失败**：遇到不可恢复错误时，保留检查点并优雅退出。
- **现实失败**：明确的错误信息反馈。

## 9. Harness 工程：自维护与自验证闭环

### 9.1 LangChain Harness 模式

- **自验证循环**：系统自我检查，形成闭环。
- **可拆卸性**：模块之间低耦合，支持独立升级和替换。
- **预防-修复-测量**：强调系统的预防、修复与测量能力。

### 9.2 输出解析与鲁棒性

- **常见问题类型**：
  - 礼貌性自杀：模型输出"抱歉我不能..."等非结构化文本。
  - Markdown 强迫证：强制包裹在 Markdown 代码块中。
  - 类型混乱：数字变字符串等。
  - 截断式：输出不完整。
  - 幻觉补全：编造不存在的字段。
  - 引号问题：转义错误。
- **修复手段**：
  - **约束解码**：使用 Function Calling 的 Strict 模式或 Logit Masking。
  - **后处理**：使用 `json_repair` 等开源库自动修复。
  - **验证器重试**：Schema 校验失败后，将错误信息回传给 LLM 自动修正。
  - **代码清洗**：去除 Markdown 标记。
  - **Prompt 修复**：让 LLM 自动修复自己的输出。

### 9.3 评测与迭代

- **Pass@k**：尝试 k 次，至少成功一次的概率（考察解决问题的能力）。
- **Pass^k**：连续 k 次尝试都成功（考察稳定性）。
- **降智评测**：在限制资源或干扰下，Agent 是否还能保持基本功能。
- **评分维度**：代码评分、模型评分、人工评分。
- **自动化测试**：建立测试用例库，记录中间过程和最终结果。

### 9.4 协议与互联

- **A2A 协议**：Google 发布的跨厂商、跨组织协议，支持独立部署的 Agent 动态发现和第三方集成，是企业级场景的关键。

## 附录：常见面试问题与解析

**Q1: 在多智能体架构中，如何避免 Agent 之间陷入死循环或无效沟通？**

**A:** 关键在于引入**状态管理**和**明确的退出机制**。

1. **状态隔离**：使用状态 Agent 维护全局任务进度，避免信息在对话中丢失。
2. **文件通信**：Agent 间通过读写文件交互，而非无限叠加的对话历史，减少上下文污染。
3. **最大循环限制**：在 Orchestrator 层设置最大迭代次数，超时强制触发"快速失败"或人工介入。

**Q2: 面对长上下文（Long Context）带来的高延迟和高成本，有哪些优化策略？**

**A:** 核心是**分层压缩**与**缓存利用**。

1. **Prefill 缓存**：将 System Prompt 等静态部分缓存，只对新输入进行推理。
2. **信息蒸馏**：对历史对话进行"激进摘要"，仅保留关键决策和结论，丢弃中间推理过程。
3. **按需加载**：不将所有工具描述放入 Prompt，而是根据当前意图动态检索并注入相关工具定义。

**Q3: 如何保证 Agent 执行高危操作（如 rm -rf 或数据库删除）的安全性？**

**A:** 必须建立**确定性防线**。

1. **分类器拦截**：在工具调用前，通过一个小模型或规则引擎识别操作风险等级。
2. **人机回环（Human-in-the-loop）**：高危操作必须暂停执行，请求用户显式授权。
3. **沙箱环境**：所有代码执行和文件操作必须在容器或受限权限的沙箱中进行，物理隔离生产环境。

---

> **总结**：构建优秀的 Agent 系统，不仅是调用 LLM API，更是一场关于**上下文管理、确定性工程约束、以及人机协作边界**的系统工程。通过模块化设计、闭环学习机制和严格的安全沙箱，可以让 Agent 从"玩具"进化为可靠的"生产力工具"。
