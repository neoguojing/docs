# AI 上下文工程与记忆管理架构

## 1. 核心目标与原则

- **目标**：找到**最小的高信噪比 Token 集合**，最大化期望结果的概率。
- **原则**：不是尽可能多塞信息，而是提取与任务最相关的关键信息。
- **本质**：从"被动输入静态 Prompt"转向"主动构建、管理动态上下文系统"。

## 2. 核心挑战：为什么需要上下文工程？

### 2.1 输入变长，性能下降（上下文腐烂 Context Rot）

- 随着上下文增长，模型出现事实性错误增加、逻辑连贯性减弱。
- **"中间迷失"效应 (Lost in the Middle)**：模型注意力呈 U 型分布，过度关注开头和结尾，显著忽视中间部分。
- **相似任务模式固化**：无脑重复，缺乏变异。

### 2.2 成本与延迟

- **KV Cache 命中**：缓存 Token 成本极低（如 $0.3/百万），未缓存成本高昂（如 $3/百万），差距可达 10 倍。
- **计算复杂度**：Transformer 自注意力机制复杂度为 $O(n^2)$，长度翻倍计算量变四倍。

## 3. 上下文工程六大策略体系

为了解决上述问题，业界提炼出了六层工程实践：

### 3.1 压缩重启 (Compaction)

- 摘要压缩，翻页续写。
- 当对话接近上限，用模型对历史做高保真摘要，带着摘要重启新窗口。

### 3.2 外化记忆 (Externalization)

- 关键信息写入文件（如 `TODO.md`, `NOTES.md`）。
- 上下文只保留结论和下一步，利用文件系统作为"终极上下文"。

### 3.3 及时加载 (Just-in-Time Context)

- 维护标识符（文件路径、数据库查询、网页链接）。
- 按需拉取，而非一次性全量注入。

### 3.4 上下文隔离 (Isolation)

- 多 Agent 架构，子 Agent 独立上下文，互不污染。

### 3.5 工具设计 (Tool Design)

- 通过 **Logits 遮蔽**不需要使用的工具，避免"工具爆炸"导致模型困惑。
- 分层动作空间：Agent as Tool（子流程封装）、沙箱工具、原子函数。

### 3.6 缓存友好 (Cache Friendly)

- 围绕 KV Cache 设计，保持 **Stable Prefixes**（稳定前缀）和 **Append-Only**（追加式更新）。

## 4. 记忆管理系统 (Memory Management)

记忆系统的设计遵循"分层存储、按需检索"的原则。

### 4.1 记忆的分层与分类

- **短期/工作记忆**：当前会话上下文，滑动窗口管理。
- **长期记忆**：
  - **用户 Profile**：偏好、习惯、设备类型。
  - **反馈记忆**：用户纠正了什么、肯定了什么。
  - **项目记忆**：时间、地点、状态、设计文档地址、服务器地址等外部依赖。
  - **经验/程序性记忆**：工作流模板、技能逻辑。

### 4.2 记忆的"存"与"不存"

**存什么**：不能通过工具直接获取的信息、用户纠正/肯定的反馈、项目关键状态（Why）、外部依赖引用。

**不存什么**：代码模式、架构、文件路径（可直接获取的）、版本记录、调试修复方案、说明文件里已有的内容、临时性规则。

### 4.3 记忆的检索与注入流程

1. **扫描**：扫描记忆目录，读取上限（如 200 个），且只读前面部分（如 30 行）。
2. **摘要**：记忆整理拼接（类型：名字：时间：描述）。
3. **选择**：输入和记忆给另外一个 LLM 模型，返回最相关记忆；校验文件是否存在。
4. **注入**：每轮最多注入少量记忆（如 5 条，每条 4000 字节），避免重复注入。

### 4.4 记忆的写入机制（谁来写？）

- **后台 Agent 写记忆**：主 Agent 专注任务，后台 Agent 负责全局记忆管理。
- **权限限制**：限制写入目录范围。
- **两轮对话策略**：读取所有记忆文件和最近对话，并行写入。
- **互斥机制**：主模型自己写了，后台就不继续写。

## 5. 架构可视化

```
用户输入 → 上下文构建器

┌─────────────────────────────────────────────────────────────┐
│                    记忆管理系统 (Memory System)               │
│  长期记忆库 → 用户Profile / 反馈记忆 / 项目与引用记忆          │
└─────────────────────────────────────────────────────────────┘
          ↑ 1.扫描/选择/摘要
          ↓ 2.检索/注入
┌─────────────────────────────────────────────────────────────┐
│                    外部存储 (External Storage)                │
│  文件系统/数据库 → TODO.md / NOTES.md / 代码/文档             │
└─────────────────────────────────────────────────────────────┘
          ↑ 3.读取引用
          ↓ 4.组装
┌─────────────────────────────────────────────────────────────┐
│                    上下文窗口 (Context Window)                │
│  系统提示(Stable Prefix) / 历史摘要(Compressed) / 检索记忆    │
│  即时加载内容(JIT) / 当前任务与工具结果                        │
└─────────────────────────────────────────────────────────────┘
          ↓
      大语言模型 (LLM)
          ↓
      Agent 执行
          ↓
  更新进度(TODO) / 记录结论(NOTES) / 触发后台写入(长期记忆)
```

## 6. 渐进式披露与外挂存储

- **渐进式披露**：不一次性加载全量知识或工具。工具层只加载当前任务相关的工具描述；知识层通过 RAG 按需检索；任务层通过 ReAct 模式分步披露全局信息。
- **外挂存储**：中间结果存文件，文件系统是终极上下文。

## 7. 自动压缩策略

参考 ChatGPT 的记忆设计：

- 不用 RAG（因为不够精确），采用结构化记忆。
- **分层记忆**：用户长期事实、近期对话摘要、历史经验案例。
- **会话元数据**：时区、使用习惯、设备类型。

## 8. 常见面试问题

### Q1: 什么是"上下文腐烂"（Context Rot）或"中间迷失"（Lost-in-the-Middle）？如何解决？

**回答要点**：解释模型注意力在长文本中呈 U 型分布，中间信息易被忽略。解决方案包括：结构化变异（打破模式固化）、将关键信息置于开头或结尾、使用摘要压缩、外化记忆（只保留引用）。

### Q2: 在构建长程 Agent 时，如何平衡 KV Cache 的命中率与上下文动态变化的需求？

**回答要点**：强调 **Stable Prefixes**（系统提示、工具定义保持不变）和 **Append-Only**（历史只追加不修改）原则。对于动态变化的工具，可以使用 Logits 遮蔽而非从 Prompt 中移除，以维持 Cache 结构。

### Q3: 为什么推荐使用"文件系统"作为 Agent 的终极上下文，而不是全部塞入 Context Window？

**回答要点**：Context Window 昂贵且有限（注意力稀释）。文件系统无限、持久化。通过 **Just-in-Time (JIT)** 机制，Agent 按需读取（如 `ls`, `grep`, `cat`），保持工作记忆的高信噪比。

### Q4: 记忆系统中，哪些信息应该持久化存储，哪些应该丢弃？

**回答要点**：存储"不可再生"或"高价值"信息（用户偏好、纠正反馈、关键决策原因）。丢弃"可再生"信息（代码结构、文件路径、临时调试信息），这些应通过工具实时获取。

### Q5: 什么是渐进式披露（Progressive Disclosure）在上下文工程中的应用？

**回答要点**：不一次性加载全量知识或工具。例如，工具层只加载当前任务相关的工具描述；知识层通过 RAG 按需检索；任务层通过 ReAct 模式分步披露全局信息。
