# 微服务体系面试指南

> 目标：用于高级后端 /
> 架构师面试。每个问题包含「描述、核心答案、关键技术」，重点掌握为什么、怎么做、优缺点和方案权衡。

## 一、微服务基础与拆分

### 1. 微服务是什么

**描述：**
将一个大型系统拆分成多个围绕业务能力构建、可独立开发和部署的服务。

**答案：**
微服务的核心不是"服务多"，而是业务能力解耦、独立部署和独立扩展。每个服务拥有相对清晰的职责，通过
API 或消息进行协作。

**关键技术：** REST、RPC、MQ、Registry、Gateway、Docker、Kubernetes。

### 2. 为什么使用微服务

**描述：** 为什么不继续使用单体架构。

**答案：**
当系统规模、团队规模和业务复杂度增加后，单体应用会出现代码耦合、发布风险大、扩展粒度粗等问题。微服务可以实现业务解耦、独立部署和按需扩展。但如果系统规模较小，微服务带来的治理成本可能超过收益。

**关键点：** 不是为了微服务而微服务，要看业务和组织规模。

### 3. 单体 vs 微服务

**描述：** 两种架构的主要区别。

**答案：**
单体部署简单、调用成本低、事务容易处理；微服务独立部署和扩展能力更强，但增加了网络通信、服务治理、分布式事务和运维复杂度。

**关键点：** 微服务解决的是规模问题，同时引入分布式系统问题。

### 4. 微服务的优缺点

**答案：** - 优点：解耦、独立部署、独立扩展、故障隔离、团队自治。 -
缺点：网络调用增加、分布式事务复杂、运维复杂、链路排查困难、部署成本提高。

**面试重点：** 能否结合实际项目说明 trade-off。

### 5. 微服务拆分原则

**答案：**
优先按照业务能力和领域边界拆分，而不是按照技术层拆分。一个服务应该有明确职责，并尽量保持数据和业务逻辑内聚。

**原则：** 高内聚、低耦合；稳定边界；独立演进；避免过度拆分。

### 6. 业务边界 / 领域边界

**答案：**
服务边界应该对应相对完整的业务能力。例如订单、支付、库存可以形成不同领域。边界的判断依据是业务职责、数据归属、变化频率和团队职责。

**关键技术：** DDD、Bounded Context。

### 7. 服务粒度如何确定

**答案：**
没有固定标准。太大无法独立演进，太小会造成大量网络调用和治理成本。通常根据业务边界、数据边界、团队规模、调用关系和独立扩展需求确定。

**判断：** 是否能独立部署、扩展和故障隔离。

## 二、服务通信与消息

### 8. 服务之间如何通信

**答案：** 主要分同步和异步。同步通常使用 HTTP/REST 或
RPC，适合实时获取结果；异步通过 Kafka 等 MQ
解耦，适合事件通知、削峰和耗时任务。

### 9. REST / HTTP

**答案：** 基于 HTTP 的资源式 API，简单、通用、跨语言，适合开放 API
和业务服务之间的常规调用。

**优点：** 简单、生态成熟。 **缺点：** JSON 体积较大、协议约束较弱。

### 10. RPC / gRPC

**答案：** RPC 将远程调用抽象成类似本地方法调用。gRPC 通常使用 HTTP/2 +
Protobuf，具有强类型、性能较好、接口契约明确等特点。

**适合：** 内部微服务高频调用。

### 11. 同步 vs 异步

**答案：** - 同步：调用方等待结果，简单直观，但服务之间耦合较强。 -
异步：通过消息传递，降低耦合并削峰，但需要处理消息可靠性、重复消费和最终一致性。

### 12. 消息队列

**答案：** MQ
的主要价值是解耦、异步和削峰。例如订单服务产生事件，其他服务异步消费，而不需要订单服务直接依赖所有下游。

**关键问题：** 丢消息、重复消息、顺序、积压、消费失败。

### 13. Kafka

**答案：** Kafka 是分布式消息系统，核心概念包括
Topic、Partition、Producer、Consumer、Consumer Group 和
Offset。Partition 提供并行能力，Consumer Group 提供消费端水平扩展。

**面试重点：** 为什么使用
Kafka、如何保证可靠性、如何处理重复消费和消息积压。

## 三、服务发现与负载均衡

### 14. 服务注册

**答案：** 服务启动时向 Registry
注册实例地址、端口和元数据；退出时注销或等待健康检查将其摘除。

### 15. 服务发现

**答案：** 调用方根据服务名查询可用实例，而不是直接依赖固定 IP。

**解决：** 动态实例变化问题。

### 16. 服务自动寻址

**答案：** 服务调用使用逻辑服务名，通过 Registry/Discovery
获取实例地址，实现 IP 与业务代码解耦。

### 17. 心跳 / 健康检查

**答案：**
通过心跳或主动探活判断服务是否健康。连续失败的实例可以被标记为不可用，避免继续接收流量。

### 18. 服务上下线

**答案：**
上线时注册并加入流量；下线时先停止接收新请求，再等待已有请求完成，最后摘除实例。

**关键：** 优雅下线。

### 19. 故障实例摘除

**答案：**
通过健康检查发现异常实例后，将其从可用实例列表中移除，恢复后再加入。

### 20. 负载均衡

**答案：** 将请求分配给多个实例，提高吞吐量和可用性。

**常见算法：** Round Robin、Weighted、Least Connections、Hash。

### 21. F5

**答案：** F5 属于典型的 Server-side Load Balancer。客户端请求先到
F5，再由 F5 将流量转发到后端服务实例。

**特点：** 硬件/虚拟化负载均衡、稳定、成熟，适合企业级流量入口。

### 22. Nginx

**答案：** Nginx 可以承担反向代理、HTTP 负载均衡、TLS 终止和网关等职责。

### 23. Client-side / Server-side Load Balance

**答案：** - Client-side：客户端发现实例并自行选择，例如服务 SDK +
Registry。 - Server-side：客户端只访问统一入口，由 F5/Nginx/Gateway
选择后端。

**区别：** Client-side 灵活，但客户端复杂；Server-side
集中治理，但增加中间层。

### 24. Gateway

**答案：** Gateway
是统一流量入口，可以负责路由、鉴权、限流、协议转换、灰度等。

### 25. 路由

**答案：** 根据 URL、Header、服务名、版本等规则将请求转发到目标服务。

**技术：** Nginx、Gateway、K8s Ingress。

## 四、服务治理与稳定性

### 26. 限流

**答案：** 限制单位时间内的请求量，保护服务和数据库。

**算法：** 令牌桶、漏桶、滑动窗口。

### 27. 熔断

**答案：**
当下游服务持续失败时，暂时停止继续调用，避免故障扩散；经过一段时间后再尝试恢复。

### 28. 降级

**答案：** 非核心功能出现故障时返回兜底结果，优先保证核心业务可用。

### 29. 超时

**答案：** 为调用设置最大等待时间，防止请求长期占用线程、连接等资源。

### 30. 重试

**答案：**
对临时性错误重新请求，但必须设置次数、退避时间，并结合幂等设计。

**风险：** 重试风暴会进一步压垮下游。

### 31. 幂等

**答案：** 同一个请求执行一次和执行多次，最终业务结果应该一致。

**方案：** Request ID、唯一键、状态机、去重表。

### 32. 服务雪崩

**答案：**
一个下游服务故障导致请求堆积，进一步耗尽上游资源，最终多个服务连锁故障。

**解决：** 超时、限流、熔断、降级、隔离、舱壁。

### 33. 故障隔离

**答案：** 将不同业务或依赖的资源隔离，限制故障传播范围。

**方案：** 独立线程池、连接池、资源配额、服务拆分。

------------------------------------------------------------------------

## 五、分布式事务与数据

### 34. 分布式事务

**答案：** 一个业务操作涉及多个服务或数据库时，需要保证整体一致性。

**方案：** 2PC、TCC、Saga、消息最终一致性。

### 35. 数据一致性

**答案：**
多副本、多服务之间的数据是否符合预期。需要根据业务选择强一致、弱一致或最终一致。

### 36. 最终一致性

**答案：** 不要求所有节点立即一致，只要求经过一定时间后达到一致。

**常见方案：** MQ + 重试 + 幂等 + 补偿。

### 37. 缓存 / Redis

**答案：** Redis 常用于缓存热点数据，降低数据库压力并提高访问速度。

**重点：** 缓存穿透、击穿、雪崩、数据一致性、热点 Key。

### 38. 数据库拆分

**答案：**
微服务通常让数据跟随业务边界拆分，每个服务负责自己的数据，减少跨服务直接访问数据库。

### 39. 分库分表

**答案：**
当单库/单表的数据量或并发达到瓶颈时，通过水平拆分降低单节点压力。

**问题：** 跨库查询、事务、扩容和数据迁移。

### 40. 读写分离

**答案：** 写请求进入主库，读请求分发到副本，提高读吞吐。

**注意：** 副本同步存在延迟。

## 六、配置、治理与可观测性

### 41. 配置中心

**答案：**
将数据库地址、服务地址、开关等配置集中管理，实现动态配置和环境隔离。

**技术：** Nacos、Apollo、Consul、K8s ConfigMap/Secret。

### 42. 服务治理

**答案：**
对服务的注册发现、配置、路由、负载均衡、限流、熔断、监控、发布等进行统一管理。

### 43. 日志

**答案：** 记录服务运行状态和错误信息，是故障排查的基础。

**重点：** 结构化日志、Trace ID、集中采集。

### 44. Metrics

**答案：** 用指标描述系统运行状态，例如
QPS、RT、错误率、CPU、内存、连接数。

**技术：** Prometheus。

### 45. Trace / 链路追踪

**答案：** 给一次请求分配 Trace
ID，记录跨服务调用链，定位慢请求和故障服务。

**技术：** OpenTelemetry、Jaeger、SkyWalking。

### 46. 监控告警

**答案：** 监控关键业务和基础设施指标，超过阈值后告警。

**重点：** 可用性、延迟、错误率、资源利用率。

### 47. 灰度发布

**答案：** 先让少量用户或流量使用新版本，观察指标正常后逐步扩大。

### 48. 蓝绿发布

**答案：**
同时维护旧环境和新环境，通过流量切换完成发布，回滚速度快，但资源成本高。

### 49. 滚动发布

**答案：** 分批替换旧实例，逐渐完成版本升级，资源成本较低。

### 50. CI/CD

**答案：** 自动完成代码构建、测试、镜像制作和部署，减少人工操作。

**流程：** Git → Build → Test → Image → Deploy → Verify。

------------------------------------------------------------------------

## 七、部署与 Kubernetes

### 51. VM 部署

**答案：**
每个服务部署在独立或隔离的虚拟机中，隔离性较好，但资源利用率和部署效率相对较低。

### 52. Container

**答案：** 容器通过镜像标准化运行环境，相比 VM 更轻量，启动更快。

### 53. Docker

**答案：** Docker
提供容器镜像构建和运行能力，解决应用及依赖环境一致性问题。

### 54. Kubernetes

**答案：** Kubernetes
是容器编排平台，负责容器部署、调度、服务发现、扩缩容和故障恢复。

### 55. Pod

**答案：** Pod 是 K8s 最小调度和部署单元，一个 Pod
可以包含一个或多个紧密协作的容器。

### 56. Deployment

**答案：** Deployment 管理无状态应用的 Pod 副本，并支持滚动升级和回滚。

### 57. Service

**答案：** Service 为一组 Pod
提供稳定访问入口，并承担服务发现和负载均衡。

### 58. Ingress

**答案：** Ingress 管理外部 HTTP/HTTPS 请求到集群内部 Service 的路由。

### 59. K8s Service Discovery

**答案：** K8s 通过 Service + DNS
提供稳定的服务发现能力，客户端不需要知道具体 Pod IP。

### 60. K8s 负载均衡

**答案：** Service 将请求分发到后端 Pod；集群外部还可以通过
LoadBalancer、Ingress 等方式接入。

### 61. K8s 调度

**答案：** Scheduler 根据
CPU、Memory、节点标签、亲和性、污点等条件选择合适节点运行 Pod。

### 62. 自动扩缩容

**答案：** 根据 CPU、内存或业务指标动态调整 Pod 副本数。

**技术：** HPA。

### 63. 故障自动恢复

**答案：** Pod 异常退出后，K8s
可以自动重启或重新创建；节点故障时可以重新调度。

### 64. 资源隔离

**答案：** 通过 Requests/Limits、Namespace、Quota
等限制资源使用，避免单个服务影响其他服务。

## 八、架构演进与大数据

### 65. 微服务架构演进

**答案：**
架构不是一次设计完成，而是随着业务规模和基础设施成熟度逐步演进。

### 66. VM → 自研 Registry → F5 → Container → K8s

**答案：** 可以把它理解为基础设施能力逐步下沉：

``` text
业务服务拆分
    ↓
VM 独立部署
    ↓
自研 Registry / 服务发现
    ↓
F5 / 负载均衡
    ↓
Docker / Container
    ↓
Kubernetes
    ↓
自动调度 / 扩缩容 / 故障恢复
```

**面试表达：** 重点不是罗列技术，而是说明为什么每一步需要演进。

### 67. 微服务 + Kafka

**答案：** 微服务负责业务能力，Kafka 负责异步事件传递。典型模式是：

``` text
Service A
   ↓
Kafka
   ↓
Service B / C / D
```

实现服务解耦、异步处理和削峰。

### 68. 微服务 + 大数据

**答案：** 微服务负责在线业务，Kafka 负责数据流转，Flink/Spark
负责计算，ClickHouse 等负责分析查询。

``` text
业务服务
   ↓
Kafka
   ↓
实时/离线计算
   ↓
OLAP / 数据湖
   ↓
查询分析
```

### 69. OLTP vs OLAP

**答案：** - OLTP：在线事务处理，关注高并发、低延迟、事务一致性，例如
MySQL。 - OLAP：在线分析处理，关注大规模数据扫描和聚合，例如
ClickHouse。

### 70. 流处理 vs 批处理

**答案：** - 流处理：数据到达后立即计算，低延迟。 -
批处理：积累一批数据后统一计算，适合离线分析。

**技术：** Flink / Spark。

### 71. 海量数据分区

**答案：** 将数据按时间、业务维度或 Hash
等方式划分，减少单分区数据量并提高并行处理能力。

### 72. 数据并行计算

**答案：** 将数据拆成多个分片，由多个计算节点同时处理，再汇总结果。

**核心：** Partition + Parallelism。

### 73. 数据一致性与可靠性

**答案：** 需要从数据库、MQ、计算任务三个层面考虑：

``` text
数据库：事务 / 副本
MQ：ACK / Retry / Offset
计算：Checkpoint / Retry
```

## 九、故障排查与架构设计

### 74. 微服务故障排查

**答案：** 按请求链路逐层定位：

``` text
客户端
 ↓
Gateway / F5
 ↓
服务实例
 ↓
RPC / HTTP
 ↓
Redis / MySQL
 ↓
Kafka / 下游服务
```

结合 **日志 + Metrics + Trace** 判断问题发生在哪里。

### 75. 架构方案权衡

**答案：**
架构设计没有绝对最优方案，要从性能、可靠性、复杂度、成本、扩展性、团队能力等维度权衡。

### 76. 为什么选择这个方案

**答案模板：**

> 当时首先分析业务规模、性能要求、可靠性要求和团队能力，然后比较几种方案。最终选择这个方案，是因为它在当时的业务规模和基础设施条件下综合成本最低，同时能够满足扩展需求。

### 77. 方案的缺点是什么

**答案模板：**

> 这个方案并不是完美的，主要问题是增加了分布式系统复杂度，例如服务治理、网络调用和故障排查成本。如果业务规模较小，我会优先考虑更简单的单体方案。

### 78. 如果重新设计怎么做

**答案模板：**

> 如果现在重新设计，我会保留原有的业务边界，但基础设施尽量使用成熟组件，减少自研；同时加强可观测性、自动化部署、服务治理和故障恢复能力。核心原则是业务复杂度和基础设施复杂度分离。

------------------------------------------------------------------------

# 十、面试最终复习主线

把 78 个问题最终压缩成这条主线：

``` text
1. 为什么拆？
   ↓
2. 怎么拆？——业务边界 / 服务粒度
   ↓
3. 怎么调用？——HTTP / RPC / MQ
   ↓
4. 服务在哪里？——Registry / Discovery
   ↓
5. 请求发给谁？——F5 / Nginx / Gateway / LB
   ↓
6. 出故障怎么办？——Timeout / Retry / Circuit Breaker / Degrade
   ↓
7. 数据怎么保证？——事务 / 一致性 / 幂等
   ↓
8. 怎么部署？——VM → Docker → K8s
   ↓
9. 怎么治理？——Config / Metrics / Trace / CI/CD
   ↓
10. 数据量大怎么办？——Kafka → Flink/Spark → ClickHouse
```

## 架构师面试最重要的 10 个问题

1.  **为什么要拆成微服务？**
2.  **服务边界怎么确定？**
3.  **服务之间如何通信？**
4.  **服务注册发现怎么做？**
5.  **负载均衡怎么做？**
6.  **如何解决超时、重试、熔断、雪崩？**
7.  **分布式事务和最终一致性怎么解决？**
8.  **VM → Docker → K8s 为什么演进？**
