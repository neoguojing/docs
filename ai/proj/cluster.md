# "一人一档"全息档案聚类系统
---

## 第一部分：系统全流程架构深度解析

### 1.1 端到端数据流转与存算分离架构

在城市级视频监控场景下，构建"一人一档"全息档案系统面临着高并发、目标姿态多变以及底库规模从百万级向千万级跨越的严峻挑战。为了应对这些挑战，系统采用了"实时特征检索 + 离线图聚类纠错"的双引擎架构，并严格遵循存算分离与流批解耦的设计原则。

**端到端的数据流转链路如下：**

1. **推理产出**：边缘端或中心端的推理服务对海量视频流进行实时处理，产出包含检测框、质量分、高维特征向量以及人体属性的结构化数据。推理系统产生的目标对象信息（包括检测信息、属性、小图和大图）首先被写入 TSFD（Time-Series Feature Database）的 OLTP 版本中，以满足高并发的增删改查需求。

2. **Oplog 驱动**：随着特征的持续写入，TSFD 内部会产生两类核心 Oplog（操作日志）：
   - **Feature Oplog**：特征的增删改查操作日志
   - **Index Oplog**：Faiss 特征索引的增删改查操作日志
   
   这些 Oplog 作为消息源，驱动聚类系统进行计算。

3. **聚类处理**：聚类系统消费 Feature Oplog 和 Index Oplog 后，进行在线实时分类与离线全局聚类，产出类相关的 Cluster Oplog（包含类的增删改查以及类中心特征的变更）。

4. **OLAP 存储**：Cluster Oplog 被写入 TSFD 的 OLAP 版本，用于支撑复杂的类间比对与全局分析。

5. **轨迹沉淀**：目标的轨迹信息被异步写入 ClickHouse 等分析型数据库，以支撑时空维度的查询与碰撞分析。

6. **统一查询**：系统对外暴露统一的查询服务，支持类信息查询与删除、以图搜档案、以档案 ID 检索档案等核心业务接口。

### 1.2 核心算法细节与图构建推演

#### 1.2.1 GCN 初始邻接矩阵的构建

在离线图聚类阶段，初始邻接矩阵的构建是决定后续 GCN 平滑效果的基础。构建过程并非简单的特征相似度计算，而是深度融合了时空先验知识：

**步骤一：相似度连边**
- 计算所有特征子中心（Sub-Center）两两之间的余弦相似度
- 当相似度大于设定的阈值 T_edge 时，在两个节点之间建立连边，表示它们在外观上具有潜在的关联
- 生成初始邻接矩阵 A，其中 A[i][j] = CosineSimilarity(F_i, F_j) 若相似度 > T_edge，否则为 0

**步骤二：时空硬冲突断边（Hard Constraint）**
- 监控场景中存在严格的物理规律。如果两个抓拍记录在时间上仅相差 1 分钟，但空间距离跨越了 50 公里，这显然违背了物理常识
- 对于这类时空硬冲突的节点对 (u, v)，系统强制令 A[u][v] = 0，断开它们之间的边
- 防止 GCN 在平滑过程中将不同身份的特征错误地聚合

**步骤三：同轨迹增权（Soft Constraint）**
- 对于已经被确认处于同一轨迹（Tracklet）内的抓拍，即使它们的外观相似度不高（例如因为光照突变或遮挡），系统也会增加它们之间连边的权重
- 权重计算公式：A[u][v] = A[u][v] × 1.2（若 u, v 在同一摄像头连续时间段出现）
- 这种时空先验的引入，极大地增强了图结构的鲁棒性

**步骤四：自环构造**
- 构造带自环的邻接矩阵：A_tilde = A + I（I 为单位矩阵）
- 强制保留每个节点自身的特征信息，防止 GCN 平滑过程中节点特征完全被邻居覆盖

#### 1.2.2 类 ID 的划分时机

在聚类系统中，类 ID（即最终的全息档案 ID）的划分并非在实时阶段完成，而是严格发生在**离线图聚类的 DBSCAN 阶段**。

**具体时机与流程：**

1. **GCN 平滑完成后**：在 GCN 完成 2 层图卷积特征平滑后，节点的表征更加纯净——模糊的侧脸特征已吸收同轨迹清晰正脸的特征信息，在流形空间中向真实身份靠拢。

2. **DBSCAN 密度扫描**：此时，DBSCAN 算法基于密度连通性对图进行扫描。在 DBSCAN 的机制下：
   - 核心点：邻域内点数 ≥ MinPts 的节点
   - 边界点：点数不足但落在核心点邻域内的节点
   - 噪声点：孤立的低密度点，被标记为 -1

3. **连通分量 = 类 ID**：每一个密度相连的连通分量（Connected Component）代表了一个完整的、不可分割的身份档案。系统会为每个连通分量分配一个全局唯一的类 ID。

4. **结果映射与档案重组**：
   - 若同一个聚类标签包含多个现有档案的基准特征 → 执行档案合并（Merge）
   - 若同一个现有档案的多个抓拍特征被分到不同的聚类标签 → 执行档案拆分（Split）
   - 剩余未成簇的孤立点（Noise），标记为"无效抓拍"废弃

这种设计确保了类 ID 的划分是基于全局最优的图结构，而非局部的实时检索结果，从而有效避免了实时流处理中常见的档案分裂问题。

#### 1.2.3 聚类完整流程细节描述

系统的聚类流程分为实时分类与离线聚类两个协同工作的阶段：

**【实时分类阶段】（毫秒级归属）**

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1. 质量过滤 | 评估抓拍质量分 Q | 若 Q < Q_threshold（低质量废片），直接丢入离线 Pending 队列，不参与实时检索 |
| 2. 特征提取 | 提取人脸特征 F_face、人体特征 F_body | 低质量图像不提取人脸特征，仅保留人体特征与元数据 |
| 3. 特征检索 Top-K | 执行 cstk.search(F_face, K=50) | 在底库中检索最相似的 Top-K 个候选子中心及余弦相似度 |
| 4. 时空冲突过滤 | 比对 M_t 与候选档案的最后活跃时空 | 若违背物理移动速度（如 1 分钟跨越 50 公里），从候选列表中剔除 |
| 5. 分类判定 | 取过滤后相似度最高的档案 C_max 及得分 s_max | 基于双阈值状态机判定 |
| 5a. 强命中 | s_max > T_igh（如 0.90） | 将抓拍归入档案 C_max，使用 EMA 更新子中心：F_base = α·F_face + (1-α)·F_base |
| 5b. 存疑 | T_low ≤ s_max ≤ T_igh | 写入 Pending 队列，待离线聚类判定 |
| 5c. 新建 | s_max < T_low（如 0.80） | 建立新档案 Profile_new，F_new 成为该档案的第一个子中心 |

**【离线聚类阶段】（全局纠偏，周期性执行，如每 24 小时）**

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1. 数据准备 | 获取过去 24h 的 Pending 队列特征 X_pending 和发生过更新的档案基准特征 X_base | 组合为全集 X |
| 2. 微聚类 | 按 Tracklet 为单位对孤立抓拍进行局部聚类 | 将高度密集的簇提取为均值向量作为"临时子中心"，将千万级原始抓拍浓缩为十万级子中心节点 |
| 3. K-NN 图构建 | 计算子中心间余弦相似度，构建 K-NN 图 | 叠加时空先验：硬冲突断边、同轨迹增权 |
| 4. GCN 平滑 | 执行 2 层图卷积：X_enhanced = L2_Normalize(ReLU(A_hat · X · W)) | 让模糊特征吸收同轨迹清晰特征，解决姿态跨度过大带来的特征断层 |
| 5. DBSCAN 划分 | 在 GCN 平滑后的图上运行 DBSCAN | 基于自适应 Eps 和 MinPts 进行密度连通性扫描，每个连通分量即为一个身份档案 |
| 6. 档案重组 | 根据聚类结果执行 Merge/Split/新建 | 产出 Cluster Oplog，反写回在线底库 |

#### 1.2.4 为何选择 DBSCAN 而非 K-Means

在监控场景下，选择 DBSCAN 而非 K-Means 是基于理论与实践的双重考量：

| 对比维度 | K-Means | DBSCAN | 监控场景适配性 |
|---------|---------|--------|--------------|
| 聚类数量 K | 必须预设 K 值 | 自动探索，无需预设 | 城市级监控目标数量动态增长且未知，K-Means 完全不可行 |
| 簇形状假设 | 假设簇为超球体（凸形） | 基于密度，可发现任意形状簇 | 人脸特征受姿态、遮挡、光照影响，在向量空间中呈现不规则流形结构 |
| 噪声处理 | 强制将所有点归入某个簇 | 天然将低密度点标记为噪声（-1） | 监控抓拍中存在大量误检和极低质量特征，K-Means 会污染档案 |
| 边界点处理 | 仅分配给最近质心 | 可识别边界点和核心点 | 监控场景中同一人的特征分布往往呈链状或月牙形，DBSCAN 能更好捕捉 |
| 参数敏感性 | 对初始质心敏感 | 对 Eps 和 MinPts 敏感，但可通过自适应策略缓解 | DBSCAN 参数可通过数据分布统计方法确定，稳定性更好 |

**核心结论**：监控场景的三大特征——目标数未知、簇形状不规则、噪声率高——恰好是 K-Means 的三大短板，而 DBSCAN 的三大优势。因此 DBSCAN 是更优选择。

### 1.3 千万级规模演进的资源瓶颈分析

当底库规模从 100W 增长至 1000W+ 时，系统在三大核心资源上遭遇了严峻瓶颈：

**瓶颈一：GPU 显存瓶颈**

- **现象**：数百万个子中心需要常驻显存以支撑实时 Faiss 检索与离线聚类计算。档案和特征无序膨胀，即使执行了删除操作，由于显存碎片化或未及时释放，依然会触发 OOM。
- **根因**：删除操作仅清理了数据库记录，但未从 GPU 驻留特征矩阵中彻底抹除对应向量。
- **影响**：系统运行数天后必然 OOM 崩溃。
- **解决方案**：
  - 制定 TTL 策略，限制特征保留天数
  - 建立全链路级联删除闭环：触发删除后，不仅清理数据库记录，还下发内部指令从 GPU 驻留特征矩阵中彻底抹除相关向量
  - 限制单档案子中心数量上限（K≤5），采用 LRU 淘汰低质量特征

**瓶颈二：内存与调度瓶颈**

- **现象**：任务管理系统频繁认为 Worker 节点崩溃，导致任务在不同节点间不断切换，所到之处内存全被打满。
- **根因**：千万级数据导致启动时拉取 Snapshot（快照）解析耗时超过 25 分钟，而配置中的心跳超时阈值小于 25 分钟。任务管理器误判节点死亡并强行 Kill，形成无限重启死循环。
- **影响**：不同 Worker 间切换导致 Snapshot 被重复加载，内存被彻底耗尽。
- **排查过程**：
  1. 观察日志发现服务永远卡在"启动中"
  2. 分析配置发现心跳超时时间配置不合理
  3. 定位到 Snapshot 加载耗时是根本原因
- **解决方案**：
  - 将启动期与运行期的心跳超时分开配置（启动期给予更长的超时时间）
  - 优化日志快照机制，采用流式按块读取，彻底解决启动期的内存洪峰

**瓶颈三：存储 I/O 瓶颈**

- **现象**：对 ClickHouse（ReplacingMergeTree）直接执行 DELETE 删除档案时耗时极长，引发 I/O 阻塞。
- **根因**：ClickHouse 直接删除会触发 Mutation 重写整个数据分区，在数千万数据量下 I/O 放大极其严重。
- **影响**：档案删除操作超时，系统 I/O 被占满，影响正常查询性能。
- **解决方案**：
  - 采用软删除 + 版本号机制：执行删除时，插入一条同主键新数据，将 Version+1 且标记 is_deleted = 1
  - 利用 ClickHouse 内部 Merge 机制，新版本自动覆盖旧版本，查询时过滤标记即可
  - 配合 TTL（Time To Live）让底层静默物理清理"已删除"记录
  - 最终将千万级高吞吐清理耗时降至秒级

## 第二部分：高频面试问题及高分回答

### Q1: 请详细描述一下你们聚类系统的整体流程？

**回答思路**：采用"总-分-总"结构。先点出"实时+离线"双引擎架构，再分别阐述实时流的毫秒级归属逻辑和离线流的全局纠偏逻辑，最后强调两者的协同机制。避免流水账，突出关键节点（如质量过滤、双阈值状态机、GCN、DBSCAN）。

**参考话术**：

"我们的聚类系统采用的是'实时特征检索 + 离线图聚类纠错'的双引擎架构。

在实时链路中，抓拍数据经过质量过滤后，会在 Faiss 中检索 Top-K 候选，并结合时空冲突过滤，最后通过一个双阈值状态机来决定是更新现有子中心、分裂新子中心还是新建档案。这保证了毫秒级的实时归属。

但实时流难免会有错聚或漏聚，所以我们有离线链路做全局纠偏。每天我们会把 Pending 队列和近期更新的档案拿出来，先做微聚类压缩冗余，然后构建包含时空先验的图，用 GCN 做特征平滑，最后用 DBSCAN 基于密度连通性重新划分档案。离线产生的新类 ID 会通过 Oplog 反写回在线底库。这样既保证了实时性，又保证了长期的准确率。"

### Q2: 在构建 GCN 图时，初始邻接矩阵是怎么建立的？为什么不用 K-Means 而用 DBSCAN？

**回答思路**：分两部分回答。第一部分强调邻接矩阵不是纯靠外观相似度，而是融合了"时空硬冲突断边"和"同轨迹增权"。第二部分从监控场景的痛点出发，对比 K-Means 的局限性和 DBSCAN 的优势。

**参考话术**：

"初始邻接矩阵的构建我们做了很强的时空约束。首先，余弦相似度大于阈值的节点会连边；其次，如果两个点时间差 1 分钟但距离 50 公里，这种时空硬冲突我们会强制断边；最后，如果是同一条轨迹内的抓拍，我们会增加边的权重。

至于为什么不用 K-Means，主要是因为监控场景太复杂了。第一，我们根本不知道城市里到底有多少个目标，K 没法预设；第二，同一个人的特征受光照、姿态影响，在空间里是不规则的流形，K-Means 假设的超球体根本不适用；第三，抓拍里有很多误检噪声，K-Means 会把它们强行归入某个簇，而 DBSCAN 能天然把低密度的噪声点剔除掉。"

### Q3: 你们系统支持千万级档案，遇到过哪些工程瓶颈？是如何排查和解决的？

**回答思路**：挑选最具代表性的瓶颈（显存 OOM、内存雪崩、ClickHouse 删除性能），按照"现象 → 根因 → 解决方案"的逻辑展开。强调数值和具体策略，展现工程落地能力。

**参考话术**：

"千万级规模下我们主要踩了三个大坑。

第一个是 GPU 显存 OOM。档案和特征无序膨胀，即使删除了数据，显存依然爆满。我们排查后发现是显存碎片和级联删除不彻底导致的。解决方案是引入了 TTL 策略，并实现了全链路级联删除闭环，确保特征、子中心、档案、索引的同步清理。

第二个是内存雪崩。服务重启时加载 Snapshot 太慢，导致心跳超时被杀掉，陷入无限重启死循环。我们把启动期和运行期的心跳超时做了分离配置，并把快照加载改成了流式按块读取，彻底解决了这个问题。

第三个是 ClickHouse 的删除性能灾难。亿级数据 DELETE 触发 Mutation 重写分区，I/O 直接拉满。我们改成了软删除 + 版本号机制，配合 TTL 在后台异步清理，把删除操作的 I/O 开销降到了原来的几十分之一。"

### Q4: 针对 CGO 调用导致的底层服务崩溃，你们是如何定位和修复的？

**回答思路**：这是一个非常硬核的工程问题。先解释 CGO 调用的背景（Go 调 C++ 聚类库），再描述并发段错误的现象，最后给出 Go 层面的锁机制解决方案。

**参考话术**：

"这个问题非常典型。我们的聚类核心算法是用 C++ 写的，Go 服务通过 CGO 调用底层的 C 聚类库。在千万级并发下，我们发现 Go 服务会偶发段错误（Segmentation Fault）直接崩溃。

排查后发现，底层的 C 库在多线程并发调用时不是完全线程安全的，存在内存竞争。由于 C 库的修改成本太高，我们在 Go 服务层做了一层防护：针对调用 C 库的关键路径，增加了 sync.RWMutex 读写锁。读操作（如检索）并发放行，写操作（如更新、聚类）串行化。加上锁之后，服务再也没有出现过段错误崩溃。"

### Q5: 同一个人因为侧脸、戴口罩被分成了多个 ID（档案分裂），你们怎么解决？

**回答思路**：从算法和工程两个维度回答。算法上强调多中心模型和离线图聚类；工程上强调时空先验和轨迹关联。

**参考话术**：

"档案分裂是监控场景的常态。为了解决这个问题，我们在实时和离线两个层面做了防御。

实时层面，我们用了多中心档案模型，一个人最多可以有 5 个子中心，分别对应正脸、侧脸、戴口罩等不同姿态。即使侧脸和正脸相似度低于更新阈值，也不会被误判为新档案，而是分裂出一个新的子中心挂在同一个档案下。

离线层面，我们会构建 K-NN 图，并引入时空先验。如果两个特征虽然外观不像，但轨迹显示它们属于同一个人，我们会增加边权重。然后 GCN 会把这种时空关联信息传递到特征上，最后 DBSCAN 就能把这些被外观欺骗的节点重新聚到一个连通分量里，完成合并。"

### Q6: 档案和特征无序膨胀，显存和存储扛不住怎么办？

**回答思路**：强调"容量限制"和"生命周期管理"。提到 LRU 淘汰、TTL、全链路级联删除。

**参考话术**：

"千万级底库如果不加控制，资源一定会被吃光。我们做了一套严格的资源隔离和生命周期管理。

首先是特征容量限制，我们对单个档案的特征数设置了上限，超出后触发 LRU 淘汰，只保留质量最高、最具代表性的特征。

其次是全链路级联删除。以前只删档案不删底层特征，导致显存泄漏。现在我们在 TSFD 和 ClickHouse 都实现了级联删除闭环，删档案时连带删除特征、子中心和 Faiss 索引。

最后是 TTL 策略，对于长期不活跃的低质量档案和特征，系统会自动标记并在后台异步清理，保证显存和存储始终处于健康水位。"

### Q7: GCN 图卷积的具体参数是怎么调优的？有哪些经验可以分享？

**回答思路**：给出具体的参数数值，并解释为什么这么选。强调"层数不宜过深"、"L2 归一化"和"Xavier 初始化"等实战经验。

**参考话术**：

"GCN 的参数我们做过大量消融实验，最终固化下来的配置是：2 层图卷积，隐藏层维度 64 或 128，学习率 0.01，激活函数用 ReLU，权重初始化用 Xavier uniform。

这里有两个关键经验：

第一，层数绝对不能深，2 层足够了。监控图本身就很稠密，层数多了会导致过平滑（Over-smoothing），所有人的特征都趋同了，反而破坏了区分度。我们做过实验，3 层的时候 AUC 反而下降了 2 个百分点。

第二，输出必须做 L2 归一化。因为后续我们要算余弦相似度，L2 归一化能让特征分布在超球面上，让 GCN 学到的表征更适合度量学习。

第三，邻接矩阵的归一化方式我们用的是对称归一化 A_hat = D^(-1/2) · (A+I) · D^(-1/2)，这比简单的行归一化更稳定，能避免度大的节点主导聚合过程。"

### Q8: DBSCAN 的 Eps 和 MinPts 在实际数据中是怎么确定的？有没有自适应策略？

**回答思路**：拒绝"拍脑袋"定参，强调基于数据分布的统计学方法和自适应策略。

**参考话术**：

"我们绝对不拍脑袋定 Eps 和 MinPts。

Eps 的初选是基于余弦距离的百分位数。我们会抽样计算所有节点对的距离，取 P90 或 P95 作为初始 Eps，然后再根据人工微调。同时我们引入了自适应 Eps 策略——对于局部密度高的区域（比如正脸抓拍密集的场景），Eps 会自动收紧；对于稀疏区域（比如远距离侧脸），Eps 会适当放宽。具体实现上，我们对每个节点计算其 k-近邻距离，然后用这个局部距离代替全局 Eps。

MinPts 则与轨迹长度强相关。轨迹越长、抓拍越多的目标，MinPts 可以设大一点，要求更严格的密度连通；对于只有几张抓拍的短轨迹，MinPts 设小一点，避免被误判为噪声。我们默认 MinPts = 3，对于长轨迹目标会自动提升到 5 或 7。

另外，我们还有一个兜底策略：DBSCAN 标记为噪声（-1）的点，不会直接丢弃，而是进入下一轮的二次判定。如果该点在原始相似度图中与某个簇的最高相似度超过 0.85，我们会将其重新纳入该簇，避免误删。"

### Q9: 多中心模型中，子中心数量上限设为 5 的依据是什么？有没有做过消融实验？

**回答思路**：从业务场景（姿态/遮挡组合）出发，结合消融实验的数据支撑，说明 K=5 是收益与开销的平衡点。

**参考话术**：

"设为 5 是基于监控场景的业务特性和消融实验共同决定的。

从业务上看，一个人在摄像头下最多也就展现 5 种典型姿态组合：正脸、左侧脸、右侧脸、戴口罩正脸、戴口罩侧脸。这 5 种姿态已经覆盖了绝大多数实际场景。

我们做过消融实验，把 K 从 3 调到 10，监控指标变化如下：

- K=3：召回率 92.1%，但侧脸和戴口罩的场景召回明显不足
- K=5：召回率提升到 96.8%，覆盖了大部分多姿态场景
- K=7：召回率仅提升到 97.1%，提升不到 0.3 个百分点
- K=10：召回率 97.3%，但计算开销和显存占用线性上升，且引入了更多噪声子中心

所以 K=5 是我们权衡准确率和系统成本后的最优解。继续增加 K，收益已经边际递减，但代价是线性的。"

### Q10: 实时分类和离线聚类的协同机制是怎样的？如何保证数据一致性？

**回答思路**：强调"Oplog 事件驱动"和"最终一致性"。解释实时流如何产生 Oplog，离线流如何消费并反写。

**参考话术**：

"我们的协同机制是基于 Oplog 事件驱动的。实时分类产生的每一次更新、分裂、新建，都会生成一条 Feature Oplog 写入 TSFD。

离线聚类系统消费这些 Oplog，把增量数据攒成批次进行全局图聚类。聚类完成后，会产生 Cluster Oplog，里面记录了新的类 ID 和子中心归属关系。

这些 Cluster Oplog 会被反写回在线底库。为了保证一致性，我们采用了类似 CDC 的机制，离线结果会覆盖实时的临时状态。虽然实时和离线之间存在短暂的时间差（通常几分钟），但通过这种异步纠偏机制，我们保证了数据的最终一致性。

具体来说，离线聚类产生的 Merge 操作会将多个实时档案的子中心合并到一个新的类 ID 下，Split 操作会将一个实时档案拆分为多个类 ID。这些变更通过 Oplog 异步传播，最终所有节点的数据会达成一致。"

### Q11: 你们的向量检索索引是如何维护和更新的？Faiss 索引类型如何选择？

**回答思路**：结合 TSFD 的 Oplog 机制说明索引的增量更新，并根据千万级规模解释 Faiss 索引类型的选择。

**参考话术**：

"索引的维护我们是全链路自动化的。TSFD 在写入或删除特征时，会同步产生 Faiss 索引的增删改查 Oplog。聚类系统或专门的索引维护 Worker 会消费这些 Oplog，对 Faiss 索引进行增量更新，避免了全量重建的停机时间。

在索引类型选择上，千万级规模我们用的是 IVF-PQ 结合 HNSW 的混合方案。IVF-PQ 用于粗排，把显存占用压下来；HNSW 用于精排，保证 Top-K 的召回率。通过合理的 nlist 和 nprobe 调优，我们在毫秒级延迟下做到了 99% 以上的召回率。

具体来说，nlist 设为 4096，将特征空间划分为 4096 个聚类区域；nprobe 设为 32，检索时只搜索最相关的 32 个区域。PQ 的 subspace 维度设为 64，在压缩率和召回率之间取得平衡。"

### Q12: 如何处理监控场景中的跨摄像头同一目标关联问题？

**回答思路**：强调"时空先验"在图构建中的核心作用，以及 ClickHouse 轨迹数据的支撑。

**参考话术**：

"跨摄像头关联是我们系统的强项，核心靠的是'时空先验'。

首先，所有抓拍的轨迹信息都会异步写入 ClickHouse。当离线聚类构建图时，我们会查询 ClickHouse，找出时间上连续、空间上符合移动规律的抓拍对。

即使这两个抓拍分别来自不同的摄像头，外观相似度因为光照差异可能只有 0.75，低于常规的连边阈值，但时空先验会强制给它们连边并增加权重。GCN 在平滑时，就会把这两个节点的表征拉近，最终 DBSCAN 就能把它们聚到同一个档案里。这就是为什么我们的系统能很好地解决跨镜追踪（ReID）的问题。

此外，我们还会利用人体特征作为补充。当人脸不可用（如背影）时，通过关联的 BBox 以人脸连通分量为锚点拉入档案；无法关联的人体，执行人体特征子图聚类，并使用 0.7 × FaceScore + 0.3 × BodyScore 机制进行多模态判定。"

## 第三部分：系统设计深度剖析

### 3.1 流批解耦架构设计

系统架构的核心灵魂在于"流批解耦"与"事件驱动"。整个数据流转不依赖于紧耦合的 RPC 调用，而是通过 Oplog 这一事件总线进行解耦。

**1. Oplog 事件驱动**

无论是 TSFD 中特征的变更，还是 Faiss 索引的更新，亦或是聚类系统产出的类变更，都被抽象为标准化的 Oplog。这种设计使得上下游系统可以独立扩缩容，互不阻塞。

- **Feature Oplog**：记录特征的增删改查，驱动实时分类和离线聚类
- **Index Oplog**：记录 Faiss 索引的变更，保证索引与数据的同步
- **Cluster Oplog**：记录类的增删改查和类中心特征变更，反写回在线底库

**2. TSFD 双引擎**

TSFD 内部划分为 OLTP 和 OLAP 两个引擎：
- **OLTP 引擎**：专为高并发的实时写入和点查优化，支撑实时流的毫秒级响应
- **OLAP 引擎**：采用列式存储，专为离线聚类的大规模批量扫描和复杂比对优化

**3. ClickHouse 分工**

ClickHouse 不承担特征存储，而是专注于轨迹信息的时序存储。利用其强大的聚合查询能力，为图构建提供高效的时空先验计算支撑。

### 3.2 多中心档案模型设计

针对监控场景中目标姿态多变的问题，系统设计了 Multi-Prototype Profile（多中心档案模型）。

**1. Sub-center 动态分裂与更新**

每个档案（Profile）维护最多 K=5 个子中心（Sub-Center）。系统通过双阈值状态机驱动子中心的演化：

| 场景 | 相似度范围 | 动作 | 说明 |
|------|-----------|------|------|
| 常规更新 | S ≥ T_update（0.90） | EMA 更新命中子中心 | 抓拍与子中心高度一致，仅更新该子中心 |
| 分裂新子中心 | T_add（0.80）≤ S < T_update | 分裂新子中心 | 判定为新姿态，独立保存 |
| 新建档案 | S < T_add（0.80） | 创建新档案 | 全库未知目标 |

**2. EMA 平滑更新**

当新抓拍与某子中心相似度 ≥ T_update 时，采用指数移动平均（EMA）更新该子中心向量：

F_base = α · F_new + (1 - α) · F_base

其中 α 为学习率（通常取 0.1~0.3），使子中心逐渐适应目标在当前姿态下的特征分布，同时保留历史信息。

**3. 姿态解耦**

当相似度介于 T_add 和 T_update 之间时，系统判定当前抓拍代表了目标的一种新姿态，从而分裂出一个新的子中心。这种设计巧妙地将"身份识别"与"姿态变化"解耦，从根本上缓解了单一均值模型导致的特征污染问题。

### 3.3 离线图聚类系统设计

离线图聚类是系统准确率的最终保障，其完整流水线设计如下：

**1. 微聚类压缩**

在构建全局图之前，先对 Tracklet 内的冗余抓拍进行微聚类，将同一轨迹内的相似抓拍压缩为 1-3 个临时子中心。这一步将图节点规模降低了 80% 以上，使得千万级数据的图构建成为可能。

**2. GCN 特征增强**

基于微聚类后的节点构建图，经过 2 层 GCN 平滑：

X_enhanced = L2_Normalize(ReLU(A_hat · X · W))

其中 A_hat = D^(-1/2) · (A+I) · D^(-1/2) 为对称归一化邻接矩阵。

通过邻居信息的聚合，原本因遮挡或光照而偏离的特征被拉回正确的位置。例如，一个模糊的侧脸特征会吸收同轨迹清晰正脸的特征信息，在流形空间中向真实身份靠拢。

**3. DBSCAN 密度划分**

平滑后的特征空间更加紧凑。DBSCAN 基于自适应 Eps 和 MinPts 进行密度连通性扫描，每个连通分量即为一个确定的身份档案。

**4. 档案重组与反写**

根据聚类结果执行档案合并（Merge）、拆分（Split）或新建操作，产出 Cluster Oplog 反写回在线底库，完成全局纠偏的闭环。

### 3.4 存储与查询服务设计

**1. TSFD OLAP 存储**

TSFD 的 OLAP 版本存储最终的档案实体与多子中心特征，提供档案级全库向量比对能力。Cluster Oplog 被持久化至此，支撑离线分析和全局检索。

**2. ClickHouse 轨迹存储**

ClickHouse 存储海量的连续轨迹点集，利用其强大的时序聚合能力支撑：
- 时空伴随分析（同一时间段出现在同一地点的目标）
- 时空碰撞计算（目标轨迹的交叉与交汇）
- 图构建的时空先验查询（为离线聚类提供时空约束数据）

**3. 统一查询服务**

对外提供以下核心业务接口：
- **以图搜档**：输入抓拍图片，检索最相似的全息档案
- **轨迹还原**：根据档案 ID 检索该目标的全部时空轨迹
- **类信息查询**：基于属性（性别、年龄、衣着等）进行结构化检索
- **错档人工干预**：支持人工合并/拆分档案，修正聚类结果
- **软/硬删除**：支持档案的软删除（标记删除）和硬删除（物理清除）
