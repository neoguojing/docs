这份笔记精准捕捉了《数据密集型应用系统设计》（DDIA）中最核心的架构演进与数据工程理念。以下对这些知识点进行了系统性的重组与逻辑分类，并在关键概念处做了适当的补充和扩展，以便于建立更完整的知识体系。

---

## 一、 数据系统的基本组件与职责

现代应用极少由单一的数据存储满足所有需求，通常会组合多种不同的数据系统，每个系统承担特定的职责：

*   **数据库（Database）：** 存储数据，作为权威的持久化记录，以便日后能可靠地再次找到。
*   **缓存（Cache）：** 记住开销昂贵（如复杂计算或跨网络获取）的操作结果，以空间换时间，加快读取速度。
*   **搜索索引（Search Index）：** 允许用户按关键字检索数据，或进行复杂的多维过滤。
*   **流处理（Stream Processing）：** 面向无界数据，在事件和数据变更发生后**实时或准实时**地进行捕获和处理。
*   **批处理（Batch Processing）：** 面向有界数据，定期（如每天、每小时）处理累积的大批量数据。

---

## 二、 核心数据处理模式：OLTP 与 OLAP

随着数据量的增长和团队分工的细化，数据系统在处理模式上产生了明确的分化。

**事务（Transaction）**：在数据库语境中，指构成一个逻辑单元的一组读写操作，并非仅指金融交易。

| 属性 | 事务型系统（OLTP） | 分析型系统（OLAP） |
| :--- | :--- | :--- |
| **全称** | 联机事务处理（Online Transaction Processing） | 联机分析处理（Online Analytical Processing） |
| **主要使用者** | Web/移动应用的最终用户，或机器级验证服务 | 业务分析师、数据科学家、管理层 |
| **主要读取模式** | **点查询**（按主键读取单条或少量记录） | **大规模聚合**（扫描大量记录，计算统计值） |
| **主要写入模式** | 随机写入，创建、更新和删除单条记录 | **批量导入（ETL）**或持续的事件流写入 |
| **数据表示含义** | 数据的最新状态（当前时间点的快照） | 一段时间内发生的事件历史（强调不可变性） |
| **查询模式** | 由应用代码预先定义的固定查询集 | 探索性分析，分析师可按需编写任意复杂查询 |
| **数据集规模** | GB 至 TB 级别 | TB 至 PB 级别 |
| **代表机器行为** | 检查操作权限、扣减库存余额 | 检测欺诈行为、推荐系统特征提取、业务报表生成 |

### 团队角色与职责边界
*   **数据工程师（Data Engineer）：** 负责搭建“桥梁”。专注于数据基础设施的建设，解决数据管道（Pipeline）问题，将分布在各个 OLTP 系统中的数据安全、高效地集成到分析型系统中。
*   **分析工程师（Analytics Engineer）：** 介于数据工程和业务分析之间。负责在数仓内部对清洗后的数据进行建模和转换，构建宽表或星型模型，使其更易于数据科学家和业务人员使用。

## 三、 数据架构的演进：从孤岛到湖仓一体

直接在 OLTP 数据库上运行复杂的分析查询会导致严重的性能灾难（锁竞争、资源耗尽），同时面临**数据孤岛**（难以跨系统联合查询）和安全合规限制。为了解决这些问题，数据架构经历了几个阶段的演进：

1.  **数据仓库与 ETL：**
    *   通过 **ETL（提取-转换-加载）** 流程，将 OLTP 系统中的数据定期同步到专门优化的**数据仓库**。
    *   数据在入仓前会被强制转换为统一的模式（Schema-on-write），适合结构化分析（如星型或雪花型模式）。
2.  **数据湖（Data Lake）：**
    *   **痛点应对：** 随着非结构化数据和机器学习的兴起，传统数仓显得僵化且昂贵。
    *   **核心理念（寿司原则）：** “原始数据更好”。数据湖是一个集中式存储库，保存事务型系统的全量数据副本。它不强制规定数据模型或格式（Schema-on-read），消费者可以按需自行转换。
3.  **数据湖仓（Lakehouse）：**
    *   融合了数据湖的灵活性与数仓的事务性。在数据湖的底层文件（如 Parquet）之上，增加元数据管理层、ACID 事务支持和查询执行引擎。
4.  **HTAP（混合事务/分析处理）：**
    *   试图在同一个底层系统上同时支持高并发 OLTP 和复杂 OLAP，通过内存列存副本等技术，减少 ETL 延迟。

## 四、 系统的源头与云原生演进

### 1. 数据的来源分类
*   **权威记录系统（System of Record）：** 也称单一事实来源（Single Source of Truth）。它是数据的诞生地，保存数据的规范版本。
*   **衍生数据系统（Derived Data System）：** 数据是基于另一个系统的数据经过转换、聚合处理得来的。**缓存、搜索索引、数据仓库、物化视图均属于衍生系统。** 其核心特征是：即使数据丢失，也可以随时从源系统重新计算恢复。

### 2. 部署形态：自托管 vs 云原生
云原生架构专为利用云的弹性伸缩、存算分离和托管服务而设计。Serverless（无服务器）模式进一步将按量计费精细化到了代码执行时间，极大降低了运维心智负担。

| 类别 | 传统/自托管系统 | 现代云原生系统（按需扩展，存算分离） |
| :--- | :--- | :--- |
| **事务型/OLTP** | MySQL, PostgreSQL, MongoDB | AWS Aurora, Google Cloud Spanner |
| **分析型/OLAP** | Teradata, ClickHouse (自建), Spark | Snowflake, Google BigQuery, Databricks |

## 五、 分布式系统架构设计与衡量指标

把单一庞大的系统拆分为由多台机器通过网络通信协作的系统，即为**分布式系统**。微服务架构正是这种 SOA（面向服务架构）思想的现代演进。

系统设计的首要逻辑是：**存储和计算数据的价值，必须高于其成本。**

### 1. 非功能性需求的“三大支柱”
*   **可靠性（Reliability）：** 系统在面临硬件故障、软件错误或人为失误时，仍能继续正确运行。
*   **可伸缩性（Scalability）：** 当系统面临更大的负载（数据量、流量、复杂性）时，增加计算或存储资源能够显著、成比例地提高系统的处理能力。
*   **可维护性（Maintainability）：** 软件生命周期的大部分成本在于维护。
    *   *可运维性：* 良好的可观测性（监控、日志、链路追踪），便于团队保持系统平稳运行。
    *   *简单性：* 采用一致的抽象和**设计模式**，避免偶发复杂度，降低新人的认知负荷。
    *   *可演化性：* 系统易于修改，能够敏捷地适应未知的业务需求变化。

### 2. 性能与延迟的细微差别
DDIA 对时间的定义极其严谨，这是排查性能瓶颈的关键：

*   **服务时间（Service Time）：** 机器/服务真正用于处理用户请求所需的时间。
*   **排队延迟（Queueing Delay）：** 请求到达后处于等待状态的时间（如等待 CPU 分配、等待网络缓冲区）。高负载时，请求往往受阻于**队头阻塞（Head-of-line blocking）**。
*   **网络延迟（Latency）：** 泛指请求和响应在网络中传输、潜伏的时间（与处理无关）。
*   **响应时间（Response Time）：** = `服务时间` + `排队延迟` + `网络延迟`。这是**客户端实际感知到**的总耗时。

### 3. 指标衡量与尾部延迟
*   **吞吐量（Throughput）：** 系统每秒处理的请求数或数据量。由于排队效应，吞吐量逼近上限时，响应时间会急剧上升。
*   **百分位数：** 平均值掩盖了异常波动，**中位数（p50）**更能反映普通用户的体验。而**高分位数（如 p95, p99）**被称为**尾延迟（Tail Latencies）**。
*   **尾部延迟放大：** 在微服务架构（扇出机制）中，只要一条调用链路上有一个服务触发了尾延迟，整个客户端请求就会变慢。

## 六、 高并发下的稳定性与扩展方案

### 1. 流量风暴与亚稳态故障
当系统负载过高导致超时，客户端如果不加控制地重试，会引发**重试风暴（Retry Storm）**。即使实际用户流量下降，系统也会因为内部重试一直处于过载的“死亡螺旋”中，称为**亚稳态故障（Metastable Failure）**。

**防御手段：**
*   **客户端侧：** 指数退避（Exponential Backoff）加随机抖动（Jitter），熔断器（Circuit Breaker）暂停向故障节点发请求。
*   **服务端侧：** 负载卸除（Load Shedding，主动丢弃低优先级请求），背压（Backpressure，要求上游限流），以及使用令牌桶等算法进行限流。

### 2. 读写放大的权衡：物化视图
*   **扇出（Fan-out）：** 指单个输入请求需要放大为多少个后端请求，或需要更新多少条记录。
*   **物化（Materialization）：** 预先计算并持久化查询结果（如社交网络的时间线缓存）。它是经典的“空间换时间”和“写入成本换读取性能”的策略。

### 3. 硬件扩展架构的演进
*   **共享内存架构（Scale-up/垂直扩展）：** 多 CPU 共享同一块 RAM，受限于硬件物理瓶颈和指数级增长的成本。
*   **共享磁盘架构：** 独立的 CPU/RAM，通过高速网络共享磁盘阵列（多见于传统商用数据库）。
*   **无共享架构（Shared-nothing / 向外扩展 Scale-out）：** 现代分布式系统的主流。每个节点是独立的机器，拥有自己的 CPU、内存和磁盘，节点间通过普通网络协调。通过数据分片和副本机制，实现理论上的线性伸缩。

### 4. 应对复杂度的终极武器：抽象
在代码和架构层面，管理复杂度的最佳方式是**抽象（Abstraction）**。通过**领域驱动设计（DDD）**和合理的接口封装，将实现细节隐藏在干净的外观之下，是构建高可维护性系统的基石。


# 深入解析数据模型与查询语言

对于每层数据模型，其核心的关键问题始终是：**它是如何用低一层数据模型来“表示”的？**
一个模型可以用另一个模型来模拟（例如在关系型数据库中存储图数据），但结果往往十分笨拙。因此，针对不同的数据关联特征，选择合适的原生数据模型至关重要。

---

## 一、 关系模型与文档模型（The Great Debate）

关系模型与文档模型的对比，是数据库领域最经典的讨论之一。其核心分歧在于如何处理数据之间的关联以及模式的严格程度。

### 1. 核心概念对比
*   **关系模型（SQL）：** 数据被组织成“关系”（表 Table），每个关系由无序的“元组”（行 Row）构成。擅长处理多对一（N:1）和多对多（M:N）关系。
*   **文档模型（NoSQL）：** 数据通常以 JSON 等格式呈现。最初由 MongoDB 等推广，主打局部性（Local locality）和模式灵活性。适合一对多（1:N）的树状嵌套结构。

### 2. 阻抗不匹配与 ORM
*   **阻抗不匹配（Impedance Mismatch）：** 应用程序通常使用面向对象编程，而数据库使用关系模型，两者之间的脱节被称为“阻抗不匹配”。
*   **对象关系映射（ORM）：** 框架（如 ActiveRecord, Hibernate, MyBatis）应运而生，旨在减少内存对象与持久化关系数据之间转换的样板代码。但也常常因为屏蔽了底层 SQL 逻辑、导致复杂查询性能低下而遭到批评。

### 3. 规范化 vs 反规范化
实质上是在决定：**是存储 ID 还是存储文本字符串？**

| 属性 | 规范化（Normalization / 存 ID） | 反规范化（Denormalization / 存全量文本） |
| :--- | :--- | :--- |
| **数据冗余** | 无冗余，信息只存一份，其他地方用 ID 引用。 | 数据存在多个副本。 |
| **读取性能** | 较慢（往往需要多表 Join 连接）。 | 较快（信息自包含，无需跨表）。 |
| **写入性能** | 较快（只需更新一处）。 | 较慢（需更新所有副本，且占用更多空间）。 |
| **适用场景** | 多对一、多对多关系。 | 强局部性、一次性读取整个文档的场景。 |

### 4. 模式（Schema）管理的本质差异
非关系型数据模型常被误认为“没有模式”（Schemaless），但这并不准确。任何应用在读取数据时都隐含了对数据结构的假设。
*   **写时模式（Schema-on-write）：** 关系数据库的传统做法。模式是明确的，数据库在写入时强制校验，犹如强类型编程语言。
*   **读时模式（Schema-on-read）：** 文档数据库的典型做法。数据结构是隐含的，写入时不校验，只有在读取时应用程序才去解释数据，犹如动态类型语言。这使得应用更容易适应不断变化的需求。

---

## 二、 分析型数据模型：数据仓库架构

数据仓库通常采用关系模型，但为了满足复杂的分析聚合需求，衍生出了特定的建模惯例。

### 1. 星型模式（Star Schema）
*   **事实表（Fact Table）：** 位于中心，每一行代表一个发生的事件（如一笔订单、一次点击）。通常体积巨大。
*   **维度表（Dimension Table）：** 环绕在事实表周围，代表事件发生的对象、时间、地点、原因等属性。事实表通过外键指向维度表。
*   **视觉呈现：** 事实表在中央，连接周围维度表的线条形如星星的光芒。

### 2. 其他模式
*   **雪花模式（Snowflake Schema）：** 星型模式的变体，其中的维度表进一步被规范化，分解成子维度（例如：将“城市”维度进一步拆分出“国家”维度表）。
*   **一张大表（OBT - One Big Table）：** 极度反规范化的做法，牺牲存储空间换取极致的查询速度。

---

## 三、 图数据模型（Graph Data Models）

当数据中多对多（M:N）关系变得极为普遍且高度关联时，图数据模型是最佳选择。
*   **应用场景：** 社交网络、知识图谱、路径导航、推荐系统。
*   **主要流派：** 属性图（Property Graphs）和三元组存储（Triple Stores）。

### 1. 属性图模型 (Property Graph)
由 Neo4j、Memgraph 等实现。
*   **顶点（Vertex / Node）：** 包含唯一 ID、标签（类型）、属性（键值对）以及入边和出边集合。
*   **边（Edge / Relationship）：** 包含唯一 ID、起点（尾部顶点）、终点（头部顶点）、标签（关系类型）以及属性（键值对）。
> *注：用图遍历数据时，邻接表（Adjacency List）适合图遍历查询，而邻接矩阵（Adjacency Matrix）更适合机器学习计算。*

### 2. 三元组存储 (Triple Store) & 语义网
所有信息都以极简的 **（主语，谓语，宾语）** 三部分陈述来存储。
*   例如：`(Jim, 喜欢, 香蕉)`。
*   **RDF：** 专为语义网设计的数据模型。
*   **SPARQL：** 面向 RDF 的查询语言（读作 "sparkle"）。

### 3. 用 SQL 查询图数据的痛苦（为什么要用专门的图数据库？）
如果将图的顶点和边强行存在关系数据库（两张表）中，使用 SQL 查询长度未知的图遍历路径（如“找出既在美国出生又在欧洲居住的人”），需要使用复杂的 **递归公用表表达式（`WITH RECURSIVE`）**：

```sql
-- SQL 的笨拙实现：冗长、极难阅读、维护成本极高
WITH RECURSIVE
    in_usa(vertex_id) AS (
        SELECT vertex_id FROM vertices WHERE label = 'Location' AND properties->>'name' = 'United States'
      UNION
        SELECT edges.tail_vertex FROM edges JOIN in_usa ON edges.head_vertex = in_usa.vertex_id WHERE edges.label = 'within'
    ),
    -- ... (省略极其冗长的 in_europe, born_in_usa, lives_in_europe 递归定义)
SELECT vertices.properties->>'name'
FROM vertices
JOIN born_in_usa ON vertices.vertex_id = born_in_usa.vertex_id 
JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;
```

**而使用图专门的声明式查询语言 Cypher，逻辑清晰得如同画图：**

```cypher
// Cypher 的优雅实现：直观、紧凑
MATCH
    (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (:Location {name:'United States'}),
    (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name
```
> *注：为了统一图查询生态，目前正在推进将 GQL（Graph Query Language）加入 SQL 标准。*

## 四、 声明式查询语言的力量

SQL、Cypher、SPARQL 甚至数据处理的 Datalog 都是**声明式（Declarative）**查询语言。
*   **声明式 vs 命令式（Imperative）：** 声明式语言只需要你指定**“想要什么结果”**及满足的条件，而无需指定**“计算机该如何去一步步实现”**。
*   **优势：** 数据库优化器可以自由决定最佳的执行计划（使用什么索引、按什么顺序 Join），且更容易在多核或集群架构下实现并行化运算，而不影响业务代码。

## 五、 其他前沿模型：事件与数据框

### 1. 事件溯源（Event Sourcing）与 CQRS
*   **事件溯源：** 将数据的每次状态变化（Update/Delete）都记录为不可变的“事件”追加到日志中，把“事件流”作为权威的单一事实来源。
*   **CQRS（命令查询责任分离）：** 从只追加的事件日志（写入优化）中，异步派生出独立的视图（读取优化）。这源于领域驱动设计（DDD）思想，本质是维护两个或多个不同的数据模型以适应读写的分离。

### 2. 数据框（Dataframes）
*   **应用场景：** 数据科学家和机器学习的核心工具（如 Python 的 Pandas，大数据的 Spark DataFrames）。
*   **定位：** 在关系数据库与多维数组（矩阵计算）之间架起的桥梁。
*   **操作方式：** 区别于 SQL 的一步声明到位，数据框通常通过一系列命令式 API 逐步（Step-by-step）对数据进行“清洗”和转换。

# 数据库存储引擎与检索机制核心解析

任何类型的索引都会在读取和写入之间进行权衡：**索引可以极大地加快读取速度，但通常会拖慢写入速度**，因为每次写入数据时，都必须同步更新底层的索引结构。

在 OLTP（联机事务处理）领域，存储引擎主要分为两大思想流派：**日志结构（Log-Structured）** 和 **就地更新（In-Place Update）**。

---

## 一、 流派一：日志结构与 LSM 树 

日志结构学派的核心理念是：**只允许向文件追加数据（顺序写）和删除过时文件，从不修改已经写出的文件。** 典型代表：RocksDB, Cassandra, HBase, Lucene。

### 1. 核心组件与写入流程
*   **内存表（Memtable）：** 收到写入请求时，数据首先被插入到内存中的有序树结构（如红黑树、跳表）。这保证了写入的极速，同时也维护了键的有序性。
*   **排序字符串表（SSTable）：** 当 Memtable 达到一定阈值（如几 MB）时，将其按键排序后刷入磁盘，成为一个新的 SSTable 段文件。SSTable 具有不可变性。
*   **稀疏索引：** 由于 SSTable 是按键排序的，不需要在内存中保存所有键的索引，只需保存每个数据块（通常几 KB）第一个键的位置即可，这被称为“稀疏索引”。
*   **崩溃恢复（WAL）：** 为防止断电丢失 Memtable 中的数据，系统会维护一个仅追加的日志文件，每次写入先记录日志。Memtable 落盘后，对应日志即可截断。

### 2. 读取机制与优化
读取时，系统会依次查询：`Memtable -> 最新的 SSTable -> 更旧的 SSTable`。
*   **布隆过滤器（Bloom Filter）：** 为了防止读取一个不存在的键而遍历所有底层文件（极其缓慢），引擎会为每个 SSTable 配置布隆过滤器。它可以快速判断一个键“绝对不存在”或“可能存在”。假阳性无害，只会导致多查一次磁盘。

### 3. 后台清理：压实（Compaction）
如果不断追加，磁盘终将耗尽。后台会运行合并与压实过程，类似于“多路归并排序”，合并多段记录并丢弃旧值。删除操作则是写入一个特殊的**墓碑（Tombstone）**标记，在压实期间真正清除数据。
*   **按大小分层压实（Size-tiered）：** “小文件攒一堆，一次性合并成大文件”。写入友好，能应对极高写入吞吐量，但合并时极其耗费 IO 和临时磁盘空间。
*   **分级压实（Leveled）：** 将数据分层级，每层按 Key Range 切分成极小的 SSTable。合并更加增量，查询更容易定位，但 Compaction 动作更频繁。

## 二、 流派二：就地更新与 B 树

B 树是应用最广泛的索引结构，是关系型数据库（如 MySQL/InnoDB, PostgreSQL）的基石。其核心理念是：**把磁盘划分为固定大小的页（Page/Block，通常为 4KB~16KB），并允许在原位置直接覆写数据。**

### 1. 核心机制
*   **树状页结构：** 每一页都有标识，页与页之间通过指针引用。树的深度通常极浅（O(log n)），一棵四层深的 B 树就能存储 250TB 数据。
*   **分裂与平衡：** 如果一页写满，就将其拆分成两个半满的页，并更新父节点。这保证了树始终保持平衡。
*   **预写日志（WAL）：** 就地更新（特别是分裂页时）是非常危险的。如果崩溃可能导致“孤儿页”或“页撕裂”。因此 B 树也必须先将修改写入 WAL，再刷入树页本身，以便崩溃恢复。

### 2. B 树的碎片化
随着数据的不断删除和更新，B 树会产生空闲的碎片页，这些页面位于文件中间，难以归还给操作系统。虽然以后可以复用，但会降低空间利用率，需要数据库定期进行“碎片整理”。

## 三、 LSM 树 vs B 树的巅峰对决

| 维度 | LSM 树 (如 RocksDB) | B 树 (如 MySQL InnoDB) |
| :--- | :--- | :--- |
| **主要写入模式** | 顺序写入（追加） | 随机写入（就地覆写） |
| **写入吞吐量** | **极高**（更适合写入密集型工作负载） | 较高（受限于随机 IO 瓶颈） |
| **读取吞吐量** | 较高（需检查多层 SSTable） | **极高**（性能稳定可预测） |
| **写放大** | **较低**（只重写有效数据，且压缩率高） | **较高**（改一个字节也要重写整页 16KB+WAL） |
| **磁盘碎片化** | 极少（压实过程天然整理了碎片） | 严重（随时间推移页面内部产生空洞） |
| **并发控制机制** | 相对简单（不可变文件避免了复杂锁竞争） | 复杂（涉及行锁、页锁、间隙锁） |

> **SSD 的硬件特性影响：** 现代固态硬盘（SSD）每次只能按块（Block，如 512KB）进行擦除垃圾回收（GC）。LSM 树的大块顺序写入对 SSD 更加友好，而 B 树频繁的随机页更新会加剧 SSD 的写放大与硬件磨损。

## 四、 复杂检索：全文、空间与向量

除了基于键值匹配的查询，现代数据库还支持高维度的复杂检索。

1.  **多列联合索引：** 将一列接在另一列之后组合成键，顺序极为重要。
2.  **空间索引（地理位置）：** 常规 B 树无法高效处理 `(x, y)` 二维坐标查询。通常使用 **空间填充曲线** 将二维转一维，或使用专用的 **R 树（R-Tree）** 索引。
3.  **全文检索（Lucene/Elasticsearch）：** 本质上是处理庞大维度的布尔查询。把搜索转换为“包含词项 X 位图”与“包含词项 Y 位图”的**按位与运算**。使用类似字典树的**莱文斯坦自动机**来支持容错（拼写错误、模糊匹配）。
4.  **向量嵌入（Vector Embeddings）：** 语义搜索的基石。将文本转为多维浮点数空间中的一个点。查询本质是在寻找“距离最近的点”。
    *   **平面索引（Flat）：** 暴力比对，百分百精确但速度极慢。
    *   **IVF 索引（倒排文件）：** 将空间划分为多个聚类（质心）。先找目标落入哪个分区，再在分区内查找。是一种牺牲精度换取速度的近似搜索。
    *   **HNSW 索引（分层可导航小世界）：** 维护多层结构图，从顶层稀疏图开始粗略定位，逐层向下进入底层密集图精确查找。目前向量数据库（如 Faiss, pgvector）的主流算法。

## 五、 分析型存储（OLAP）的核心优化

数据仓库针对需要扫描海量记录的复杂聚合查询进行了专门的优化。

### 1. 行式存储 vs 列式存储
*   **行式存储（Row-Oriented）：** OLTP 的标配，同一行的所有数据相邻存放。缺点是：如果一张宽表有 100 列，分析时只查其中 4 列，引擎依然要将整行 100 列全从磁盘载入内存，造成极大的 IO 浪费。
*   **列式存储（Column-Oriented）：** 将同一“列”的所有值相邻存放。查询时只需精确加载需要的列即可。由于按列单独存储，在还原为整行时，只需按照行号偏移量进行拼接。

### 2. 极致的列压缩
列式存储天然极度适合压缩。因为同一列的数据类型完全一致，且不同值的数量通常远小于总行数（例如几十亿条记录，商品类别只有几万个）。
*   **位图编码（Bitmap Encoding）：** 将一个列转换成 N 张独立位图。
*   **游程编码（Run-length Encoding）：** 如果位图极度稀疏（全是 0），可以直接记录连续出现 0 或 1 的数量（如 `0x1000, 1x1, 0x500`），进一步极大压缩体积。

### 3. 物化视图与聚合
*   **虚拟视图：** 只是 SQL 查询的宏替换（快捷方式），读取时会即时展开为底层查询。
*   **物化视图（Materialized Views）：** 是实际写入磁盘的查询结果副本。针对高频出现的 COUNT、SUM 等操作，使用**物化聚合**可以避免每次重新扫描原始海量数据，大幅提升报表加载速度。

# 数据编码、模式演化与数据流架构

系统间的数据交换不仅关乎运行效率，更深刻影响着应用程序的架构设计与未来的平滑演化。

## 一、 兼容性与数据表示基础

随着系统的演进，新旧代码往往需要同时运行，这要求数据格式具备良好的兼容性：
*   **向后兼容（Backward Compatibility）：** 较新的代码可以无缝读取由较旧代码写入的数据。
*   **向前兼容（Forward Compatibility）：** 较旧的代码可以无缝读取由较新代码写入的数据。

### 数据的两种存在形态
1.  **内存表示：** 数据保存在对象、结构体、树或哈希表等结构中。这些结构通常使用指针，专门针对 CPU 的高效访问进行了优化，但指针离开当前进程便失去意义。
2.  **传输/存储表示：** 若要将数据写入文件或通过网络发送，必须将其转换为自包含的字节序列。
    *   **编码（序列化 / 编组）：** 从内存表示转换为字节序列。
    *   **解码（反序列化 / 解组）：** 从字节序列恢复为内存表示。

---

## 二、 文本格式的局限：JSON、XML 与 CSV

尽管 JSON、XML 和 CSV 具备人类可读性，但在实际工程中隐藏着一些不易察觉的痛点：

| 局限性维度 | 具体表现与案例 |
| :--- | :--- |
| **数值歧义与精度丢失** | XML/CSV 无法区分纯数字字符串与数值；JSON 不区分整数与浮点数。**大数处理风险：** 大于 2⁵³ 的整数在采用 IEEE 754 双精度的语言（如 JavaScript）中会失真。例如，X（Twitter）的 64 位帖子 ID 必须在 API 中同时以数值和字符串两种形式返回，以防客户端解析错误。 |
| **二进制数据支持差** | 文本格式缺乏对原生字节流的支持。常规的 Base64 编码绕过方案虽然可行，但会导致**数据体积膨胀 33%**。 |
| **模式（Schema）缺失或极其复杂** | CSV 完全没有模式，行列定义依赖应用层硬编码，且转义规则含糊。XML/JSON Schema 虽功能强大，但学习曲线陡峭，实现复杂。 |

---

## 三、 JSON 模式 (JSON Schema)

JSON Schema 已成为 Web 服务（如 OpenAPI）和数据库（如 PostgreSQL、MongoDB）中广泛采用的数据建模标准。

*   **内容模型策略：**
    *   **开放内容模型（默认）：** 允许出现未定义的任意字段（`additionalProperties: true`）。它主要用于定义“不允许出现什么”（无效值），而非穷举“允许出现什么”。
    *   **封闭内容模型：** 只允许出现显式定义的字段。
*   **演化挑战：** JSON Schema 支持正则约束（`patternProperties`）、条件逻辑（if/else）和远程引用。这些强大的特性反而让模式定义变得庞杂，导致向前/向后兼容的演化充满挑战。

---

## 四、 二进制编码与模式演化（Protobuf 与 Avro）

基于模式的二进制编码（如 Google 的 Protocol Buffers 和 Apache Avro）提供了比文本格式更优的性能与演化保障。

### 1. Protocol Buffers (Protobuf) 核心机制
*   **字段标签取代字段名：** 编码数据中不包含 userName 等字符串字段名，而是使用模式中定义的**数字标签（1, 2, 3）**。这大幅压缩了数据体积。
*   **变长整数（Varint）：** 根据数字大小动态分配字节数（如小数字仅占 1 字节），进一步节省空间。
*   **列表表示：** 没有显式数组类型，通过 `repeated` 修饰符让同一标签号在记录中重复出现。

### 2. Protobuf 的兼容性与演化规则
模式演化的核心在于**字段标签号绝对不能修改**：
*   **向前兼容：** 新增字段分配新标签号。旧代码遇到不认识的新标签时，可依靠类型注解计算长度并跳过，同时保留该未知字段。
*   **向后兼容：** 新代码读取旧数据时，如果找不到新增加的标签号，会自动填入类型默认值（如空字符串、数值 0）。
*   **字段删除：** 废弃的标签号必须被标记为“保留（reserved）”，绝不能再次分配给新字段。

> **二进制编码的核心优势：**
> 1. 数据极其紧凑。
> 2. Schema 本身即是强制同步的说明文档。
> 3. 支持在部署前执行兼容性静态检查。
> 4. 支持静态类型语言的代码生成与编译时检查。

---

## 五、 数据流转架构与通信模式

数据在系统进程间的流动主要分为三种典型架构：

### 1. 远程过程调用（RPC）与服务路由
RPC 旨在提供**位置透明性**，让调用远程网络服务如同调用本地函数一样自然。其背后的负载均衡与服务发现机制包括：
*   **硬件 / 软件负载均衡器：** 专用设备或 Nginx/HAProxy 等软件，负责连接管理与故障转移。
*   **DNS 路由：** 简单易用，但受限于缓存延迟，无法敏捷应对实例的频繁上下线。
*   **服务发现系统：** 集中式注册表。服务实例主动注册并发送心跳，客户端查询可用列表后直连端点。适合动态环境。
*   **服务网格（Service Mesh）：** 如 Istio、Linkerd。通过“边车（Sidecar）”代理接管本地流量，透明化处理 TLS 加密，并提供强大的调用链路追踪与流量监控。

### 2. 工作流引擎（Workflow Engines）
通常由**编排器（调度）**与**执行器（运行任务）**组成。
*   **数据 / ETL 编排：** Airflow、Dagster、Prefect。
*   **可视化业务编排：** Camunda、Orkes（支持 BPMN 标准）。
*   **持久化执行引擎：** Temporal、Restate（保障长时间运行任务的状态不丢失）。

### 3. 事件驱动架构与消息代理
与 RPC 的同步等待不同，事件驱动采用异步通信。
*   **消息代理（Message Broker）：** 请求（事件/消息）先发送至中间件暂存，接收者异步消费。
*   **常见实现：** Kafka、RabbitMQ、ActiveMQ，以及云原生的 AWS Kinesis、GCP Pub/Sub 等。

### 4. 分布式 Actor 模型
*   **Actor 模型：** 一种单进程并发的编程范式。将状态与逻辑封装在 Actor 内部，通过互相发送异步消息进行通信，从根本上避免了多线程死锁与竞态条件。分布式 Actor 框架将其扩展到了跨网络多节点环境。


分布式数据库通过将数据和负载分散到多台计算机上，以满足高并发、海量存储、高可用与低延迟的需求。以下为整理后的分布式数据库架构、复制机制与一致性模型全景梳理：

---

**一、 分布式系统架构与数据分布策略**

**分布式架构对比**

| 架构类型 | 工作原理 | 优点 | 缺点 / 局限性 |
| :--- | :--- | :--- | :--- |
| **共享内存 (Shared-Memory)** | 多处理器共享同一块内存与磁盘（包含 NUMA 架构） | 任意处理器可访问任意内存与磁盘 | 硬件成本呈非线性爆发增长，存在总线瓶颈 |
| **共享磁盘 (Shared-Disk)** | 独立处理器和内存，通过快速网络连接共享磁盘阵列 | 节点故障不影响底层存储 | 锁竞争与存储网络瓶颈限制了扩展性 |
| **无共享 (Shared-Nothing)** | 每个节点（虚拟机/物理机）拥有独立的处理器、内存和磁盘 | **水平扩展（Scaling Out）**能力极强，成本低 | 需要在软件层面实现复杂的网络协调逻辑 |

**数据分布的基本方式**
* **复制（Replication）：** 在不同节点上保留相同数据的副本，用于冗余容错、提升吞吐量与降低访问延迟。
* **分区（Partitioning / Sharding）：** 将大型数据库拆分为较小的子集（分片），指派给不同的节点处理。

---

**二、 复制模型（Replication Topologies）**

**1. 单主复制（Single-Leader / Master-Slave）**
* **工作原理：** 只有一个节点接受客户端写请求（领导者），领导者将新数据写入本地后，将变更日志发送给其他只读节点（追随者/从库）。
* **同步机制：**
  * **同步复制：** 追随者保证数据最新，但任意追随者挂起会导致领导者阻塞所有写入。
  * **半同步复制（推荐）：** 保留 1 个同步追随者 + 多个异步追随者。若同步追随者异常，则自动提升一个异步追随者为同步。
* **追随者追赶机制：** 取得一致性快照 $\rightarrow$ 复制快照至新追随者 $\rightarrow$ 连接主库请求快照位点后的日志（如 PostgreSQL 的 **LSN**，MySQL 的 **binlog 位点/GTID**） $\rightarrow$ 追赶进度。
* **故障切换（Failover）与风险：**
  * **超时判定：** 节点间定期心跳，超时（如 30 秒）认定失效。
  * **脑裂（Split-Brain）：** 旧主库因网络抖动“假死”后恢复，系统出现两个主库同时接收写入。通常使用**栅栏（Fencing）机制**强制关闭或隔离旧主库。

**2. 多主复制（Multi-Leader）**
* **适用场景：** 跨地域数据中心部署（降低写入延迟）、离线编辑与本地优先（如 Google Docs 实时协作同步引擎）。
* **常见拓扑：** 全对全（All-to-all）、环形（Ring）、星形/树形（Star/Tree）。
* **冲突解决（Conflict Resolution）：**
  * **冲突避免：** 确保同一条记录的所有写操作强绑定到固定领导者。
  * **最后写入者胜（LWW）：** 按时间戳保留最新写入，实现简单但可能静默丢失数据。
  * **自动算法合并：** 采用无冲突复制数据类型（**CRDT**）或操作变换（**OT**）进行无损合并。
  * **版本向量（Version Vector）：** 用于精确检测并识别并发写入冲突。

**3. 无主复制（Leaderless / Dynamo-style）**
* **代表系统：** Cassandra、ScyllaDB、Riak。
* **同步与修复机制：**
  * **读修复（Read Repair）：** 客户端并行读取多节点，发现陈旧数据后将最新值反向写入旧节点。
  * **提示移交（Hinted Handoff）：** 目标节点挂掉时，由第三方节点暂存写入，待目标节点恢复后移交。
  * **反熵（Anti-Entropy）：** 后台进程定期扫描并拉齐不同节点的数据差异。
* **法定人数（Quorum）原则：**
  * 设总副本数为 $n$，写入确认节点数为 $w$，读取查询节点数为 $r$。
  * 当满足 **$w + r > n$** 时，读取操作至少能命中一个包含最新写入的节点。通常取 $w = r = \lfloor n/2 \rfloor + 1$。

---

**三、 复制日志（Replication Log）实现机制**

| 日志类型 | 实现原理 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **基于语句 (Statement-based)** | 领导者记录并转发每个 INSERT/UPDATE 语句 | 日志文件紧凑 | 无法安全处理非确定性函数（如 `NOW()`, `RAND()`） |
| **物理 WAL 传输** | 直接传输存储引擎的磁盘块字节修改日志 | 底层精准一致 | 与存储引擎高度耦合，主从库难以跨版本升级 |
| **逻辑/行日志 (Row-based)** | 记录数据行的变更（MySQL binlog / PG 逻辑解码） | 与存储机制解耦，易于跨版本/异构系统同步 | 批量修改多行时产生的日志体量较大 |

---

**四、 复制延迟与一致性模型**

异步复制系统在正常运行中保证**最终一致性（Eventual Consistency）**，但在复制延迟（Replication Lag）较大时，系统需要提供更高层级的一致性保证：

* **写后读一致性（Read-After-Write / Read-Your-Own-Writes）**
  * **保障：** 用户重新加载页面时，必定能看到自己刚提交的修改。
  * **实现：** 用户修改过的敏感内容固定从主库读取；或记录最后一次更新时间，更新后指定时间（如 1 分钟）内的读取路由至主库。
* **单调读（Monotonic Reads）**
  * **保障：** 避免“时光倒流”现象（即先读到了最新数据，刷新后又读到了旧追随者的陈旧数据）。
  * **实现：** 强制同一用户的读取请求始终路由给同一个副本（如基于用户 ID 进行哈希路由）。
* **一致前缀读（Consistent Prefix Reads）**
  * **保障：** 保证因果关系不颠倒（例如：问题的回答不能早于问题本身出现）。
  * **实现：** 确保存在因果关系的写入操作全部分配到同一个分片/分区处理。

# 数据库分片（Sharding / Partitioning）核心知识整理

## 1. 核心概念
* **基本定义**：通常情况下，每条数据（记录、行或文档）属于且仅属于一个分片。
* **分片与复制的结合**：分片通常与复制（Replication）结合使用，每个分片的副本存储在多个节点上以获得容错能力。在单主复制模型中，每个分片有一个领导者（Leader）和多个追随者（Follower）。一个节点可以同时是某些分片的领导者和其他分片的追随者。
* **不同数据库中的术语**：
  * **Partition（分区）**：Kafka
  * **Range（范围）**：CockroachDB
  * **Region（区域）**：HBase, TiDB
  * **Tablet（表分片）**：Bigtable, YugabyteDB
  * **vnode（虚节点）**：Cassandra, ScyllaDB, Riak
  * **vBucket（虚桶）**：Couchbase
* **分区 vs 分片**：在 PostgreSQL 等部分系统中，“分区”指将单机大表拆分为同一台机器上的多个文件（便于快速删除整个分区等）；而“分片”指将数据集跨多台机器拆分。在许多其他系统中，两者是同义词。

## 2. 分片的目的与挑战
* **核心目的（可伸缩性）**：当数据量或写入吞吐量超出单节点承受极限时，分片能将负载分散到多节点，是实现**水平扩展（Scale-out）**的主要手段。
* **适用场景**：非常适合键值（Key-Value）数据，因为可以直接按键分片；对关系型数据较棘手，因为涉及跨分片的二级索引搜索或连表操作。
* **单机多核利用**：Redis、VoltDB、FoundationDB 采用每个核心一个进程的方式，利用分片将负载分摊到同一机器的多核 CPU 上。
* **挑战与代价**：分片是一种重量级方案，增加了系统复杂性（如需要选择分区键）。如果数据量和并发量单机足以应对，通常最好避免分片。
* **倾斜（Skew）与热点（Hotspot）**：如果分片不均匀，会导致“倾斜”，大幅降低分片效果。极端情况下大部分节点闲置，个别节点成为瓶颈。
  * **热分片**：负载高得不成比例的分片。
  * **热键**：导致极高负载的单一键（如社交网络中的名人账号）。

## 3. 主要分片策略
### 3.1 按键的范围分片 (Key Range Sharding)
* **原理**：键按顺序排列，每个分片负责一个最小值到最大值之间的所有键。
* **优点**：支持高效的范围查询。
* **缺点**：如果应用频繁访问排序位置相近的键，极易形成热点。
* **再平衡**：当分片过大时，通常动态将其拆分为两个子范围。

### 3.2 按键的哈希分片 (Hash Sharding)
* **原理**：对每个键应用哈希函数，分片拥有一段哈希值范围，而非直接对应键的范围。
* **优点**：打破了键的连续顺序，使负载分布更均匀，有效避免热点。
* **缺点**：破坏了键的顺序，使得范围查询效率降低。

### 3.3 复合键策略
* **原理**：以键的第一部分作为“分区键”（决定数据进入哪个分片），其余部分用于在分片内排序。
* **优点**：在保证数据均匀分布的同时，允许对相同分区键的记录执行高效的范围查询。

### 3.4 动态与固定分片方案
* **固定数量分片**：一种常见且简单的方案是预先创建远多于节点数的分片（如 10 节点分 1000 个片，每节点 100 个）。增删节点时，只需在节点间直接迁移整个分片，系统另行记录映射关系。
* **哈希范围分片**：结合哈希与范围分片，使得分片数量能轻松适应工作负载。
* **一致性哈希 (Consistent Hashing)**：一种哈希算法，保证键均匀映射到指定数量的分片，且在分片数量改变时，尽可能少地在分片间迁移键。（注：这里的“一致性”仅指键尽量留在原分片的倾向，与副本一致性或 ACID 无关）。相关算法如最高随机权重（约会哈希）、跳跃一致性哈希，Cassandra/ScyllaDB 采用了类似设计。

## 4. 二级索引的分片
二级索引也需要分片，主要有两种方案：
* **本地二级索引 (Local Secondary Index)**
  * **原理**：二级索引与主键及其数据存储在同一个分片中。
  * **特点**：写入极其高效（只需更新一个分片），但读取索引时必须访问并读取所有分片（Scatter-Gather），代价较高。
* **全局二级索引 (Global Secondary Index)**
  * **原理**：根据索引值采用另一套独立的分片方式。
  * **特点**：读取高效（只需访问一个索引分片即可定位，尽管获取实际记录仍需读其他分片）；但写入或更新记录时，可能需要跨多个分片去更新对应的索引条目。

## 5. 请求路由与集群协调
* **记录与映射**：系统需要准确记录哪个分片分配在哪个节点上。
* **协调服务**：许多分布式数据系统依赖 **ZooKeeper, etcd** 等独立协调服务来管理分片分配。这些服务使用共识算法实现容错，防止“脑裂”。
* **跨分片挑战**：分片数据库能够横向伸缩是因为各分片大体独立运行。然而，当某个操作需要写入多个分片时，如果部分成功、部分失败，处理起来会非常棘手。

# 数据库事务与并发控制核心笔记

事务是简化数据库读写问题的首选机制，它将多个读写操作组合成一个逻辑单元。整个事务要么全部成功（提交），要么全部失败（中止/回滚）。这种机制极大地简化了应用程序的错误处理，免去了对“部分失效”的担忧。

新兴的“NewSQL”数据库（如 CockroachDB、TiDB、Spanner、FoundationDB 和 YugabyteDB）证明了事务系统同样可以结合分片与共识协议，在大规模场景下提供强 ACID 保证。

---

## 1. ACID 特性

事务提供的安全保证通常用 **ACID** 来描述：

*   **原子性（Atomicity）**：提供“全有或全无”的保证。如果事务执行中途发生错误，事务会中止并丢弃之前完成的所有写入。这使得应用程序能够安全地重试。
*   **一致性（Consistency）**：指由具体应用定义的数据库“良好状态”。这主要取决于应用程序如何使用数据库，并非数据库自身的纯粹属性。
*   **隔离性（Isolation）**：并发执行的事务彼此隔离，不能相互干扰。
*   **持久性（Durability）**：事务一旦成功提交，其写入的任何数据都不会遗失。
    *   **单节点**：通常通过写入硬盘/SSD、使用 `fsync()` 系统调用落盘，以及预写日志（WAL）来保证。
    *   **分布式/复制**：意味着数据已成功复制到一定数量的节点。

### 事务重试的局限性
虽然重试中止的事务简单有效，但也存在缺陷：
1. **网络超时**：事务可能已在数据库成功提交，只是向客户端确认时网络中断。无去重机制的盲目重试会导致执行两遍。
2. **过载雪上加霜**：若错误源于系统过载，重试会加剧问题（建议使用限制重试次数、指数退避等策略）。
3. **副作用无法撤销**：如果事务在数据库外产生副作用（如发送邮件），重试会导致副作用多次发生。
4. **客户端崩溃**：重试期间若客户端进程崩溃，待写入数据将丢失。
5. **适用场景**：仅瞬态错误（死锁、网络中断）值得重试；永久性错误（违反约束）重试无意义。

---

## 2. 弱隔离级别与并发异常

出于性能考量（强隔离性代价高昂），许多数据库在实践中采用弱隔离级别，这会引发特定的并发异常现象。

### 读已提交 (Read Committed)
最基本的事务隔离级别，提供两项保证：
1. **没有脏读**：读取时，只能看到已提交的数据。
2. **没有脏写**：写入时，只能覆盖已提交的数据（通常通过行级排他锁实现）。

### 快照隔离 (Snapshot Isolation) 与 MVCC
为了解决**读偏差（不可重复读）**，快照隔离让每个事务都从数据库的“一致性快照”中读取数据。
*   **核心原则**：读不阻塞写，写不阻塞读。
*   **多版本并发控制 (MVCC)**：数据库保留同一行的多个版本。
    *   *实现（如 PostgreSQL）*：每个事务有唯一单调递增的事务 ID (`txid`)。行有 `inserted_by` 和 `deleted_by` 字段。垃圾收集进程会在无事务访问时清理旧版本数据。索引通常指向特定的行版本。
    *   *注意*：PostgreSQL 的“可重复读”即快照隔离，而 MySQL 的“可重复读”是一致性弱于快照隔离的 MVCC 实现。

### 常见的并发冲突与应对方案

*   **丢失更新 (Lost Update)**：发生在“读取—修改—写入”循环中。
    *   *解决方案*：原子写操作、显式加锁（`SELECT FOR UPDATE`）、条件写入/CAS（比较并设置）。
*   **写偏差 (Write Skew)**：事务基于读取到的前提作出决定并写入，但写入时前提已失效。
    *   *解决方案*：真正的可串行化隔离。
*   **幻读 (Phantom Read)**：一个事务的写入改变了另一个事务搜索查询的结果。
    *   *物化冲突*：将幻读转化为具体行上的锁冲突（设计难、易出错，仅作最后手段）。

---

## 3. 可串行化 (Serializable)

最强的隔离级别，保证并发事务的最终结果与它们完全串行执行的结果相同。主要有三种实现方式：

### ① 实际串行执行 (Actual Serial Execution)
在单线程上严格按顺序执行事务（如 VoltDB、Redis）。
*   **优势**：省去加锁协调开销，内存中执行速度极快。
*   **劣势**：吞吐量受限于单 CPU 核。不适合交互式事务，通常使用现代存储过程（Lua, JavaScript, Java 等）一次性提交执行。

### ② 两阶段锁定 (2PL - Two-Phase Locking)
长达几十年的标准方法（如 MySQL InnoDB 的可串行化）。
*   **机制**：写会阻塞其他写和读；读也会阻塞写（区别于 MVCC）。
*   **锁模式**：共享锁（读）与独占锁（写）。
*   **两阶段**：事务执行期间获取锁（第一阶段），事务结束时一次性释放所有锁（第二阶段）。
*   **问题**：性能较差，极易发生死锁。通常使用**索引范围锁 (next-key locking)** 来锁定搜索条件覆盖的范围，防止幻读。

### ③ 可串行化快照隔离 (SSI - Serializable Snapshot Isolation)
一种乐观并发控制技术，建立在快照隔离之上。
*   **机制**：不阻塞事务运行，而在准备提交时检查是否发生了破坏隔离性的事件（如读取了过时的版本，或先前的读取被后来的写入影响）。若有冲突，则中止并重试。
*   **优势**：读写互不阻塞，查询延迟可预测，适合读取密集型负载。

---

## 4. 分布式事务

跨越多个节点的事务，原子性的保证变得更加复杂。

### 两阶段提交 (2PC - Two-Phase Commit)
跨多节点实现原子事务提交的经典算法（不同于 2PL 两阶段锁定）。
*   **角色**：协调者 (Coordinator) 与 参与者 (Participants)。
*   **第一阶段（准备）**：协调者询问所有参与者是否可以提交。
*   **第二阶段（执行）**：若全回答“是”，发出提交请求；若有任一回答“否”，发出中止请求。
*   **存疑状态**：如果参与者投了“是”后协调者崩溃，参与者只能等待（不确定事务）。
*   **开销**：来自强制刷盘 (`fsync`) 和额外的网络往返。

### 分布式事务类型
*   **内部事务**：所有节点运行同一种数据库软件（如 TiDB, Spanner）。
*   **异构事务 (XA 事务)**：X/Open XA 是一套跨异构技术（如不同数据库、消息队列）实现 2PC 的 C API 标准。

---

## 附录：并发异常速查表

| 异常现象 | 描述 | 解决方案 / 隔离级别 |
| :--- | :--- | :--- |
| **脏读 (Dirty Read)** | 读到了另一个事务尚未提交的写入数据。 | 读已提交及以上 |
| **脏写 (Dirty Write)** | 覆盖了另一个事务尚未提交的写入数据。 | 读已提交及以上 (行级锁) |
| **读偏差 (Read Skew)** | 即不可重复读，不同时间点观察到数据库的不同部分。 | 快照隔离 (MVCC) |
| **丢失更新 (Lost Update)** | 并发读写循环中，未合并对方修改导致覆盖/丢失。 | 原子操作 / 显式加锁 / CAS |
| **写偏差 (Write Skew)** | 基于读取的值作出决定并写入，但写入时依据的前提已失效。 | 可串行化隔离 |
| **幻读 (Phantom Read)** | 某事务的写入改变了另一事务的范围搜索结果。 | 快照隔离 (防直接幻读) / 索引范围锁 (防写偏差场景) |


### 补充 1：读已提交防脏读的底层实现
*(可补充在“读已提交”部分)*
* **防脏写**：最常见的办法是使用行级锁。事务想修改某一行时必须先取得该行的独占锁，并一直持有到事务结束。
* **防脏读（保留旧值机制）**：对于每一行写入，数据库会**同时保留旧的已提交值，以及当前持有写锁的事务写入的新值**。在该写事务进行期间，其他事务读取这一行时只会得到旧值；等新值正式提交后，其他事务才会改为读取新值。

### 补充 2：MVCC 的底层细节与索引处理
*(可补充在“快照隔离 (Snapshot Isolation) 与 MVCC”部分)*
* **PostgreSQL 的 MVCC 实现机制**：
  * 事务启动时会获得一个唯一且单调递增的事务 ID（`txid`）。
  * 表中每一行都有一个 `inserted_by` 字段（保存插入该行的 `txid`）和一个初始为空的 `deleted_by` 字段。
  * **删除标记**：删除某行时并非立即移除，而是把 `deleted_by` 设为请求删除的 `txid`。
  * **链表遍历**：同一行的各个版本组成链表（可反向或正向连接），使查询能在内部遍历该行的所有版本。等到确定没有旧事务访问时，垃圾收集进程（GC）才会真正移除带删除标记的行。
* **多版本数据库中的索引如何工作？**
  * 最常见的做法是：每个索引项指向与其匹配的某个行版本（最旧或最新版本）。使用索引的查询必须沿行版本链遍历，找到既对当前事务可见、值又符合查询条件的那一行。垃圾收集移除旧版本时，会一并删除相应的索引项。

### 补充 3：丢失更新的处理与 LWW
*(可补充在“常见的并发冲突与应对方案 - 丢失更新”部分)*
* **自动检测**：部分数据库允许这些循环并行执行，一旦事务管理器检测到丢失更新，便中止相应事务并迫使它重试。
* **最后写入者胜 (LWW)**：这是一种基于时间戳的冲突解决办法，但它**非常容易导致更新丢失**。

### 补充 4：实际串行执行与存储过程细节
*(可补充在“可串行化 - ① 实际串行执行”部分)*
* **摒弃 PL/SQL，拥抱通用语言**：现代存储过程实现已经放弃了传统的 PL/SQL。例如，VoltDB 使用 Java 或 Groovy，Datomic 使用 Java 或 Clojure，Redis 使用 Lua，MongoDB 使用 JavaScript。
* **无 I/O 等待**：只要事务所需的全部数据都在内存中，存储过程就能快速执行，无须等待任何网络或磁盘 I/O。这是单线程串行系统保持高性能的关键前提。

### 补充 5：两阶段锁定 (2PL) 的死锁与锁退化
*(可补充在“可串行化 - ② 两阶段锁定”部分)*
* **读写互相阻塞**：2PL 与快照隔离的关键区别在于，2PL 中不仅写会阻塞其他写和读，**读同样会阻塞写**。
* **死锁更为频繁**：基于锁的读已提交也会发生死锁，但在 2PL 严格隔离下死锁往往更为频繁。事务因死锁中止重试必须从头重做，若死锁频繁，浪费的计算量会相当可观。
* **锁退化（回退机制）**：如果没有合适的索引可供附加范围锁（Next-key locking），数据库就会**退回到对整张表加共享锁**。这样会阻塞所有其他事务写表，性能极差，但这是一种安全的后备方案。

### 补充 6：SSI 的具体冲突检测机制
*(可补充在“可串行化 - ③ 可串行化快照隔离 (SSI)”部分)*
数据库如何判断查询结果可能已经变化（即依据了过时的前提）？SSI 主要通过检测以下两种情况来决定是否中止事务：
1. **检测陈旧的 MVCC 读取**：即未提交的写入发生在了读取操作之前。
2. **检测影响先前读取的写入**：即写入操作发生在了读取操作之后，改变了先前读取的结果。

# 分布式系统面临的挑战与现实模型

分布式系统的核心在于将“容忍部分失效”构建到软件中。在没有全局共享状态的混乱物理现实里，系统必须面对网络、时钟和节点行为的极度不确定性。

## 1. 不可靠的网络与故障检测

*   **网络的不确定性**：请求或响应可能丢失、延迟，或远程节点失效。TCP 虽有重传和拥塞控制，但无法在超时后分辨出是请求丢失还是确认包丢失，也无法解决物理断连问题。
*   **异步网络与超时机制**：现实中的数据中心多为具有“无界延迟”的异步网络。系统只能依靠**超时**来检测故障，但这无法准确区分是节点崩溃、处理缓慢还是网络拥堵。

## 2. 不可靠的时钟与时间同步

*   **日历时钟 vs 单调时钟**：日历时钟（依赖 NTP）易受网络阻断、漂移和回拨影响，不适合严格的事件排序；单调时钟持续递增，更适合用于测量时间间隔（如计算超时）。
*   **TrueTime 与置信区间**：Google Spanner 使用 TrueTime API 返回时间的置信区间 `[earliest, latest]`。事务提交前会刻意等待一段等于区间长度的时间，以确保不重叠的时间戳能准确反映因果关系。
*   **逻辑时钟**：相比于度量真实流逝时间的物理时钟，逻辑时钟基于递增计数器，仅记录事件的相对先后顺序，在分布式并发写入排序中更为安全。

## 3. 进程暂停、租约与隔离

*   **进程暂停与多数派原则**：节点可能因垃圾回收（GC）等原因长时间“睡着”，醒来后却毫无察觉。系统决策不能依赖单点，必须服从超过半数节点组成的**多数派（Quorum）**。
*   **租约与脑裂防范**：领导者通常依靠带有超时的“租约”维持身份。若旧领导者因暂停导致租约过期，新领导者接管后，旧领导者醒来继续写入，便会引发“脑裂”。
*   **栅栏令牌 (Fencing Tokens)**：为彻底隔离无感知的“僵尸”节点，锁服务每次授权时分配一个单调递增的令牌。存储端会严格校验并拒绝携带过期令牌的写请求。

## 4. 拜占庭故障与现实抽象模型

*   **拜占庭故障**：在互不信任的环境中，节点不仅可能崩溃，还可能“撒谎”（发出错误、矛盾或恶意的响应）。能在此类环境中正确运行的系统被称为具备“拜占庭容错”能力。
*   **部分同步模型**：现实中的分布式系统多属于**部分同步模型**——它们在大多数时候像同步系统一样快速响应，但偶尔会突破网络延迟、进程暂停和时钟漂移的界限。

> **核心总结**：分布式系统的力量在于，通过复杂的协调协议和多数派共识，将脆弱的单点硬件故障在节点层面解决，从而在服务层面实现理论上的永不停机。

# 分布式系统笔记：一致性、逻辑时钟与共识机制

本文档系统梳理了分布式环境下的强一致性（线性一致性）模型、全局 ID 与逻辑时钟的演进，以及分布式共识机制的理论基础与工程实践。

---

## 一、 核心概念：线性一致性 vs 可串行化

在分布式系统中，“强一致性”通常特指**线性一致性**。应用开发者往往希望系统能隐藏复制的内部细节，表现得宛如单机。

| 对比维度 | 线性一致性 (Linearizability) | 可串行化 (Serializability) |
| :--- | :--- | :--- |
| **别名** | 原子一致性、强一致性、即时/外部一致性 | 事务隔离级别（最高） |
| **约束对象** | **单个对象**（如单个寄存器、单行记录）的读写 | **多个对象**的集合（事务组合） |
| **核心保证** | **新鲜度保证 (Freshness Guarantee)** | **执行顺序等效保证** |
| **行为特征** | 一旦新值被写入或读取，后续所有读取必须看到该值。时间线严格单向推进。 | 事务行为等同于某种不交叉的串行执行顺序。 |
| **局限与缺陷** | 无法把操作组合成事务，不能防止多对象的“写偏差”与“幻读”现象。 | 允许“陈旧读取”（Stale Read），不保证时间维度上的新鲜度。 |

**依赖线性一致性的典型场景**：
1. **锁定与领导者选举**：如 etcd（v3后默认线性一致读取）、ZooKeeper 的 Leader 选举。
2. **约束与唯一性保证**：防止并发创建同名文件或注册同名用户。
3. **跨通道时序依赖**：消除多系统协作时的数据竞态（如文件先存入存储，后发消息至队列，若无线性一致性可能导致队列消费者读不到文件）。

---

## 二、 数据复制拓扑与一致性权衡

不同的复制架构对线性一致性的支持程度具有本质差异：

*   **单主复制（可能满足）**：如果所有读写都严格由主节点处理，则具备线性一致性。但存在主节点单点故障、脑裂或陈旧读取的风险。
*   **共识算法（很可能满足）**：如 Raft（etcd）或 Zab（ZooKeeper）。内置防脑裂设计，但要求节点在处理读取前，必须向多数派确认自己仍是合法的 Leader，否则可能返回陈旧结果。
*   **多主复制（非线性一致）**：并发写入+异步复制，必然产生写入冲突，不满足线性一致性。
*   **无主复制（通常不满足）**：如 Dynamo、Cassandra。即使满足仲裁读写（$W + R > N$），由于解决冲突通常依赖“最后写入者胜（LWW）”，而 LWW 高度依赖易发生漂移的物理日历时钟，事件实际顺序极易被破坏。

---

## 三、 CAP 定理与物理延迟极限

> **CAP 定理的准确表述**：
> 网络分区（P）是客观存在的基础设施故障，不可避免。只有在网络发生分区时，系统才必须在**强一致性（CP：断开连接、拒绝服务）**与**全面可用性（AP：允许陈旧数据、独立处理请求）**之间二选一。网络正常时，系统可同时提供一致性与可用性。

**线性一致性的性能代价**：
*   **延迟不确定性定律（Attiya & Welch）**：要获得线性一致性，读写请求的响应时间至少与网络延迟的不确定程度成正比。
*   **物理硬件限制**：即使是单机多核 CPU 上的 RAM 也不满足线性一致性（需依靠内存屏障/栅栏指令）。因此，追求强一致性必然带来高延迟，不存在“又快又强一致”的魔法。

---

## 四、 全局 ID 生成器与时钟的演进

在分布式系统中，生成全局唯一且能反映事件因果顺序的 ID 是一大挑战。

### 1. 常见 ID 生成方案的局限

| 方案 | 特点与优势 | 致命缺陷 |
| :--- | :--- | :--- |
| **单节点内存自增** | 严格线性一致，全局绝对有序 | 存在单点故障（SPOF），跨地域延迟极高 |
| **分片/预分配区块** | 奇偶分片或分段获取，支持高并发本地发号 | 完全失去顺序含义，无法比较不同节点 ID 的先后 |
| **随机 UUID (v4)** | 本地即时生成，无需网络通信 | 占用128位空间，完全无序 |
| **时间戳+防碰撞** (Snowflake, ULID, UUID v7) | 趋势递增，高位时间戳排序，低位防冲突 | **极度依赖物理日历时钟**，遭遇 NTP 漂移或时钟回拨会导致顺序错乱，不满足线性一致性 |

### 2. 工程解法：逻辑时钟与预言机
*   **Lamport 逻辑时钟**：采用 `(计数器, 节点ID)` 二元组。不度量流逝的时间，仅计算已发生事件数。保证任意时间戳可比较（全序），且严格吻合因果关系（但缺乏严格的线性一致性）。
*   **混合逻辑时钟 (HLC)**：结合物理时间与逻辑递增，保证始终单调向前，将 NTP 时钟跳变的误差控制在极小范围内。
*   **时间戳预言机 (Timestamp Oracle)**：如 TiDB/TiKV 的 TSO 机制，采用带有强容错（单主复制）的单节点原子计数器，解决高并发下的线性一致性 ID 分配。
*   **Spanner TrueTime**：依赖原子钟/GPS，返回时间戳的置信区间 `[earliest, latest]`，并在提交前强制等待不确定区间耗尽。

---

## 五、 共识算法的本质与理论推演

**共识（Consensus）**的核心是：让多个节点就某个决策达成一致，且一旦决定不可篡改。

### 1. FLP 不可能性定理
在异步系统模型中，只要允许节点崩溃，没有任何确定性算法能够保证**每次都能终止（得出结论）**。
*   **工程破解法**：实践中，系统通过引入**超时机制**（怀疑节点崩溃）或**随机数**，成功绕过了该理论限制，实现了可用的共识。

### 2. 共识问题的四大等价形态
以下四个分布式问题在数学与工程上**完全等价**（解决其一即可转换解决所有）：
1.  **单值共识**：多数节点就某个提议值达成一致。
2.  **比较并设置 (CAS)**：容错且线性一致的寄存器原子更新。
3.  **全序广播 / 共享日志**：决定多节点并发追加日志的严格顺序（State Machine Replication 的基础）。
4.  **原子事务提交**：所有节点一致决定分布式事务的 Commit 或 Abort（类似 2PC，但引入了容错性）。

### 3. 共识算法的核心属性
任何正确的共识算法必须满足：
1.  **一致同意 (Uniform Agreement)**：节点间不产生分歧。
2.  **完整性 (Integrity)**：一旦决定，不可撤销/改变。
3.  **有效性 (Validity)**：决定的值必须是曾经被提议过的值。
4.  **终止 (Termination)**：每个存活节点最终都能得出决定。

---

## 六、 共识算法的工程实现 (Raft / Zab / Paxos)

共识本质上是**“正确实现了自动故障切换的单主复制”**。

### 1. 破解“先有鸡还是先有蛋”
选举 Leader 需要共识，而共识又依赖 Leader。
*   **解法（Epoch/Term/View）**：算法引入递增的“纪元编号”。分为两轮投票：第一轮选出当前纪元的唯一 Leader，第二轮对该 Leader 的日志追加进行表决。

### 2. 法定人数重叠 (Quorum Overlap)
为了保证故障切换时不丢失已提交数据，算法要求两轮投票的**多数派节点必须存在交集**。新选出的 Leader 必定经过了前任 Leader 日志的洗礼，Raft 更是直接要求只有日志足够新鲜的节点才能当选。

### 3. 共识的沉重代价
*   **容错比率**：容忍 $f$ 个节点失效，至少需要 $2f+1$ 个节点（严格多数派）。
*   **超时敏感**：强依赖超时检测，设置过长导致恢复极慢，过短引发无休止的选举风暴。
*   **网络敏感**：在特定网络抖动下，Raft 等协议可能因选票瓜分或链路不对称导致 Leader 频繁禅让，系统停顿。

---

## 七、 分布式协调服务

**协调服务**（如 ZooKeeper, etcd, Consul）是将共识算法打包封装，专为构建复杂分布式系统提供的底层基座（以 Google Chubby 为蓝本）。

**核心应用范式**：
1.  **锁与租约**：依靠底层的强一致 CAS 操作，解决分布式并发资源的争抢。
2.  **栅栏机制 (Fencing Tokens)**：利用单调递增的日志 ID（ZooKeeper 的 `zxid`，etcd 的修订号），配合存储端校验，彻底阻断因 GC 暂停等原因产生的“僵尸节点”脑裂写入。
3.  **故障检测与临时节点**：依靠长期会话与心跳交换，超时后自动释放租约并清理 Ephemeral Nodes。
4.  **变更通知 (Watch)**：主动将集群拓扑或配置的变更推给客户端，替代高延迟的轮询。
5.  **工作分配与服务发现**：调度主实例、分配分片。需要注意，对于单纯的“服务发现”（路由寻址），强一致性的协调服务略显笨重，业界更倾向于基于 DNS/多层缓存的弱一致性高可用方案。


# 批处理与派生数据系统核心笔记

## 1. 数据系统的基础分类

*   **记录系统 (System of Record / 真相源)**：持有数据的权威版本。
*   **派生数据系统 (Derived Data Systems)**：数据由其他系统中的现有数据转换或处理而来（例如：缓存）。若数据丢失，可从原始来源重新创建。二者的根本区别在于**应用程序中的使用方式**，而非使用的工具。
*   **在线系统 (Online Systems)**：默认快速响应，交互式处理请求，核心性能指标为**响应时间**，需具备高可用与容错能力。
*   **离线/批处理系统 (Offline/Batch Systems)**：处理规模极大、数据量过高，无法在交互式请求中完成的任务。

## 2. 批处理存储底座的演进

### 分布式文件系统 (DFS) 与 无共享架构
*   **核心架构**：基于“无共享 (Shared-Nothing)”原则，仅使用普通数据中心网络连接，无需定制硬件（区别于 NAS/SAN 的共享磁盘架构）。
*   **HDFS (Hadoop DFS)**：
    *   大块设计：默认块大小为 128 MB（相比 ext4 的 4,096 字节大得多）。**优势**：极大减少需跟踪的元数据（PB级影响显著），降低寻道开销占比。
    *   组件：守护进程 `DataNode` 负责暴露 API 供远程读写；`NameNode` 服务负责维护集群元数据。
*   **NFS 演进**：传统 NFS 用于连接单台服务器，现代实现（如 AWS EFS）在底层分布式化，但对客户端仍保持单一端点兼容。

### 对象存储的崛起
*   **趋势**：批处理存储层正从传统 DFS（HDFS, GlusterFS, CephFS）转向 S3 等对象存储服务。云数据仓库（BigQuery, Snowflake）进一步模糊了数仓与批处理的界限。
*   **特性**：
    *   结构：对象通过全局唯一的存储桶 (Bucket) 和桶内唯一的键 (Key) 进行 URL 寻址。
    *   操作 API：通过 `get` 读取，`put` 写入。**不支持** `fopen`、`fseek` 等文件句柄 API。
    *   不可变性：对象写入后即不可变，更新必须完整重写（极少数支持追加，如 Azure Blob, S3 Express）。

## 3. 分布式作业编排与资源调度

*   **作业依赖与工作流 (DAG)**：大量批处理作业呈现有向无环图（DAG）特征（上游输出为下游输入），通常包含 50-100 项作业。
*   **编排工具迭代**：早期以 Hadoop 为中心的 Oozie、Azkaban 已被支持多种框架和云数仓的通用工具（Airflow、Dagster、Prefect）取代。
*   **核心组件**：
    *   任务执行器 (Task Executor)
    *   资源管理器 (Resource Manager)：中心化特性，易成为伸缩性与可用性瓶颈。
    *   调度器 (Scheduler)：核心难点在于平衡公平与效率。这是一个 NP-hard 问题，实践中采用启发式算法（FIFO、主导资源公平 DRF、优先级队列、装箱算法等）进行资源分配。

## 4. 批处理计算模型的演进

### MapReduce (初代模型)
*   **地位**：由 Google 2004 年提出，曾让商用硬件处理规模跨越新台阶，但现已基本过时。
*   **工作流**：
    *   **Mapper**：按记录独立处理，提取键值对，不保留跨记录状态。
    *   **Reducer**：框架收集同键的所有值，通过迭代器调用 Reducer 生成输出。
*   **性能缺陷**：基于文件的 I/O 无法形成作业流水线，必须等上游作业完全写入磁盘，下游才能开始，导致速度极慢。

### 数据流引擎 (Dataflow Engines / 现代主导)
*   **代表框架**：Spark, Flink, Daft, Dataflow。
*   **核心优势**：
    *   将整个依赖流作为一项作业处理，显式建模流转过程，算子组合更加灵活（不局限于严格交替的 map/reduce）。
    *   中间数据驻留内存，必要时才“溢写”到磁盘，仅将最终结果写入 DFS。
    *   容错机制：Spark 跟踪计算过程以便丢失时重算；Flink 采用定期快照检查点。

### 混洗 (Shuffle) —— 批处理的核心算法
*   **定义**：一种输入输出均经过分片的分布式排序与路由算法。
*   **作用**：将具有相同键的数据集中到同一个处理节点。MapReduce 与所有现代数据流引擎、云数仓的“连接(Join)”与“聚合(Group by)”操作都高度依赖此算法。

## 5. 高级抽象与 AI/ML 应用

*   **易用性提升**：由于运维逐渐成熟，数据流 API、数据框 (DataFrame) API 和 **SQL (批处理通用语言)** 得到广泛支持。查询优化器能将声明式查询转为高效执行计划。

## 6. 批处理系统核心用例总结

批处理式 I/O 具备输入有界、不可变、无副作用的特性，极易于重跑和调试。其核心用例包括：
1.  **ETL 数据管道**：跨系统定时提取、转换、加载数据。
2.  **数据分析**：支持预聚合的仪表板计算与即席查询。
3.  **机器学习**：准备和处理大规模训练数据集。
4.  **线上系统赋能**：通过批量加载或流式导入，将离线衍生数据提供给面向生产流量的在线系统使用。

为了缩短延迟，可以更频繁地运行处理——比如每秒结束时处理这一秒的数据——也可以完全抛开固定的时间切片，改为连续处理，每个事件一发生就立即处理。这就是 流处理
在流式系统中，相关事件通常被归入同一个 主题（topic） 或 流（stream）。

发布/订阅 模型中，不同系统采取了五花八门的方法，没有一种答案适合所有用途。要区分这些系统，下面两个问题尤其有用：

如果生产者发送消息的速度超过消费者的处理速度，会发生什么？ 大体上有三种选择：系统可以丢弃消息、把消息缓存在队列中，或施加 背压（backpressure）（也称为 流量控制（flow control），即阻塞生产者，令其暂停发送更多消息）。例如，Unix 管道和 TCP 都采用背压：它们有一个固定大小的小缓冲区；如果缓冲区已满，发送者就会被阻塞，直到接收者从中取走数据（参见“网络拥塞与排队”）。

如果消息被缓存在队列中，就必须弄清楚队列不断增长会有什么后果：队列大到内存容纳不下时，系统会崩溃，还是会把消息写入磁盘？如果写入磁盘，磁盘访问会怎样影响消息传递系统的性能5？磁盘写满时又会发生什么6？

如果节点崩溃或暂时离线，会发生什么——是否会丢失消息？ 和数据库一样，要实现持久性，可能需要以某种方式组合使用磁盘写入与复制（参见侧栏“复制与持久性”），而这会付出代价。如果能够容忍偶尔丢失消息，那么在同样的硬件上，通常可以获得更高的吞吐量和更低的延迟。
Webhook11就建立在这一思想之上：把一个服务的回调 URL 注册到另一个服务中，后者每逢事件发生便向该 URL 发出请求。
直接从生产者传递给消费者
消息代理
一种广泛使用的替代方案是通过 消息代理（message broker）（也称为 消息队列（message queue））发送消息。消息代理实质上是一类针对消息流优化的数据库12。它作为服务器运行，生产者和消费者则作为客户端连接到它。生产者把消息写入代理，消费者通过读取代理来接收消息。
数据集中到代理之后，系统更容易容忍客户端时而连接、时而断开乃至崩溃，持久性问题也转移给了代理。有些消息代理只把消息保存在内存中，另一些则会根据配置把消息写入磁盘，以免代理崩溃时丢失消息。面对缓慢的消费者，它们通常允许队列无限增长，而不是丢弃消息或施加背压，不过具体行为也可能取决于配置。

排队还有一个后果：消费者通常是 异步的。生产者发送消息时，一般只等待代理确认消息已被缓存，并不等待消费者完成处理。消息会在未来某个无法确定的时间点传递给消费者——往往不到一秒，但如果队列中积压了大量消息，也可能晚得多。

负载均衡
每条消息只传递给 一个 消费者，因此多个消费者可以分担处理该主题消息的工作。
扇出
每条消息都传递给 所有 消费者。扇出让几个相互独立的消费者都能“收听”同一份消息广播，彼此互不影响——相当于流处理版本的“几个不同批处理作业读取同一个输入文件”。
这两种模式可以结合使用，例如 Kafka 的 消费者组（consumer group） 功能。消费者组订阅某个主题后，该主题中的每条消息都会发送给组内的一个消费者（在组内消费者之间进行负载均衡）。如果两个不同的消费者组订阅同一主题，那么每条消息都会发送给各组中的一个消费者（在消费者组之间实现扇出）。
负载均衡与重新传递的结合仍不可避免地会使消息发生重排。要避免这个问题，可以为每个消费者使用单独的队列，也就是不使用负载均衡。如果消息彼此完全独立，重排并无大碍；但如果消息之间存在因果依赖，顺序就可能十分重要
死信队列（dead letter queue，DLQ） 用来处理这类问题。系统不再把消息留在当前队列中无限重试，而是将其移到另一条队列，让消费者能够继续前进17、18。通常会对死信队列设置监控——队列中出现任何消息都意味着发生了错误。
为什么不能把两者结合起来，既采用数据库的持久存储方式，又具备消息传递的低延迟通知能力？这就是 基于日志的消息代理（log-based message broker） 的思想
同一种结构也可以用来实现消息代理：生产者把消息追加到日志末尾，以此发送消息；消费者顺序读取日志，以此接收消息。消费者读到日志末尾后，便等待新消息追加的通知。
在每个分片中——Kafka 把它称为 分区（partition）——代理会为每条消息分配一个单调递增的序列号，也就是 偏移量（offset）（图 12-3 方框中的数字就是消息偏移量）。分区是仅追加的，因此这样的序列号有明确含义：分区内的消息具有全序，而不同分区之间没有顺序保证。于分片日志通常只能保持单个分片内部的消息顺序，所有必须以一致顺序处理的消息都需要路由到同一个分片。例如，应用可能要求与某个特定用户有关的事件始终以固定顺序出现。可以根据事件的用户 ID 选择分片来实现这一点；换句话说，把用户 ID 作为 分区键（partition key）。
消费者偏移量
顺序消费一个分片，很容易判断哪些消息已经处理：偏移量小于消费者当前偏移量的消息都已处理，偏移量更大的消息则尚未读到。因此，代理无需跟踪每条消息的确认应答，只需定期记录消费者偏移量。
让我们粗略估算一下。在本书写作时，典型的大容量硬盘为 20 TB，顺序写入吞吐量为 250 MB/s。如果始终以最高速度写入消息，大约 22 小时后磁盘就会写满，必须开始删除最旧的消息。这意味着，即使有许多机器和许多磁盘，磁盘日志也总能缓冲至少 22 小时的消息，因为增加磁盘会同时增加可用空间和总写入带宽。实际部署很少用满磁盘的全部写入带宽，所以日志通常可以保存数天乃至数周的消息。
消费者跟不上生产者发送消息的速度时可采取的三种办法：丢弃消息、缓冲消息或施加背压。按照这种分类，基于日志的方法属于缓冲，它提供了一个很大但大小固定的缓冲区，其上限由可用磁盘空间决定。

实践中，大多数稍具规模的应用都要组合多种技术才能满足要求：例如用 OLTP 数据库处理用户请求，用缓存加速常见请求，用全文索引处理搜索查询，再用数据仓库进行分析。每个系统都有自己的数据副本，并采用为自身用途优化的表示形式。
双写：数据发生变化时，应用代码显式写入每个系统，例如先写数据库，再更新搜索索引，最后使相应的缓存项失效（也可能并发执行这些写入）。
变更数据捕获（change data capture，CDC）越来越受关注。它是这样一个过程：观察写入数据库的所有数据变化，将其提取成可以复制到其他系统的形式28。如果变化一经写入就立即以流的形式提供出来，CDC 尤其有用。
开源项目 Debezium 正是为解决这些问题而生。它为 MySQL、PostgreSQL、Oracle、SQL Server、Db2、Cassandra 以及其他许多数据库提供了 源连接器。这些连接器接入数据库复制日志，以标准事件模式呈现其中的变化；随后便可转换消息并将其写入下游数据库。Kafka Connect 框架也为各种数据库提供了更多 CDC 连接器。Maxwell 通过解析 binlog 为 MySQL 提供类似功能29；GoldenGate 为 Oracle 提供类似功能；pgcapture 则面向 PostgreSQL。

即便 Cassandra 这类最终一致、基于法定人数的数据库，如今也支持变更数据捕获。正如 “线性一致性与仲裁” 中所述，客户端必须把写入持久化到多数节点，该写入才被视为可见。法定人数写入很难支持 CDC，因为没有唯一的权威数据源可供订阅；数据是否可见，取决于每个读取者选择的一致性级别。Cassandra 绕开了这个问题：它不提供统一的变更流，而是公开每个节点的原始日志段。消费数据的系统必须读取每个节点的原始日志段，再自行决定如何将其合并成一股流，做法很像法定人数读取者32。
更数据捕获与事件溯源
我们来比较一下变更数据捕获与事件溯源。与变更数据捕获相似，事件溯源也把应用状态的所有变化存成变更事件日志。两者最大的区别在于抽象层次不同：

在变更数据捕获中，应用以可变方式使用数据库，可以随意更新和删除记录。变更日志从数据库底层提取（例如解析复制日志），从而确保提取出的写入顺序与实际写入顺序一致，避免 图 12-4 中的竞态条件。

在事件溯源中，应用逻辑显式构建在写入事件日志的不可变事件之上。事件存储只允许追加，通常不鼓励或禁止更新、删除事件。事件旨在反映应用层发生的事情，而不是底层的状态变化。
内部模式与外部模式解耦的一种常见方法是采用 发件箱模式（outbox pattern）。发件箱是具有独立模式的表；CDC 系统对外公开这些表，而不是数据库中的内部领域模型35、36。这样，开发者便可按需修改内部模式，而保持发件箱表不变。这看起来像双写——它确实就是双写。不过，两次写入都留在同一个系统（数据库）中，可以出现在同一个事务里，因此发件箱避开了 “保持系统同步” 中讨论的问题。

不过，发件箱也有一些权衡。开发者仍须维护内部模式与发件箱模式之间的转换，这可能并不容易。发件箱还会增加数据库写入底层存储的数据量，可能引发性能问题。

只要持久存储变更日志，状态便可以重现。如果把事件日志视为权威记录系统，把所有可变状态都看作由它衍生而来，系统中的数据流就更容易推理。正如 Jim Gray 和 Andreas Reuter 在 1992 年所说39：

从根本上说，根本没有必要保留数据库；日志已经包含了全部信息。之所以要存储数据库（即日志末尾所对应的当前状态），只是为了提升检索操作的性能。

日志压实是衔接日志与数据库状态的一种方式：它只保留每条记录的最新版本，丢弃已经被覆盖的版本。

这些情况下，只在日志末尾追加一个事件，表示先前的数据应视为已删除，并不足够——你真正想做的是改写历史，假装那些数据从未写入。Datomic 把这种功能称为 切除（excision）47，Fossil 版本控制系统中也有一个类似概念，称为 排斥（shunning）48。
一种允许删除不可变数据的方法是 密码学粉碎（crypto-shredding）50：把将来可能需要删除的数据加密存储；需要清除时，忘掉加密密钥。加密后的数据仍然存在，但已经无人能够使用。从某种意义上说，这只是转移了问题：实际数据现在不可变了，存储密钥的地方却是可变的。

流与批处理作业有一个关键区别：流永远不会结束。

流处理的应用
长期以来，流处理一直用于监控：组织希望在特定事情发生时收到警报。例如：

欺诈检测系统需要判断信用卡的使用模式是否出现意外变化，并在信用卡可能被盗时将其冻结。

交易系统需要观察金融市场的价格变化，并按照指定规则执行交易。

制造系统需要监控工厂内机器的状态，一旦发生故障便迅速查明问题。

军事与情报系统需要追踪潜在侵略者的活动，发现攻击迹象时发出警报。

这类应用需要相当复杂的模式匹配与关联分析。不过，流处理也逐渐出现了其他用途。

复合事件处理
复合事件处理（complex event processing，CEP）是一种在 20 世纪 90 年代发展起来的事件流分析方法，特别适合需要搜索特定事件模式的应用52。正如正则表达式可以在字符串中搜索特定的字符模式，CEP 允许你指定规则，在流中搜索特定的事件模式。CEP 的实现包括 Esper、Apama 和 TIBCO StreamBase。Flink、Spark Streaming 等分布式流处理器也支持使用 SQL 对流执行声明式查询。

微批处理与检查点
一种解决办法是把流分成小块，把每一块当作一个微型批处理。这种方法称为 微批处理（microbatching），Spark Streaming 就采用了它74。批次通常约为一秒，这是性能权衡的结果：批次越小，调度与协调开销越大；批次越大，流处理器的结果变得可见之前，延迟就越长。

幂等性
我们的目标是丢弃所有失败任务的部分输出，以便能安全地重试，而不会生效两次。分布式事务是实现这个目标的一种方法；另一种方法是依靠 幂等性，正如 “持久化执行与工作流” 中所见80。

幂等操作可以执行多次，效果与只执行一次相同。例如，删除键值存储中的一个键是幂等的（再次删除不会产生进一步影响）；递增计数器却不是幂等的（再执行一次递增，值就增加了两次）。

失败后重建状态
任何需要状态的流处理过程——例如计数器、平均值、直方图等窗口聚合，以及连接所用的表和索引——都必须确保发生故障后能够恢复状态。

一种选择是把状态保存在远程数据存储中并进行复制，不过为每条消息查询一次远程数据库可能很慢。另一种选择是把状态保存在流处理器本地，再定期复制。这样，流处理器从故障中恢复时，新任务可以读取状态副本，继续处理而不丢失数据。
