这份笔记精准捕捉了《数据密集型应用系统设计》（DDIA）中最核心的架构演进与数据工程理念。以下对这些知识点进行了系统性的重组与逻辑分类，并在关键概念处做了适当的补充和扩展，以便于建立更完整的知识体系。

---

## 一、 数据系统的基本组件与职责

现代应用极少由单一的数据存储满足所有需求，通常会组合多种不同的数据系统，每个系统承担特定的职责：

*   **数据库（Database）：** 存储数据，作为权威的持久化记录，以便日后能可靠地再次找到。
*   **缓存（Cache）：** 记住开销昂贵（如复杂计算或跨网络获取）的操作结果，以空间换时间，加快读取速度。
*   **搜索索引（Search Index）：** 允许用户按关键字检索数据，或进行复杂的多维过滤。
*   **流处理（Stream Processing）：** 面向无界数据，在事件和数据变更发生后**实时或准实时**地进行捕获和处理。
*   **批处理（Batch Processing）：** 面向有界数据，定期（如每天、每小时）处理累积的大批量数据。

---

## 二、 核心数据处理模式：OLTP 与 OLAP

随着数据量的增长和团队分工的细化，数据系统在处理模式上产生了明确的分化。

**事务（Transaction）**：在数据库语境中，指构成一个逻辑单元的一组读写操作，并非仅指金融交易。

| 属性 | 事务型系统（OLTP） | 分析型系统（OLAP） |
| :--- | :--- | :--- |
| **全称** | 联机事务处理（Online Transaction Processing） | 联机分析处理（Online Analytical Processing） |
| **主要使用者** | Web/移动应用的最终用户，或机器级验证服务 | 业务分析师、数据科学家、管理层 |
| **主要读取模式** | **点查询**（按主键读取单条或少量记录） | **大规模聚合**（扫描大量记录，计算统计值） |
| **主要写入模式** | 随机写入，创建、更新和删除单条记录 | **批量导入（ETL）**或持续的事件流写入 |
| **数据表示含义** | 数据的最新状态（当前时间点的快照） | 一段时间内发生的事件历史（强调不可变性） |
| **查询模式** | 由应用代码预先定义的固定查询集 | 探索性分析，分析师可按需编写任意复杂查询 |
| **数据集规模** | GB 至 TB 级别 | TB 至 PB 级别 |
| **代表机器行为** | 检查操作权限、扣减库存余额 | 检测欺诈行为、推荐系统特征提取、业务报表生成 |

### 团队角色与职责边界
*   **数据工程师（Data Engineer）：** 负责搭建“桥梁”。专注于数据基础设施的建设，解决数据管道（Pipeline）问题，将分布在各个 OLTP 系统中的数据安全、高效地集成到分析型系统中。
*   **分析工程师（Analytics Engineer）：** 介于数据工程和业务分析之间。负责在数仓内部对清洗后的数据进行建模和转换，构建宽表或星型模型，使其更易于数据科学家和业务人员使用。

## 三、 数据架构的演进：从孤岛到湖仓一体

直接在 OLTP 数据库上运行复杂的分析查询会导致严重的性能灾难（锁竞争、资源耗尽），同时面临**数据孤岛**（难以跨系统联合查询）和安全合规限制。为了解决这些问题，数据架构经历了几个阶段的演进：

1.  **数据仓库与 ETL：**
    *   通过 **ETL（提取-转换-加载）** 流程，将 OLTP 系统中的数据定期同步到专门优化的**数据仓库**。
    *   数据在入仓前会被强制转换为统一的模式（Schema-on-write），适合结构化分析（如星型或雪花型模式）。
2.  **数据湖（Data Lake）：**
    *   **痛点应对：** 随着非结构化数据和机器学习的兴起，传统数仓显得僵化且昂贵。
    *   **核心理念（寿司原则）：** “原始数据更好”。数据湖是一个集中式存储库，保存事务型系统的全量数据副本。它不强制规定数据模型或格式（Schema-on-read），消费者可以按需自行转换。
3.  **数据湖仓（Lakehouse）：**
    *   融合了数据湖的灵活性与数仓的事务性。在数据湖的底层文件（如 Parquet）之上，增加元数据管理层、ACID 事务支持和查询执行引擎。
4.  **HTAP（混合事务/分析处理）：**
    *   试图在同一个底层系统上同时支持高并发 OLTP 和复杂 OLAP，通过内存列存副本等技术，减少 ETL 延迟。

## 四、 系统的源头与云原生演进

### 1. 数据的来源分类
*   **权威记录系统（System of Record）：** 也称单一事实来源（Single Source of Truth）。它是数据的诞生地，保存数据的规范版本。
*   **衍生数据系统（Derived Data System）：** 数据是基于另一个系统的数据经过转换、聚合处理得来的。**缓存、搜索索引、数据仓库、物化视图均属于衍生系统。** 其核心特征是：即使数据丢失，也可以随时从源系统重新计算恢复。

### 2. 部署形态：自托管 vs 云原生
云原生架构专为利用云的弹性伸缩、存算分离和托管服务而设计。Serverless（无服务器）模式进一步将按量计费精细化到了代码执行时间，极大降低了运维心智负担。

| 类别 | 传统/自托管系统 | 现代云原生系统（按需扩展，存算分离） |
| :--- | :--- | :--- |
| **事务型/OLTP** | MySQL, PostgreSQL, MongoDB | AWS Aurora, Google Cloud Spanner |
| **分析型/OLAP** | Teradata, ClickHouse (自建), Spark | Snowflake, Google BigQuery, Databricks |

## 五、 分布式系统架构设计与衡量指标

把单一庞大的系统拆分为由多台机器通过网络通信协作的系统，即为**分布式系统**。微服务架构正是这种 SOA（面向服务架构）思想的现代演进。

系统设计的首要逻辑是：**存储和计算数据的价值，必须高于其成本。**

### 1. 非功能性需求的“三大支柱”
*   **可靠性（Reliability）：** 系统在面临硬件故障、软件错误或人为失误时，仍能继续正确运行。
*   **可伸缩性（Scalability）：** 当系统面临更大的负载（数据量、流量、复杂性）时，增加计算或存储资源能够显著、成比例地提高系统的处理能力。
*   **可维护性（Maintainability）：** 软件生命周期的大部分成本在于维护。
    *   *可运维性：* 良好的可观测性（监控、日志、链路追踪），便于团队保持系统平稳运行。
    *   *简单性：* 采用一致的抽象和**设计模式**，避免偶发复杂度，降低新人的认知负荷。
    *   *可演化性：* 系统易于修改，能够敏捷地适应未知的业务需求变化。

### 2. 性能与延迟的细微差别
DDIA 对时间的定义极其严谨，这是排查性能瓶颈的关键：

*   **服务时间（Service Time）：** 机器/服务真正用于处理用户请求所需的时间。
*   **排队延迟（Queueing Delay）：** 请求到达后处于等待状态的时间（如等待 CPU 分配、等待网络缓冲区）。高负载时，请求往往受阻于**队头阻塞（Head-of-line blocking）**。
*   **网络延迟（Latency）：** 泛指请求和响应在网络中传输、潜伏的时间（与处理无关）。
*   **响应时间（Response Time）：** = `服务时间` + `排队延迟` + `网络延迟`。这是**客户端实际感知到**的总耗时。

### 3. 指标衡量与尾部延迟
*   **吞吐量（Throughput）：** 系统每秒处理的请求数或数据量。由于排队效应，吞吐量逼近上限时，响应时间会急剧上升。
*   **百分位数：** 平均值掩盖了异常波动，**中位数（p50）**更能反映普通用户的体验。而**高分位数（如 p95, p99）**被称为**尾延迟（Tail Latencies）**。
*   **尾部延迟放大：** 在微服务架构（扇出机制）中，只要一条调用链路上有一个服务触发了尾延迟，整个客户端请求就会变慢。

## 六、 高并发下的稳定性与扩展方案

### 1. 流量风暴与亚稳态故障
当系统负载过高导致超时，客户端如果不加控制地重试，会引发**重试风暴（Retry Storm）**。即使实际用户流量下降，系统也会因为内部重试一直处于过载的“死亡螺旋”中，称为**亚稳态故障（Metastable Failure）**。

**防御手段：**
*   **客户端侧：** 指数退避（Exponential Backoff）加随机抖动（Jitter），熔断器（Circuit Breaker）暂停向故障节点发请求。
*   **服务端侧：** 负载卸除（Load Shedding，主动丢弃低优先级请求），背压（Backpressure，要求上游限流），以及使用令牌桶等算法进行限流。

### 2. 读写放大的权衡：物化视图
*   **扇出（Fan-out）：** 指单个输入请求需要放大为多少个后端请求，或需要更新多少条记录。
*   **物化（Materialization）：** 预先计算并持久化查询结果（如社交网络的时间线缓存）。它是经典的“空间换时间”和“写入成本换读取性能”的策略。

### 3. 硬件扩展架构的演进
*   **共享内存架构（Scale-up/垂直扩展）：** 多 CPU 共享同一块 RAM，受限于硬件物理瓶颈和指数级增长的成本。
*   **共享磁盘架构：** 独立的 CPU/RAM，通过高速网络共享磁盘阵列（多见于传统商用数据库）。
*   **无共享架构（Shared-nothing / 向外扩展 Scale-out）：** 现代分布式系统的主流。每个节点是独立的机器，拥有自己的 CPU、内存和磁盘，节点间通过普通网络协调。通过数据分片和副本机制，实现理论上的线性伸缩。

### 4. 应对复杂度的终极武器：抽象
在代码和架构层面，管理复杂度的最佳方式是**抽象（Abstraction）**。通过**领域驱动设计（DDD）**和合理的接口封装，将实现细节隐藏在干净的外观之下，是构建高可维护性系统的基石。


# 深入解析数据模型与查询语言

对于每层数据模型，其核心的关键问题始终是：**它是如何用低一层数据模型来“表示”的？**
一个模型可以用另一个模型来模拟（例如在关系型数据库中存储图数据），但结果往往十分笨拙。因此，针对不同的数据关联特征，选择合适的原生数据模型至关重要。

---

## 一、 关系模型与文档模型（The Great Debate）

关系模型与文档模型的对比，是数据库领域最经典的讨论之一。其核心分歧在于如何处理数据之间的关联以及模式的严格程度。

### 1. 核心概念对比
*   **关系模型（SQL）：** 数据被组织成“关系”（表 Table），每个关系由无序的“元组”（行 Row）构成。擅长处理多对一（N:1）和多对多（M:N）关系。
*   **文档模型（NoSQL）：** 数据通常以 JSON 等格式呈现。最初由 MongoDB 等推广，主打局部性（Local locality）和模式灵活性。适合一对多（1:N）的树状嵌套结构。

### 2. 阻抗不匹配与 ORM
*   **阻抗不匹配（Impedance Mismatch）：** 应用程序通常使用面向对象编程，而数据库使用关系模型，两者之间的脱节被称为“阻抗不匹配”。
*   **对象关系映射（ORM）：** 框架（如 ActiveRecord, Hibernate, MyBatis）应运而生，旨在减少内存对象与持久化关系数据之间转换的样板代码。但也常常因为屏蔽了底层 SQL 逻辑、导致复杂查询性能低下而遭到批评。

### 3. 规范化 vs 反规范化
实质上是在决定：**是存储 ID 还是存储文本字符串？**

| 属性 | 规范化（Normalization / 存 ID） | 反规范化（Denormalization / 存全量文本） |
| :--- | :--- | :--- |
| **数据冗余** | 无冗余，信息只存一份，其他地方用 ID 引用。 | 数据存在多个副本。 |
| **读取性能** | 较慢（往往需要多表 Join 连接）。 | 较快（信息自包含，无需跨表）。 |
| **写入性能** | 较快（只需更新一处）。 | 较慢（需更新所有副本，且占用更多空间）。 |
| **适用场景** | 多对一、多对多关系。 | 强局部性、一次性读取整个文档的场景。 |

### 4. 模式（Schema）管理的本质差异
非关系型数据模型常被误认为“没有模式”（Schemaless），但这并不准确。任何应用在读取数据时都隐含了对数据结构的假设。
*   **写时模式（Schema-on-write）：** 关系数据库的传统做法。模式是明确的，数据库在写入时强制校验，犹如强类型编程语言。
*   **读时模式（Schema-on-read）：** 文档数据库的典型做法。数据结构是隐含的，写入时不校验，只有在读取时应用程序才去解释数据，犹如动态类型语言。这使得应用更容易适应不断变化的需求。

---

## 二、 分析型数据模型：数据仓库架构

数据仓库通常采用关系模型，但为了满足复杂的分析聚合需求，衍生出了特定的建模惯例。

### 1. 星型模式（Star Schema）
*   **事实表（Fact Table）：** 位于中心，每一行代表一个发生的事件（如一笔订单、一次点击）。通常体积巨大。
*   **维度表（Dimension Table）：** 环绕在事实表周围，代表事件发生的对象、时间、地点、原因等属性。事实表通过外键指向维度表。
*   **视觉呈现：** 事实表在中央，连接周围维度表的线条形如星星的光芒。

### 2. 其他模式
*   **雪花模式（Snowflake Schema）：** 星型模式的变体，其中的维度表进一步被规范化，分解成子维度（例如：将“城市”维度进一步拆分出“国家”维度表）。
*   **一张大表（OBT - One Big Table）：** 极度反规范化的做法，牺牲存储空间换取极致的查询速度。

---

## 三、 图数据模型（Graph Data Models）

当数据中多对多（M:N）关系变得极为普遍且高度关联时，图数据模型是最佳选择。
*   **应用场景：** 社交网络、知识图谱、路径导航、推荐系统。
*   **主要流派：** 属性图（Property Graphs）和三元组存储（Triple Stores）。

### 1. 属性图模型 (Property Graph)
由 Neo4j、Memgraph 等实现。
*   **顶点（Vertex / Node）：** 包含唯一 ID、标签（类型）、属性（键值对）以及入边和出边集合。
*   **边（Edge / Relationship）：** 包含唯一 ID、起点（尾部顶点）、终点（头部顶点）、标签（关系类型）以及属性（键值对）。
> *注：用图遍历数据时，邻接表（Adjacency List）适合图遍历查询，而邻接矩阵（Adjacency Matrix）更适合机器学习计算。*

### 2. 三元组存储 (Triple Store) & 语义网
所有信息都以极简的 **（主语，谓语，宾语）** 三部分陈述来存储。
*   例如：`(Jim, 喜欢, 香蕉)`。
*   **RDF：** 专为语义网设计的数据模型。
*   **SPARQL：** 面向 RDF 的查询语言（读作 "sparkle"）。

### 3. 用 SQL 查询图数据的痛苦（为什么要用专门的图数据库？）
如果将图的顶点和边强行存在关系数据库（两张表）中，使用 SQL 查询长度未知的图遍历路径（如“找出既在美国出生又在欧洲居住的人”），需要使用复杂的 **递归公用表表达式（`WITH RECURSIVE`）**：

```sql
-- SQL 的笨拙实现：冗长、极难阅读、维护成本极高
WITH RECURSIVE
    in_usa(vertex_id) AS (
        SELECT vertex_id FROM vertices WHERE label = 'Location' AND properties->>'name' = 'United States'
      UNION
        SELECT edges.tail_vertex FROM edges JOIN in_usa ON edges.head_vertex = in_usa.vertex_id WHERE edges.label = 'within'
    ),
    -- ... (省略极其冗长的 in_europe, born_in_usa, lives_in_europe 递归定义)
SELECT vertices.properties->>'name'
FROM vertices
JOIN born_in_usa ON vertices.vertex_id = born_in_usa.vertex_id 
JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;
```

**而使用图专门的声明式查询语言 Cypher，逻辑清晰得如同画图：**

```cypher
// Cypher 的优雅实现：直观、紧凑
MATCH
    (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (:Location {name:'United States'}),
    (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name
```
> *注：为了统一图查询生态，目前正在推进将 GQL（Graph Query Language）加入 SQL 标准。*

## 四、 声明式查询语言的力量

SQL、Cypher、SPARQL 甚至数据处理的 Datalog 都是**声明式（Declarative）**查询语言。
*   **声明式 vs 命令式（Imperative）：** 声明式语言只需要你指定**“想要什么结果”**及满足的条件，而无需指定**“计算机该如何去一步步实现”**。
*   **优势：** 数据库优化器可以自由决定最佳的执行计划（使用什么索引、按什么顺序 Join），且更容易在多核或集群架构下实现并行化运算，而不影响业务代码。

## 五、 其他前沿模型：事件与数据框

### 1. 事件溯源（Event Sourcing）与 CQRS
*   **事件溯源：** 将数据的每次状态变化（Update/Delete）都记录为不可变的“事件”追加到日志中，把“事件流”作为权威的单一事实来源。
*   **CQRS（命令查询责任分离）：** 从只追加的事件日志（写入优化）中，异步派生出独立的视图（读取优化）。这源于领域驱动设计（DDD）思想，本质是维护两个或多个不同的数据模型以适应读写的分离。

### 2. 数据框（Dataframes）
*   **应用场景：** 数据科学家和机器学习的核心工具（如 Python 的 Pandas，大数据的 Spark DataFrames）。
*   **定位：** 在关系数据库与多维数组（矩阵计算）之间架起的桥梁。
*   **操作方式：** 区别于 SQL 的一步声明到位，数据框通常通过一系列命令式 API 逐步（Step-by-step）对数据进行“清洗”和转换。

# 数据库存储引擎与检索机制核心解析

任何类型的索引都会在读取和写入之间进行权衡：**索引可以极大地加快读取速度，但通常会拖慢写入速度**，因为每次写入数据时，都必须同步更新底层的索引结构。

在 OLTP（联机事务处理）领域，存储引擎主要分为两大思想流派：**日志结构（Log-Structured）** 和 **就地更新（In-Place Update）**。

---

## 一、 流派一：日志结构与 LSM 树 

日志结构学派的核心理念是：**只允许向文件追加数据（顺序写）和删除过时文件，从不修改已经写出的文件。** 典型代表：RocksDB, Cassandra, HBase, Lucene。

### 1. 核心组件与写入流程
*   **内存表（Memtable）：** 收到写入请求时，数据首先被插入到内存中的有序树结构（如红黑树、跳表）。这保证了写入的极速，同时也维护了键的有序性。
*   **排序字符串表（SSTable）：** 当 Memtable 达到一定阈值（如几 MB）时，将其按键排序后刷入磁盘，成为一个新的 SSTable 段文件。SSTable 具有不可变性。
*   **稀疏索引：** 由于 SSTable 是按键排序的，不需要在内存中保存所有键的索引，只需保存每个数据块（通常几 KB）第一个键的位置即可，这被称为“稀疏索引”。
*   **崩溃恢复（WAL）：** 为防止断电丢失 Memtable 中的数据，系统会维护一个仅追加的日志文件，每次写入先记录日志。Memtable 落盘后，对应日志即可截断。

### 2. 读取机制与优化
读取时，系统会依次查询：`Memtable -> 最新的 SSTable -> 更旧的 SSTable`。
*   **布隆过滤器（Bloom Filter）：** 为了防止读取一个不存在的键而遍历所有底层文件（极其缓慢），引擎会为每个 SSTable 配置布隆过滤器。它可以快速判断一个键“绝对不存在”或“可能存在”。假阳性无害，只会导致多查一次磁盘。

### 3. 后台清理：压实（Compaction）
如果不断追加，磁盘终将耗尽。后台会运行合并与压实过程，类似于“多路归并排序”，合并多段记录并丢弃旧值。删除操作则是写入一个特殊的**墓碑（Tombstone）**标记，在压实期间真正清除数据。
*   **按大小分层压实（Size-tiered）：** “小文件攒一堆，一次性合并成大文件”。写入友好，能应对极高写入吞吐量，但合并时极其耗费 IO 和临时磁盘空间。
*   **分级压实（Leveled）：** 将数据分层级，每层按 Key Range 切分成极小的 SSTable。合并更加增量，查询更容易定位，但 Compaction 动作更频繁。

## 二、 流派二：就地更新与 B 树

B 树是应用最广泛的索引结构，是关系型数据库（如 MySQL/InnoDB, PostgreSQL）的基石。其核心理念是：**把磁盘划分为固定大小的页（Page/Block，通常为 4KB~16KB），并允许在原位置直接覆写数据。**

### 1. 核心机制
*   **树状页结构：** 每一页都有标识，页与页之间通过指针引用。树的深度通常极浅（O(log n)），一棵四层深的 B 树就能存储 250TB 数据。
*   **分裂与平衡：** 如果一页写满，就将其拆分成两个半满的页，并更新父节点。这保证了树始终保持平衡。
*   **预写日志（WAL）：** 就地更新（特别是分裂页时）是非常危险的。如果崩溃可能导致“孤儿页”或“页撕裂”。因此 B 树也必须先将修改写入 WAL，再刷入树页本身，以便崩溃恢复。

### 2. B 树的碎片化
随着数据的不断删除和更新，B 树会产生空闲的碎片页，这些页面位于文件中间，难以归还给操作系统。虽然以后可以复用，但会降低空间利用率，需要数据库定期进行“碎片整理”。

## 三、 LSM 树 vs B 树的巅峰对决

| 维度 | LSM 树 (如 RocksDB) | B 树 (如 MySQL InnoDB) |
| :--- | :--- | :--- |
| **主要写入模式** | 顺序写入（追加） | 随机写入（就地覆写） |
| **写入吞吐量** | **极高**（更适合写入密集型工作负载） | 较高（受限于随机 IO 瓶颈） |
| **读取吞吐量** | 较高（需检查多层 SSTable） | **极高**（性能稳定可预测） |
| **写放大** | **较低**（只重写有效数据，且压缩率高） | **较高**（改一个字节也要重写整页 16KB+WAL） |
| **磁盘碎片化** | 极少（压实过程天然整理了碎片） | 严重（随时间推移页面内部产生空洞） |
| **并发控制机制** | 相对简单（不可变文件避免了复杂锁竞争） | 复杂（涉及行锁、页锁、间隙锁） |

> **SSD 的硬件特性影响：** 现代固态硬盘（SSD）每次只能按块（Block，如 512KB）进行擦除垃圾回收（GC）。LSM 树的大块顺序写入对 SSD 更加友好，而 B 树频繁的随机页更新会加剧 SSD 的写放大与硬件磨损。

## 四、 复杂检索：全文、空间与向量

除了基于键值匹配的查询，现代数据库还支持高维度的复杂检索。

1.  **多列联合索引：** 将一列接在另一列之后组合成键，顺序极为重要。
2.  **空间索引（地理位置）：** 常规 B 树无法高效处理 `(x, y)` 二维坐标查询。通常使用 **空间填充曲线** 将二维转一维，或使用专用的 **R 树（R-Tree）** 索引。
3.  **全文检索（Lucene/Elasticsearch）：** 本质上是处理庞大维度的布尔查询。把搜索转换为“包含词项 X 位图”与“包含词项 Y 位图”的**按位与运算**。使用类似字典树的**莱文斯坦自动机**来支持容错（拼写错误、模糊匹配）。
4.  **向量嵌入（Vector Embeddings）：** 语义搜索的基石。将文本转为多维浮点数空间中的一个点。查询本质是在寻找“距离最近的点”。
    *   **平面索引（Flat）：** 暴力比对，百分百精确但速度极慢。
    *   **IVF 索引（倒排文件）：** 将空间划分为多个聚类（质心）。先找目标落入哪个分区，再在分区内查找。是一种牺牲精度换取速度的近似搜索。
    *   **HNSW 索引（分层可导航小世界）：** 维护多层结构图，从顶层稀疏图开始粗略定位，逐层向下进入底层密集图精确查找。目前向量数据库（如 Faiss, pgvector）的主流算法。

## 五、 分析型存储（OLAP）的核心优化

数据仓库针对需要扫描海量记录的复杂聚合查询进行了专门的优化。

### 1. 行式存储 vs 列式存储
*   **行式存储（Row-Oriented）：** OLTP 的标配，同一行的所有数据相邻存放。缺点是：如果一张宽表有 100 列，分析时只查其中 4 列，引擎依然要将整行 100 列全从磁盘载入内存，造成极大的 IO 浪费。
*   **列式存储（Column-Oriented）：** 将同一“列”的所有值相邻存放。查询时只需精确加载需要的列即可。由于按列单独存储，在还原为整行时，只需按照行号偏移量进行拼接。

### 2. 极致的列压缩
列式存储天然极度适合压缩。因为同一列的数据类型完全一致，且不同值的数量通常远小于总行数（例如几十亿条记录，商品类别只有几万个）。
*   **位图编码（Bitmap Encoding）：** 将一个列转换成 N 张独立位图。
*   **游程编码（Run-length Encoding）：** 如果位图极度稀疏（全是 0），可以直接记录连续出现 0 或 1 的数量（如 `0x1000, 1x1, 0x500`），进一步极大压缩体积。

### 3. 物化视图与聚合
*   **虚拟视图：** 只是 SQL 查询的宏替换（快捷方式），读取时会即时展开为底层查询。
*   **物化视图（Materialized Views）：** 是实际写入磁盘的查询结果副本。针对高频出现的 COUNT、SUM 等操作，使用**物化聚合**可以避免每次重新扫描原始海量数据，大幅提升报表加载速度。

# 数据编码、模式演化与数据流架构

系统间的数据交换不仅关乎运行效率，更深刻影响着应用程序的架构设计与未来的平滑演化。

## 一、 兼容性与数据表示基础

随着系统的演进，新旧代码往往需要同时运行，这要求数据格式具备良好的兼容性：
*   **向后兼容（Backward Compatibility）：** 较新的代码可以无缝读取由较旧代码写入的数据。
*   **向前兼容（Forward Compatibility）：** 较旧的代码可以无缝读取由较新代码写入的数据。

### 数据的两种存在形态
1.  **内存表示：** 数据保存在对象、结构体、树或哈希表等结构中。这些结构通常使用指针，专门针对 CPU 的高效访问进行了优化，但指针离开当前进程便失去意义。
2.  **传输/存储表示：** 若要将数据写入文件或通过网络发送，必须将其转换为自包含的字节序列。
    *   **编码（序列化 / 编组）：** 从内存表示转换为字节序列。
    *   **解码（反序列化 / 解组）：** 从字节序列恢复为内存表示。

---

## 二、 文本格式的局限：JSON、XML 与 CSV

尽管 JSON、XML 和 CSV 具备人类可读性，但在实际工程中隐藏着一些不易察觉的痛点：

| 局限性维度 | 具体表现与案例 |
| :--- | :--- |
| **数值歧义与精度丢失** | XML/CSV 无法区分纯数字字符串与数值；JSON 不区分整数与浮点数。**大数处理风险：** 大于 2⁵³ 的整数在采用 IEEE 754 双精度的语言（如 JavaScript）中会失真。例如，X（Twitter）的 64 位帖子 ID 必须在 API 中同时以数值和字符串两种形式返回，以防客户端解析错误。 |
| **二进制数据支持差** | 文本格式缺乏对原生字节流的支持。常规的 Base64 编码绕过方案虽然可行，但会导致**数据体积膨胀 33%**。 |
| **模式（Schema）缺失或极其复杂** | CSV 完全没有模式，行列定义依赖应用层硬编码，且转义规则含糊。XML/JSON Schema 虽功能强大，但学习曲线陡峭，实现复杂。 |

---

## 三、 JSON 模式 (JSON Schema)

JSON Schema 已成为 Web 服务（如 OpenAPI）和数据库（如 PostgreSQL、MongoDB）中广泛采用的数据建模标准。

*   **内容模型策略：**
    *   **开放内容模型（默认）：** 允许出现未定义的任意字段（`additionalProperties: true`）。它主要用于定义“不允许出现什么”（无效值），而非穷举“允许出现什么”。
    *   **封闭内容模型：** 只允许出现显式定义的字段。
*   **演化挑战：** JSON Schema 支持正则约束（`patternProperties`）、条件逻辑（if/else）和远程引用。这些强大的特性反而让模式定义变得庞杂，导致向前/向后兼容的演化充满挑战。

---

## 四、 二进制编码与模式演化（Protobuf 与 Avro）

基于模式的二进制编码（如 Google 的 Protocol Buffers 和 Apache Avro）提供了比文本格式更优的性能与演化保障。

### 1. Protocol Buffers (Protobuf) 核心机制
*   **字段标签取代字段名：** 编码数据中不包含 userName 等字符串字段名，而是使用模式中定义的**数字标签（1, 2, 3）**。这大幅压缩了数据体积。
*   **变长整数（Varint）：** 根据数字大小动态分配字节数（如小数字仅占 1 字节），进一步节省空间。
*   **列表表示：** 没有显式数组类型，通过 `repeated` 修饰符让同一标签号在记录中重复出现。

### 2. Protobuf 的兼容性与演化规则
模式演化的核心在于**字段标签号绝对不能修改**：
*   **向前兼容：** 新增字段分配新标签号。旧代码遇到不认识的新标签时，可依靠类型注解计算长度并跳过，同时保留该未知字段。
*   **向后兼容：** 新代码读取旧数据时，如果找不到新增加的标签号，会自动填入类型默认值（如空字符串、数值 0）。
*   **字段删除：** 废弃的标签号必须被标记为“保留（reserved）”，绝不能再次分配给新字段。

> **二进制编码的核心优势：**
> 1. 数据极其紧凑。
> 2. Schema 本身即是强制同步的说明文档。
> 3. 支持在部署前执行兼容性静态检查。
> 4. 支持静态类型语言的代码生成与编译时检查。

---

## 五、 数据流转架构与通信模式

数据在系统进程间的流动主要分为三种典型架构：

### 1. 远程过程调用（RPC）与服务路由
RPC 旨在提供**位置透明性**，让调用远程网络服务如同调用本地函数一样自然。其背后的负载均衡与服务发现机制包括：
*   **硬件 / 软件负载均衡器：** 专用设备或 Nginx/HAProxy 等软件，负责连接管理与故障转移。
*   **DNS 路由：** 简单易用，但受限于缓存延迟，无法敏捷应对实例的频繁上下线。
*   **服务发现系统：** 集中式注册表。服务实例主动注册并发送心跳，客户端查询可用列表后直连端点。适合动态环境。
*   **服务网格（Service Mesh）：** 如 Istio、Linkerd。通过“边车（Sidecar）”代理接管本地流量，透明化处理 TLS 加密，并提供强大的调用链路追踪与流量监控。

### 2. 工作流引擎（Workflow Engines）
通常由**编排器（调度）**与**执行器（运行任务）**组成。
*   **数据 / ETL 编排：** Airflow、Dagster、Prefect。
*   **可视化业务编排：** Camunda、Orkes（支持 BPMN 标准）。
*   **持久化执行引擎：** Temporal、Restate（保障长时间运行任务的状态不丢失）。

### 3. 事件驱动架构与消息代理
与 RPC 的同步等待不同，事件驱动采用异步通信。
*   **消息代理（Message Broker）：** 请求（事件/消息）先发送至中间件暂存，接收者异步消费。
*   **常见实现：** Kafka、RabbitMQ、ActiveMQ，以及云原生的 AWS Kinesis、GCP Pub/Sub 等。

### 4. 分布式 Actor 模型
*   **Actor 模型：** 一种单进程并发的编程范式。将状态与逻辑封装在 Actor 内部，通过互相发送异步消息进行通信，从根本上避免了多线程死锁与竞态条件。分布式 Actor 框架将其扩展到了跨网络多节点环境。


数据库分布到多台机器上：

可伸缩性
如果你的数据量、读取负载、写入负载超出单台机器的处理能力，可以将负载分散到多台计算机上。
容错 / 高可用性
如果你的应用需要在单台机器（或多台机器，网络或整个数据中心）出现故障的情况下仍然能继续工作，则可使用多台机器，以提供冗余。一台故障时，另一台可以接管。
延迟
如果在世界各地都有用户，你也许会考虑在全球范围部署多个服务器，从而每个用户可以从地理上最近的数据中心获取服务，避免了等待网络数据包穿越半个世界。
许多处理器，内存和磁盘可以在同一个操作系统下相互连接，快速的相互连接允许任意处理器访问内存或磁盘的任意部分。在这种 共享内存架构（shared-memory architecture）
在大型机中，尽管任意处理器都可以访问内存的任意部分，但总有一些内存区域与一些处理器更接近（称为 非均匀内存访问（nonuniform memory access, NUMA） 1）。为了有效利用这种架构特性，需要对处理进行细分，以便每个处理器主要访问临近的内存，这意味着即使表面上看起来只有一台机器在运行，分区（partitioning） 仍然是必要的。
共享内存方法的问题在于，成本增长速度快于线性增长：一台有着双倍处理器数量，双倍内存大小，双倍磁盘容量的机器，通常成本会远远超过原来的两倍。而且可能因为存在瓶颈，并不足以处理双倍的载荷。
共享磁盘架构（shared-disk architecture），它使用多台具有独立处理器和内存的机器，但将数据存储在机器之间共享的磁盘阵列上，这些磁盘通过快速网络连接。这种架构用于某些数据仓库，但竞争和锁定的开销限制了共享磁盘方法的可伸缩性

无共享架构 3（shared-nothing architecture，有时被称为 水平伸缩，即 horizontal scaling，或 向外伸缩，即 scaling out）已经相当普及。 在这种架构中，运行数据库软件的每台机器 / 虚拟机都称为 节点（node）。每个节点只使用各自的处理器，内存和磁盘。节点之间的任何协调，都是在软件层面使用传统网络实现的。

数据分布在多个节点上有两种常见的方式：

复制（Replication）
在几个不同的节点上保存数据的相同副本，可能放在不同的位置。复制提供了冗余：如果一些节点不可用，剩余的节点仍然可以提供数据服务。复制也有助于改善性能。第六章 将讨论复制。
分区 (Partitioning)
将一个大型数据库拆分成较小的子集（称为 分区，即 partitions），从而不同的分区可以指派给不同的 节点（nodes，亦称 分片，即 sharding）。第七章 将讨论分区。
复制和分区是不同的机制，但它们经常同时使用

复制 意味着在通过网络连接的多台机器上保留相同数据的副本。正如 “分布式与单节点系统” 中所讨论的，我们希望复制数据，可能出于以下原因：

使数据在地理上更接近用户（从而降低访问延迟）
即使系统的一部分发生故障，系统仍能继续工作（从而提高可用性）
增加能够处理读查询的机器数量（从而提高读取吞吐量）
复制的全部难点都在于处理被复制数据的 变更
复制变更的算法：单主复制、多主复制 和 无主复制。几乎所有分布式数据库都采用其中一种。三者各有利弊

其中一个副本被指定为 领导者（也称 主库 或 源 2）。客户端要写入数据库时，必须把请求发给领导者；领导者首先将新数据写入本地存储。
其他副本称为 追随者（也称 只读副本、备库 或 热备）。领导者每次把新数据写入本地存储，也会把数据变更作为 复制日志 或 变更流 发送给所有追随者。每个追随者取得领导者的日志，按照领导者处理写入的相同顺序应用所有写入，从而更新本地的数据库副本。
客户端读取数据库时，可以查询领导者，也可以查询任意追随者；但只有领导者接受写入（从客户端的角度看，追随者是只读的）。
如果数据库做了分片（见 第 7 章），每个分片都有一个领导者。不同分片的领导者可以位于不同节点，但每个分片仍必须有且只有一个领导者。在 “多主复制” 中
单主复制应用极为广泛。它是 PostgreSQL、MySQL、Oracle Data Guard 3 和 SQL Server Always On 可用性组 4 等许多关系数据库的内置功能；MongoDB、DynamoDB 5 等文档数据库，Kafka 等消息代理，DRBD 等复制块设备，以及一些网络文件系统也采用这种方式。Raft 等许多共识算法同样以单个领导者为基础；CockroachDB 6、TiDB 7、etcd、RabbitMQ 法定人数队列等系统用它来实现复制，并在原领导者失效时自动选举新领导者
同步复制的优点是，追随者保证拥有与领导者一致的最新数据副本。领导者突然失效时，可以确信数据仍可从追随者取得。缺点是，如果同步追随者没有响应——无论因为崩溃、网络故障还是其他原因——写入就无法继续。领导者必须阻塞所有写入，直至同步副本重新可用。
实践中，数据库所谓的同步复制，通常是指 一个 追随者同步，其余追随者异步。如果同步追随者不可用或过慢，就把某个异步追随者切换为同步。这样可以保证至少有两个节点持有最新数据：领导者和一个同步追随者。这种配置有时也称为 半同步。
从概念上讲，其过程如下：

取得领导者数据库在某个时刻的一致快照；如果可能，不要锁住整个数据库。大多数数据库都提供这一功能，因为备份同样需要它。有些情况下需要借助第三方工具，例如 MySQL 的 Percona XtraBackup。
把快照复制到新的追随者节点。
追随者连接领导者，请求从快照生成之后发生的所有数据变更。这要求快照与领导者复制日志中的准确位置相关联。不同系统对这个位置有不同称呼：PostgreSQL 称之为 日志序列号；MySQL 则有 binlog 位点 和 全局事务标识符（GTID）两套机制。
追随者处理完快照之后积压的数据变更时，就称它已经 赶上进度。此后，它可以继续随时处理领导者产生的数据变更。
如何用基于领导者的复制实现高可用？
追随者失效：追赶恢复
领导者失效：故障切换
必须把一个追随者提升为新领导者，重新配置客户端以便把写入发给新领导者，并让其他追随者开始消费新领导者的数据变更。这个过程称为 故障切换。
自动故障切换通常包括以下步骤：

确认领导者失效。 可能出问题的地方很多：崩溃、断电、网络故障等等。没有万无一失的办法判断究竟出了什么问题，因此大多数系统只是使用超时：节点之间频繁往返传递消息，如果某个节点在一段时间内（例如 30 秒）没有响应，就认为它已经失效。（因计划维护而主动下线领导者则不适用这一规则。）
选择新的领导者。 可以通过选举完成（由剩余副本中的多数选出领导者），也可以由事先指定的 控制器节点 任命 13。最合适的候选者通常是从旧领导者收到数据变更最多、数据最新的副本，这样可以尽量减少数据损失。让所有节点就新领导者达成一致是一个共识问题，第 10 章 将详细讨论。
重新配置系统以使用新领导者。 客户端现在必须把写请求发给新领导者（参见 “请求路由”）。如果旧领导者恢复上线，它可能仍以为自己是领导者，没有意识到其他副本已经迫使它退位。系统必须保证旧领导者转为追随者，并承认新领导者。
可能有两个节点都认为自己是领导者。这种情况称为 脑裂，非常危险：如果两个领导者都接受写入，而系统又没有冲突解决流程（参见 “多主复制”），数据很可能丢失或损坏。有些系统设有保险机制，一旦发现两个领导者便关闭其中一个节点；但机制设计不当时，也可能把两个节点都关闭 15。而且，等系统发现脑裂并关闭旧节点时，可能已经为时过晚，数据早已损坏。
通过限制或关闭旧领导者来防止脑裂，称为 栅栏（fencing）
复制日志的实现
基于语句的复制
最简单的情况下，领导者会记录自己执行的每个写入请求（即 语句），并把这份语句日志发送给追随者。对于关系数据库，这意味着每条 INSERT、UPDATE 或 DELETE 语句都会转发给追随者；每个追随者解析并执行这条 SQL 语句，就像它直接来自客户端一样。
MySQL 5.1 以前使用基于语句的复制。由于日志相当紧凑，如今有时仍会采用这种方式；不过默认情况下，只要语句中存在任何非确定性，MySQL 就会切换到稍后介绍的基于行的复制。VoltDB 也采用基于语句的复制，并要求事务必须是确定性的，以保证安全 16。然而，实践中很难确保确定性，因此许多数据库更倾向于其他复制方式。

预写日志（WAL）传输
我们在 第 4 章 中看到，B 树存储引擎需要预写日志才能可靠工作：每次修改都先写入 WAL，以便崩溃后把树恢复到一致状态。WAL 包含把索引和堆恢复到一致状态所需的全部信息，因此同一份日志也能用来在另一个节点上建立副本：领导者除了把日志写入磁盘，还通过网络把它发送给追随者。追随者处理日志后，就会构建出与领导者完全相同的文件副本。
PostgreSQL、Oracle 等数据库采用这种复制方式 17 18。其主要缺点是，日志在非常低的层次描述数据：WAL 记录了哪个磁盘块中的哪些字节发生变化。因此，复制与存储引擎紧密耦合。数据库从一个版本升级到另一个版本、存储格式随之改变时，通常无法在领导者和追随者上运行不同版本的数据库软件。

另一种方法是让复制和存储引擎使用不同的日志格式，从而使复制日志与存储引擎的内部实现解耦。这种复制日志称为 逻辑日志，以区别于存储引擎的（物理）数据表示。

关系数据库的逻辑日志通常由一系列记录组成，以行的粒度描述对数据库表的写入：

插入一行时，日志包含所有列的新值。
删除一行时，日志包含足以唯一标识被删行的信息，通常是主键；如果表没有主键，则需要记录所有列的旧值。
更新一行时，日志包含足以唯一标识被更新行的信息，以及所有列的新值（或者至少包含所有发生变化的列的新值）。
修改多行的事务会生成多条这样的日志记录，随后再跟一条表示事务已经提交的记录。MySQL 配置为基于行的复制时，除了 WAL 之外，还会维护一份称为 binlog 的独立逻辑复制日志。PostgreSQL 则把物理 WAL 解码成行插入、更新和删除事件，以实现逻辑复制 19。

如果停止写入并等待一段时间，追随者最终会赶上领导者，恢复一致。因此，这种现象称为 最终一致性

多主复制拓扑
最通用的是 图 6-7(c) 所示的 全对全 拓扑，每个领导者都会把写入发送给其他所有领导者。不过，实际系统也会采用限制更多的拓扑。例如在 环形拓扑 中，每个节点从一个节点接收写入，再把这些写入连同自己的写入转发给另一个节点。另一种常见拓扑呈 星形：指定一个根节点，由它把写入转发给所有其他节点。星形拓扑还可以推广成树形。

这也是一个因果关系问题，与 “一致前缀读” 中看到的情况相似。更新依赖先前的插入，因此必须保证所有节点先处理插入，再处理更新。仅仅给每次写入附加时间戳并不够，因为不能相信各节点的时钟同步得足以让领导者 2 正确排列这些事件（见 第 9 章）。

要正确排列这些事件，可以采用本章稍后介绍的 版本向量（见 “检测并发写入”）。不过，许多多主复制系统并未使用可靠的更新排序技术，因而容易遇到 图 6-8 所示的问题。如果使用多主复制，应当了解这些风险，仔细阅读文档，并充分测试数据库，确认它确实提供了你以为它会提供的保证。
这同样形成了多主架构：每个打开共享文件的浏览器标签页都是一个副本，对文件所作的更新会异步复制到其他打开该文件的用户设备上。即使应用程序不支持离线编辑，只要多个用户可以不等服务器响应便各自编辑，它就已经是多主系统。

离线编辑与实时协作需要相似的复制基础设施：应用程序必须捕获用户对文件作出的所有变更，在线时立即发给协作者，离线时则先保存在本地，稍后再发送。同时，应用程序还要接收协作者的变更，将其合并到用户的本地文件副本，并更新界面以显示最新版本。多个用户并发修改文件时，还可能需要用冲突解决逻辑合并这些变更。

支持这一过程的软件库称为 同步引擎。
处理写入冲突
多主复制最大的难题——无论是地理分布式的服务端数据库，还是终端用户设备上的本地优先同步引擎——都是不同领导者上的并发写入可能彼此冲突，需要解决。

冲突避免
一种策略是从一开始就避免冲突。例如，如果应用程序能确保某条记录的所有写入都经过同一个领导者，那么即使整个数据库采用多主复制，也不会产生冲突。

手动冲突解决

自动冲突解决
对许多应用程序而言，处理冲突的最佳方式，是用算法自动把并发写入合并成一致状态。自动冲突解决可以保证所有副本 收敛 到同一状态：只要处理过相同的一组写入，各副本的状态就相同，与写入到达的顺序无关。
自动冲突解决时，通常使用两类算法：无冲突复制数据类型（CRDT）46 和 操作变换（OT）47。二者的设计理念与性能特征不同，但都能自动合并前面提到的各种数据。

CRDT
大多数 CRDT 不使用索引，而是给每个字符分配唯一且不可变的 ID，再据此确定插入和删除位置。
OT
记录字符插入或删除位置的索引：“n”插入索引 0，“!”插入索引 3。然后两个副本交换操作。

此外，还有一个后台进程定期查找副本之间的数据差异，把缺失的数据从一个副本复制到另一个。
更一般地说，假设有 n 个副本，每次写入必须得到 w 个节点确认才算成功，每次读取则至少查询 r 个节点。（上述例子中，n = 3、w = 2、r = 2。）只要 w + r > n，读取时就有望得到最新值，因为所查询的 r 个节点中，至少有一个必然是最新的。遵守这些 r、w 取值的操作称为 仲裁读 和 仲裁写 50。可以把 r 和 w 看作一次读或写要成立所需的最低票数。
通常，读写请求总会并行发送到全部 n 个副本。参数 w 和 r 决定要等待多少个节点，也就是在判定读或写成功之前，n 个节点中必须有多少个报告成功。
r 和 w 通常取节点的多数（多于 n/2），因为这样既能保证 w + r > n，又能容忍最多 n/2（向下取整）个节点失效。
因此，仲裁看似保证读取返回最近写入的值，实际却没有那么简单。Dynamo 风格数据库通常针对能够容忍最终一致性的场景优化。参数 w 和 r 可以调节读到陈旧值的概率 53，却不宜被当作绝对保证。

单主与无主复制的性能
基于单个领导者的复制系统能够提供强一致性保证，而无主系统很难甚至不可能做到。
Cassandra 和 ScyllaDB 在常规无主模型中实现多地区支持：客户端把写入直接发往所有地区的副本，并可选择多种一致性级别，规定请求至少得到多少响应才算成功。例如，可以要求所有地区的全部副本共同组成一个法定人数，也可以要求每个地区各自组成法定人数，或只要求客户端所在地区达到法定人数。本地法定人数无需等待其他地区的慢请求，但也更容易返回陈旧结果。

为了达到最终一致，各副本必须收敛到同一个值。可以采用 “处理写入冲突” 中讨论过的任意冲突解决机制，例如 Cassandra 和 ScyllaDB 使用的最后写入者胜、手工解决，或 “CRDT 与操作变换” 中介绍且 Riak 使用的 CRDT。
最后写入者胜很容易实现：给每次写入附加时间戳，时间戳较大的值总是覆盖较小的值。但时间戳无法告诉你两个值究竟是否冲突：它们可能是并发写入的，也可能先后写入。如果要显式解决冲突，系统必须更仔细地检测并发写入。
事实上，只要两个操作谁也不先发生于另一个——也就是说，谁都不知道对方——就可以称它们 并发 57。

复制的目标看似简单——在多台机器上保留相同数据的副本——实际却极其棘手。它要求我们仔细考虑并发、所有可能出错的环节，以及怎样应对故障造成的后果。至少要处理节点不可用和网络中断，而且这还没有算上软件缺陷或硬件错误引起的静默数据损坏等更隐蔽的故障。

我们讨论了三种主要的复制方式：

单主复制
客户端把所有写入发给一个节点（领导者），领导者再把数据变更事件流发送给其他副本（追随者）。读取可以在任意副本上执行，但追随者返回的结果可能陈旧。
多主复制
客户端把每次写入发给多个领导者中的一个，任意领导者都能接受写入。各领导者相互发送数据变更事件流，也会将其发送给追随者。
无主复制
客户端把每次写入发给多个节点，并行读取多个节点，从而发现并修复持有陈旧数据的节点。
每种方式都有优缺点。单主复制很流行，因为它相对容易理解，又能提供强一致性。多主复制和无主复制面对节点故障、网络中断和延迟尖峰时韧性更强，代价是必须解决冲突，而且只能提供较弱的一致性保证。

复制可以同步，也可以异步；发生故障时，这项选择会深刻影响系统行为。系统平稳运行时，异步复制可能很快，但仍必须弄清复制延迟增大或服务器失效时会发生什么。如果领导者失效，而你把一个异步更新的追随者提升为新领导者，最近提交的数据可能丢失。

我们考察了复制延迟可能造成的几种反常现象，并讨论了几种一致性模型，以便判断应用程序在复制延迟下应有怎样的行为：

写后读一致性
用户应当总能看到自己提交的数据。
单调读
用户看到某一时刻的数据后，不应在稍后又看到更早时刻的数据。
一致前缀读
用户看到的数据状态应符合因果关系，例如以正确顺序看到问题及其回答。
最后，我们讨论了多主复制和无主复制如何让所有副本最终收敛到一致状态：用版本向量或类似算法检测哪些写入并发，再用 CRDT 等冲突解决算法合并并发写入的值。最后写入者胜和手工解决冲突也是可选方案。
